# 1단계 — 신원 기반 스키마 명세

> [플랫폼 재설계 제안](./플랫폼-재설계-제안.md) §11 로드맵 1단계의 구현 명세.
> 이후 모든 단계(익명성·회차·품질·보상)가 이 위에 얹히므로, 여기서 잘못 잡으면 전부 흔들립니다.

---

## 1. 범위

| 포함 | 제외 (이후 단계) |
|---|---|
| `AdminUser` → `User` 통합, 다중 역할 | 회차(Campaign) — 3단계 |
| 개인화 링크 토큰 발급/검증 | 문항 단위 익명성 — 2단계 |
| 응답에 respondent 연결 (익명 허용 유지) | 포인트·정산 — 7·8단계 |
| 양식별 신원 요구 수준(`identityMode`) | Prefill — 3단계 |

### 설계 원칙

1. **기존 익명 응답은 그대로 동작해야 합니다.** 신원은 *추가* 능력이지 강제가 아닙니다.
2. **토큰 원문은 저장하지 않습니다.** 기존 `ApiKey`의 해시 저장 패턴을 그대로 따릅니다.
3. **응답자와 관리자는 같은 테이블**입니다. 총무팀 담당자도 인사팀 설문엔 응답자입니다.

### ⚠️ 선행 의존성

현재 인증은 쿠키(`adminRole`, `adminEmail`)를 신뢰하는 개발용 구조입니다.
**신원이 포인트·개인정보와 연결되는 순간 이 방식은 쓸 수 없습니다.**
`/api/auth/[...nextauth]`가 이미 있으니, 1단계와 **병행하여 실제 인증(SSO 또는 자격증명)** 을
완성해야 합니다. 이것 없이 1단계만 올리면 누구나 헤더를 위조해 타인 행세를 할 수 있습니다.

## 2. 모델 개요

```
User ──┬── UserRole          (다중 역할, 양식 단위 위임 가능)
       ├── RespondentToken   (개인화 링크)
       ├── FormRegistry      (owner)
       ├── ShareRequest      (from/to)
       └── AdminNotification

FormRegistry ── identityMode (ANONYMOUS | IDENTIFIED | AUTHENTICATED | MIXED)

Elasticsearch: SubmissionDocument
       + respondentId?     ← null이면 익명
       + identityLevel     ← 이 응답이 어떤 신원 수준으로 들어왔는지
```

## 3. `User` — `AdminUser` 흡수

```prisma
enum UserStatus {
  ACTIVE
  SUSPENDED // 계정 정지 (기존 isActive=false)
  LEFT      // 퇴사 — 로그인 불가하되 과거 응답·소유이력은 보존
}

model User {
  id       String @id @default(cuid())
  email    String @unique
  name     String
  password String // 실제 인증 도입 시 해시. SSO 전용 계정은 미사용

  // 조직 정보 — 코호트 분석(부서별 추이), k-익명성 임계값, 부서 예산의 기준이 된다.
  employeeNo String? @unique // 사번 — 인사시스템 연동 키
  department String? // 기존 orgName. 부서 개편이 잦으면 이후 Department 모델로 승격
  position   String?

  status     UserStatus @default(ACTIVE)
  // 대량 추출(CSV) 허용 여부 — 개인적 유용 우려로 개별 제한 (기존 필드 유지)
  canBulkExport Boolean @default(true)

  createdAt DateTime  @default(now())
  updatedAt DateTime  @updatedAt
  lastLoginAt DateTime?

  roles                 UserRole[]
  respondentTokens      RespondentToken[]
  formsOwned            FormRegistry[]      @relation("FormOwner")
  shareRequestsSent     ShareRequest[]      @relation("ShareRequestFrom")
  shareRequestsReceived ShareRequest[]      @relation("ShareRequestTo")
  notifications         AdminNotification[]

  @@index([department])
  @@map("users")
}
```

### 기존 필드 처리

| 기존 (`admin_users`) | 처리 |
|---|---|
| `role AdminRole` | **제거** → `UserRole` 행으로 이관 |
| `orgName` | `department`로 rename |
| `isActive Boolean` | `status UserStatus`로 승격 (퇴사자를 정지와 구분해야 함) |
| `canBulkExport` | 유지 |

> 💡 `isActive`를 `status`로 바꾸는 이유: **퇴사자와 정지 계정은 다르게 다뤄야 합니다.**
> 퇴사자는 로그인만 막고 과거 응답·소유 이력은 보존해야 하며(감사·데이터베이스제작자 권리),
> 정지는 제재이므로 해제될 수 있습니다. 불리언으로는 구분이 안 됩니다.

## 4. `UserRole` — 다중 역할 + 양식 단위 위임

```prisma
enum RoleType {
  MEMBER         // 임직원 — 응답, 마이페이지, (이후) 포인트
  AUTHOR         // 양식 제작자 — 양식 CRUD, 자기 양식 데이터
  PLATFORM_ADMIN // 플랫폼 관리자 — 정책·계정·정산
}

model UserRole {
  id     String   @id @default(cuid())
  userId String
  user   User     @relation(fields: [userId], references: [id], onDelete: Cascade)
  role   RoleType

  // 양식 단위 위임 — null이면 전역 권한.
  // AUTHOR를 특정 양식에만 부여하면 "휴가 대행", "담당자 인수인계"가 표현된다.
  scopeFormId String?
  scopeForm   FormRegistry? @relation(fields: [scopeFormId], references: [id], onDelete: Cascade)

  grantedBy String   // 부여한 사람의 email (계정 삭제와 무관하게 이력 보존)
  grantedAt DateTime @default(now())
  expiresAt DateTime? // 한시적 위임 (휴가 대행 등). null이면 무기한

  @@unique([userId, role, scopeFormId])
  @@index([userId])
  @@index([scopeFormId])
  @@map("user_roles")
}
```

### 역할 판정 규칙

```
Guest            = 인증되지 않은 접근 (역할 행이 없음 — 별도 RoleType 아님)
MEMBER           = 로그인했거나 유효한 개인화 토큰을 가진 사람
AUTHOR(전역)     = 모든 양식 제작 가능
AUTHOR(scoped)   = 해당 양식만
PLATFORM_ADMIN   = 전체
```

- 만료된 행(`expiresAt < now`)은 **권한 없음**으로 취급하되 삭제하지 않습니다 (감사 이력).
- 기존 `isOwnerOrSuperAdmin()`은 `PLATFORM_ADMIN` 또는 소유자 또는 **scoped AUTHOR** 로 확장합니다.

## 5. `RespondentToken` — 개인화 링크

```prisma
model RespondentToken {
  id String @id @default(cuid())

  // 원문은 저장하지 않는다. ApiKey와 동일 원칙 — 유출 시 피해 최소화.
  tokenHash   String @unique // SHA-256(원문)
  tokenPrefix String         // 앞 8자 — 목록에서 식별용

  userId String
  user   User   @relation(fields: [userId], references: [id], onDelete: Cascade)
  formId String
  form   FormRegistry @relation(fields: [formId], references: [id], onDelete: Cascade)
  // 3단계에서 campaignId 추가 — 회차별 발송으로 전환

  // ── 보안 ──
  expiresAt DateTime  // 필수. 무기한 토큰은 유출 시 영구 위험
  singleUse Boolean  @default(false)
  usedAt    DateTime?
  revokedAt DateTime?

  // ── 발송/열람 추적 (응답률 진단) ──
  issuedBy    String   // 발급 관리자 email
  issuedAt    DateTime @default(now())
  deliveredAt DateTime?
  openedAt    DateTime?

  @@index([userId, formId])
  @@index([formId, expiresAt])
  @@map("respondent_tokens")
}
```

### `singleUse` 선택 기준

| 설정 | 동작 | 적합한 경우 |
|---|---|---|
| `false` (권장 기본) | 만료 전까지 재진입 가능 | 대부분. 실수로 창을 닫아도 다시 들어올 수 있음 |
| `true` | 1회 제출 후 잠금 | 경품 응모, 투표 등 1인 1회가 엄격한 경우 |

> ⚠️ `singleUse=true`를 기본으로 두지 마세요. 제출 도중 이탈하면 다시 못 들어와
> 재발급 요청이 폭주합니다. 중복 제출 방지는 **`(userId, formId)` 유니크 제약**으로
> 처리하는 편이 안전합니다.

## 6. `FormRegistry` 확장

```prisma
enum IdentityMode {
  ANONYMOUS     // 신원 수집 안 함 (현재 동작 = 기본값)
  IDENTIFIED    // 개인화 링크 필수
  AUTHENTICATED // 로그인 필수
  MIXED         // 토큰 있으면 식별, 없으면 익명 허용
}

model FormRegistry {
  // ... 기존 필드 유지 ...
  identityMode IdentityMode @default(ANONYMOUS)

  respondentTokens RespondentToken[]
  scopedRoles      UserRole[]
}
```

> 💡 **`MIXED`가 실무에서 가장 유용합니다.** 공용 QR(익명)과 개인 링크(식별)를 동시에
> 운영할 수 있어, 임직원은 식별 응답으로 포인트를 받고 외부 방문객은 익명으로 응답합니다.

**기본값을 `ANONYMOUS`로 두는 것이 중요합니다** — 기존 5개 양식의 동작이 바뀌지 않습니다.

## 7. Elasticsearch — `SubmissionDocument` 확장

```ts
export interface SubmissionDocument {
  formId: string;
  submissionId: string;
  submittedAt: string;
  data: Record<string, unknown>;
  externalId?: string;
  source?: 'web' | 'api';
  schemaVersion?: number;

  // ── 1단계 추가 ──
  /** 응답자. null/누락이면 익명 응답. */
  respondentId?: string;
  /** 이 응답이 어떤 신원 수준으로 수집되었는지 — 사후에 신뢰도를 판단하는 근거. */
  identityLevel?: 'ANONYMOUS' | 'IDENTIFIED' | 'AUTHENTICATED';
}
```

매핑 추가:

```ts
const SUBMISSION_MAPPING = {
  properties: {
    // ... 기존 ...
    respondentId:  { type: 'keyword' },
    identityLevel: { type: 'keyword' },
  },
} as const;
```

> ✅ `ensureIndices()`가 기존 인덱스에도 `putMapping`을 수행하도록 이미 고쳐두었으므로,
> 배포만 하면 기존 인덱스에 새 필드가 반영됩니다.
> **`keyword`로 매핑되기 전에 문서가 먼저 들어가면 `text`로 굳어 정확 매칭이 깨집니다** —
> 반드시 매핑 반영 후 쓰기를 여세요. (이전에 `externalId`에서 실제로 겪은 문제입니다.)

기존 문서 백필:

```json
POST /webreport-submissions/_update_by_query
{
  "query": { "bool": { "must_not": { "exists": { "field": "identityLevel" } } } },
  "script": { "source": "ctx._source.identityLevel = 'ANONYMOUS'" }
}
```

## 8. 인증 흐름 — 토큰을 세션으로 교환

### 🔴 URL의 토큰은 그대로 두면 샙니다

`?t=abc123`은 **브라우저 히스토리, Referer 헤더, 웹서버 액세스 로그, 프록시 로그**에 남습니다.
누군가 그 로그를 보면 타인의 응답 링크를 그대로 쓸 수 있습니다.

**반드시 즉시 세션으로 교환하고 URL에서 제거하세요.**

```
1. 사용자가 https://forms.../q/f-101?t=abc123 클릭
2. 서버: 토큰 해시 조회 → 유효성 검사 (만료/폐기/사용여부)
3. 서버: 짧은 수명의 응답 세션 쿠키 발급 (HttpOnly, Secure, SameSite=Lax)
4. 서버: 302 리다이렉트 → /q/f-101   ← 쿼리스트링 제거
5. 이후 요청은 쿠키로 신원 확인. 새로고침해도 안전
```

추가 방어:
- `Referrer-Policy: no-referrer` (양식 페이지)
- nginx 액세스 로그에서 `t=` 파라미터 마스킹
- 응답 세션 쿠키는 **해당 양식에만** 유효 (scope 제한)

### 검증 로직

```ts
async function resolveRespondent(request): Promise<Respondent> {
  // 1) 로그인 세션이 있으면 최우선 (AUTHENTICATED)
  // 2) 응답 세션 쿠키 (IDENTIFIED)
  // 3) URL 토큰 → 검증 후 쿠키 교환 (IDENTIFIED)
  // 4) 없으면 익명 (ANONYMOUS)
}
```

양식의 `identityMode`와 대조해 미달이면 거부합니다.

| identityMode | ANONYMOUS 응답자 | IDENTIFIED | AUTHENTICATED |
|---|---|---|---|
| `ANONYMOUS` | ✅ | ✅ | ✅ |
| `MIXED` | ✅ | ✅ | ✅ (신원은 기록) |
| `IDENTIFIED` | ❌ 403 | ✅ | ✅ |
| `AUTHENTICATED` | ❌ 401 | ❌ 401 | ✅ |

## 9. 마이그레이션 계획

현재 데이터: 사용자 5명, 양식 5개, 제출 데이터 다수. **무중단이 아니어도 되지만 데이터 손실은 불가**합니다.

### 9-1. 순서

```
① 스키마 마이그레이션 (테이블 rename + 신규 테이블)
② 역할 백필 (role 컬럼 → user_roles 행)
③ ES 매핑 반영 + 기존 문서 백필
④ 애플리케이션 배포 (auth 코드 전환)
⑤ 검증 후 role 컬럼 제거 (별도 마이그레이션)
```

> ⚠️ **⑤를 ④와 같은 마이그레이션에 넣지 마세요.** `role` 컬럼을 남겨두면 문제 발생 시
> 즉시 롤백할 수 있습니다. 배포가 안정된 것을 확인한 뒤 다음 릴리스에서 제거합니다.

### 9-2. SQL 개요

```sql
-- ① 테이블/컬럼 전환
ALTER TABLE "admin_users" RENAME TO "users";
ALTER TABLE "users" RENAME COLUMN "orgName" TO "department";
ALTER TABLE "users" ADD COLUMN "employeeNo" TEXT UNIQUE,
                    ADD COLUMN "position" TEXT,
                    ADD COLUMN "updatedAt" TIMESTAMP(3),
                    ADD COLUMN "lastLoginAt" TIMESTAMP(3);

CREATE TYPE "UserStatus" AS ENUM ('ACTIVE','SUSPENDED','LEFT');
ALTER TABLE "users" ADD COLUMN "status" "UserStatus" NOT NULL DEFAULT 'ACTIVE';
UPDATE "users" SET "status" = 'SUSPENDED' WHERE "isActive" = false;
-- isActive는 ⑤ 단계에서 제거

-- ② 역할 백필 — 기존 role 컬럼을 행으로
CREATE TYPE "RoleType" AS ENUM ('MEMBER','AUTHOR','PLATFORM_ADMIN');
CREATE TABLE "user_roles" ( ... );

INSERT INTO "user_roles" ("id","userId","role","grantedBy","grantedAt")
SELECT gen_random_uuid()::text, id,
       CASE WHEN role = 'SUPER_ADMIN' THEN 'PLATFORM_ADMIN'::"RoleType"
            ELSE 'AUTHOR'::"RoleType" END,
       'migration', NOW()
FROM "users";

-- 기존 관리자는 모두 응답자이기도 하다
INSERT INTO "user_roles" ("id","userId","role","grantedBy","grantedAt")
SELECT gen_random_uuid()::text, id, 'MEMBER'::"RoleType", 'migration', NOW()
FROM "users";

-- ③ 양식 신원 모드 — 기존 동작 유지
ALTER TABLE "form_registry"
  ADD COLUMN "identityMode" "IdentityMode" NOT NULL DEFAULT 'ANONYMOUS';

-- ④ 토큰 테이블
CREATE TABLE "respondent_tokens" ( ... );
```

> FK 이름은 Postgres가 테이블 rename 시 자동으로 따라오므로 `form_registry.ownerId`,
> `share_requests.fromUserId/toUserId`, `admin_notifications.userId`는 **수정이 필요 없습니다.**
> Prisma 스키마에서 참조 타입만 `AdminUser` → `User`로 바꾸면 됩니다.

### 9-3. 롤백

| 시점 | 롤백 방법 |
|---|---|
| ①~② 직후 | `role` 컬럼이 남아 있으므로 이전 앱 버전 재배포로 즉시 복구 |
| ③ 이후 | ES 신규 필드는 무시해도 동작에 영향 없음 (선택적 필드) |
| ⑤ 이후 | 롤백 불가 — 반드시 안정성 확인 후 실행 |

## 11. 완료 기준 (검증 시나리오)

기존 회귀 + 신규 기능을 함께 확인합니다.

| # | 시나리오 | 기대 |
|---|---|---|
| 1 | 기존 익명 양식(`ANONYMOUS`)에 로그인 없이 응답 | ✅ 200 — **기존 동작 불변** |
| 2 | 기존 제출 데이터 조회 | ✅ `identityLevel: ANONYMOUS`로 표시 |
| 3 | `IDENTIFIED` 양식에 토큰 없이 접근 | ❌ 403 |
| 4 | 유효 토큰으로 접근 | ✅ 리다이렉트 후 URL에 `t=` 없음, 쿠키 발급 |
| 5 | 만료/폐기 토큰 | ❌ 401 + 재발급 안내 |
| 6 | 타 양식 토큰으로 접근 | ❌ 403 |
| 7 | 토큰 응답 제출 | ✅ `respondentId` 기록됨 |
| 8 | `MIXED` 양식에 토큰 없이 | ✅ 익명으로 수집 |
| 9 | scoped AUTHOR가 담당 양식 편집 | ✅ 허용 |
| 10 | scoped AUTHOR가 타 양식 편집 | ❌ 403 |
| 11 | 만료된 역할 위임 | ❌ 403 |
| 12 | 기존 RBAC 전체 회귀 | ✅ 이전 검증 시나리오 전부 통과 |

---

## 12. 이 단계에서 미리 잡아둘 것

이후 단계에서 **스키마를 다시 뒤집지 않으려면** 지금 고려해 두어야 합니다.

- `RespondentToken`에 `campaignId` 자리 — 3단계에서 회차별 발송으로 전환
- `SubmissionDocument`에 `revision` — 재제출/수정 이력 (3단계 prefill과 연결)
- `User.department` — 부서 개편이 잦다면 `Department` 모델로 승격 (k-익명성·예산의 기준)
- 개인정보 보관기간 필드 — 신원이 붙는 순간 파기 정책이 필요해집니다 (§11 리스크)
