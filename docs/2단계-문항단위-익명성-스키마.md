# 2단계 — 문항 단위 익명성 스키마 명세

> [플랫폼 재설계 제안](./플랫폼-재설계-제안.md) §5의 구현 명세.
> [1단계 신원 기반](./1단계-신원기반-스키마.md)이 선행되어야 합니다 — 신원이 붙은 뒤에야
> "무엇을 신원과 분리할지"가 문제가 되기 때문입니다.

---

## 1. 범위와 위협 모델

### 무엇을 보장하는가

> 🔒 **"당신이 응답했다는 사실"은 기록되지만, "당신이 무엇이라고 답했는지"는
> 누구도 — 양식 제작자도, 플랫폼 관리자도 — 알 수 없습니다.**

이 구분이 중요합니다. 참여 사실까지 숨기면 보상 지급(7단계)이 불가능해지고,
응답률 집계도 못 합니다. **참여는 기록하되 내용을 분리**하는 것이 실용적인 지점입니다.

### 위협 모델

| 상정하는 공격자 | 대응 |
|---|---|
| DB/ES에 직접 접근 가능한 운영자 | ✅ 주 대상 — 구조적으로 결합 불가하게 |
| 관리자 화면을 쓰는 양식 제작자 | ✅ 개별 응답 자체를 제공하지 않음 |
| 소수 응답을 조합해 특정하려는 시도 | ✅ k-익명성 임계값 |
| 애플리케이션 서버를 장악한 공격자 | ❌ 범위 밖 (제출 시점 평문을 볼 수 있음) |

마지막 항목은 정직하게 인정해야 합니다. **제출 순간에는 서버가 두 조각을 모두 보므로**,
서버가 완전히 장악되면 방어할 수 없습니다. 이 명세가 막는 것은 **사후 결합**입니다.

## 2. 모델 개요

```
제출 1건
   │
   ├─→ 식별 문서   webreport-submissions        respondentId 있음, 일반 문항만
   │                                            (참여 사실 = 보상·응답률의 근거)
   │
   └─→ 익명 버퍼   anonymous_response_buffer    Postgres, 암호문으로 임시 보관
          │        (k건 모일 때까지 대기)
          ↓ flush (셔플)
        익명 문서   webreport-anon-submissions   respondentId 없음, 익명 문항만
```

**버퍼를 거치는 이유는 §5에서 설명합니다** — 즉시 쓰면 저장 순서가 곧 응답자 순서가 됩니다.

## 3. `FormField` 확장 — 익명 플래그

Elasticsearch의 폼 템플릿 문서에 들어가는 필드 정의에 플래그를 추가합니다.

```ts
// src/components/builder/types.ts
export interface FormField {
  // ... 기존 필드 ...

  /**
   * 이 문항의 응답을 응답자와 분리해 익명 저장한다.
   * true인 문항은 식별 문서에 저장되지 않고, 별도 인덱스에 셔플되어 적재된다.
   * 한 번 확정(PUBLISHED)된 뒤에는 변경할 수 없다 — §9 참고.
   */
  anonymous?: boolean;
}
```

### 🔴 확정 후 익명 플래그 변경 금지

이것이 이 단계에서 가장 중요한 제약입니다.

| 변경 | 왜 금지인가 |
|---|---|
| 일반 → 익명 | 이미 식별 저장된 과거 응답은 익명이 되지 않는다. "익명입니다"라고 안내하면서 과거분은 식별 상태 — **거짓 약속** |
| 익명 → 일반 | 응답자가 익명을 믿고 답한 내용이 소급해서 식별 대상이 된다 — **신뢰 배반** |

**구현:** `updateForm()`에서 `lifecycle === 'PUBLISHED'`인 양식의 필드 `anonymous` 값이
바뀌면 거부합니다. 바꾸려면 **새 양식으로 만들어야** 합니다.

> 💡 이는 이미 있는 `schemaVersion` 증가 규칙보다 강한 제약입니다. 다른 속성은 버전만
> 올리면 되지만, 익명 여부는 응답자와의 약속이므로 되돌릴 수 없습니다.

## 4. 제출 분리 파이프라인

```
submitFormResponse(formId, data, respondent)
  │
  ├ 1. 검증        전체 data로 필수/정규식 검사 (분리 전에)
  ├ 2. 분할        template.fields의 anonymous 플래그로 두 조각으로
  │
  ├ 3a. 식별 저장   ES webreport-submissions
  │                { respondentId, submissionId, submittedAt(정확), data: 일반문항 }
  │
  └ 3b. 익명 버퍼   Postgres anonymous_response_buffer
                   { id: 랜덤, formId, payloadEncrypted, bucketAt: 절삭 }
                   ※ respondentId 없음, 정확한 시각 없음
```

**분할은 서버에서만** 수행합니다. 클라이언트가 두 요청으로 나눠 보내면
네트워크 계층에서 상관관계가 노출됩니다.

### 익명 문항만 있는 양식

식별 문서는 `data: {}`로 여전히 생성합니다. 참여 사실이 남아야
보상 지급과 응답률 집계가 가능하기 때문입니다.

## 5. `AnonymousResponseBuffer` — 왜 버퍼가 필요한가

익명 문서를 제출 즉시 쓰면 **저장 순서가 곧 응답 순서**가 됩니다.
식별 문서의 `submittedAt`으로 응답 순서를 알 수 있으므로, 두 인덱스를 순서대로
줄 세우면 그대로 매칭됩니다. 타임스탬프를 아무리 절삭해도 이건 막히지 않습니다.

```prisma
/// 익명 응답의 임시 보관소.
///
/// 익명 문항 응답을 즉시 ES에 쓰지 않고 여기에 모았다가, k건 이상 쌓이면
/// 순서를 섞어 한꺼번에 적재한다. 이렇게 해야 "몇 번째로 저장되었는가"가
/// 응답자를 특정하는 단서가 되지 않는다.
///
/// payload는 암호화해 보관한다 — 버퍼에 머무는 짧은 시간 동안에도 DB를 직접
/// 들여다보는 것만으로 내용을 읽을 수 없게 하기 위함이다.
model AnonymousResponseBuffer {
  id     String @id @default(cuid())
  formId String
  form   FormRegistry @relation(fields: [formId], references: [id], onDelete: Cascade)

  /// AES-256-GCM으로 암호화된 익명 문항 응답(JSON). src/lib/crypto.ts 사용.
  payloadEncrypted String
  /// 절삭된 제출 시각(기본 1시간 단위). 정확한 시각은 저장하지 않는다.
  bucketAt      DateTime
  schemaVersion Int

  /// 제출 직후 잠깐만 유효한 수정 키. flush 시점에 버려지므로,
  /// 적재된 뒤에는 본인조차 자기 익명 응답을 지목할 수 없다(§9).
  editTokenHash String?
  editExpiresAt DateTime?

  createdAt DateTime @default(now())

  @@index([formId])
  @@map("anonymous_response_buffer")
}
```

### flush 규칙

| 조건 | 동작 |
|---|---|
| 버퍼 건수 ≥ 임계값(k) | 전량 셔플 후 적재, 버퍼 삭제 |
| 양식 마감(CLOSED) 시 잔여분 존재 | 적재하되 `belowThreshold: true` 표시 → 조회 차단 |
| 버퍼에 머무는 동안 | 응답자 본인만 `editToken`으로 수정 가능 |

> ⚠️ **`createdAt`은 그 자체로 미세한 단서입니다.** 버퍼 행의 생성 순서를 직접 보면
> 응답 순서를 알 수 있습니다. 다만 ①payload가 암호문이고 ②flush 후 즉시 삭제되며
> ③버퍼 접근은 애플리케이션 서버만 가능하므로, 노출 창을 짧게 두는 선에서 절충합니다.
> 더 강한 보장이 필요하면 `createdAt`을 `bucketAt`으로 대체하세요(수정 만료 판정만 잃습니다).

## 6. 익명 인덱스 (Elasticsearch)

```ts
export const INDEX_NAMES = {
  FORM_TEMPLATES: 'webreport-form-templates',
  SUBMISSIONS: 'webreport-submissions',
  ANON_SUBMISSIONS: 'webreport-anon-submissions', // 신규
};

export interface AnonymousSubmissionDocument {
  /** 랜덤 UUID. 식별 문서의 submissionId와 어떤 관계도 없다. */
  anonId: string;
  formId: string;
  /** 절삭된 시각(기본 1시간 단위). 정확한 제출 시각은 존재하지 않는다. */
  bucketAt: string;
  schemaVersion: number;
  /** 익명 문항만. respondentId·submissionId는 의도적으로 없다. */
  data: Record<string, unknown>;
  /** 이 배치가 k 임계값 미만으로 적재되었는지 — true면 조회를 막는다. */
  belowThreshold: boolean;
}
```

```ts
const ANON_SUBMISSION_MAPPING = {
  properties: {
    anonId:         { type: 'keyword' },
    formId:         { type: 'keyword' },
    bucketAt:       { type: 'date' },
    schemaVersion:  { type: 'integer' },
    belowThreshold: { type: 'boolean' },
    data:           { type: 'object', dynamic: true },
  },
} as const;
```

> ⚠️ `externalId`에서 겪었듯, **매핑을 반영하기 전에 문서가 먼저 들어가면
> `keyword`가 아닌 `text`로 굳습니다.** `ensureIndices()`가 이미 `putMapping`을
> 수행하므로 배포만 하면 되지만, 순서는 반드시 매핑 → 쓰기입니다.

## 7. 재식별 경로와 대응 (전수)

| # | 경로 | 대응 | 잔여 위험 |
|---|---|---|---|
| 1 | 문서 id 공유 | 익명 문서는 **독립 랜덤 UUID** | 없음 |
| 2 | 정확한 타임스탬프 | **절삭**(기본 1시간), 정확한 값 미저장 | 시간대에 1명뿐이면 특정 가능 → #5로 보완 |
| 3 | **저장 순서** | **버퍼 + k건 모아 셔플 적재** | 버퍼 행 순서(짧은 노출) |
| 4 | 순차 ID | 랜덤 UUID 사용 | 없음 |
| 5 | 소수 응답 | **k-익명성 게이트**(§8) | 임계값 설정에 의존 |
| 6 | **감사 로그** | 익명 부분은 **응답자·시각을 로그에 남기지 않음** | ⚠️ 아래 참조 |
| 7 | 자유응답 내용 | 서술만으로 특정 가능 — 시스템이 막을 수 없음 | 응답자에게 사전 고지 |
| 8 | 총계 상관 | 응답자 1명 → 익명 문서 1건이면 자명 | k-익명성으로 차단 |

### 🔴 #6 감사 로그가 가장 놓치기 쉬운 경로입니다

지금 `submitFormResponse`는 이상치 감지 시 감사 로그를 남깁니다.
**익명 문항에서 발견된 이상치를 응답자·시각과 함께 기록하면 익명성이 그대로 깨집니다.**

```
❌  DATA_ANOMALY  user=kim@co.kr  time=14:23:07  "상사평가 문항 형식 오류"
✅  DATA_ANOMALY  user=system     time=<절삭>     "익명 문항 1건 형식 오류"
```

**규칙:** 익명 문항 관련 로그는 `userEmail='system(anon)'`, 시각은 절삭,
문항 라벨과 값은 기록하지 않습니다. 소유자 알림도 마찬가지로 건수만 알립니다.

## 8. k-익명성 — 읽기 시점 게이트

```prisma
model SystemConfig {
  // ... 기존 ...
  /// 익명 응답 결과를 공개하기 위한 최소 응답 수. 이보다 적으면 조회를 막는다.
  defaultAnonymityThreshold Int @default(5)
}

model FormRegistry {
  // ... 기존 ...
  /// 이 양식의 익명 임계값 override. null이면 시스템 기본값을 따른다.
  anonymityThreshold Int?
}
```

### 임계값은 전체가 아니라 **결과 집합**에 적용합니다

가장 흔한 실수: 전체 응답이 100건이라고 안심하는 것.

```
전체 100건 → 통과 ✅
  └ 부서=기획팀 필터 → 3건 → 🔴 차단해야 함
```

**모든 집계·교차분석의 최종 결과 집합**에 임계값을 걸어야 합니다.

```ts
// 조회 게이트 (개념)
async function assertAnonymityThreshold(formId, filters) {
  const count = await countAnonSubmissions(formId, filters);
  const threshold = form.anonymityThreshold ?? config.defaultAnonymityThreshold;
  if (count < threshold) throw new Error('BELOW_ANONYMITY_THRESHOLD');
  if (batchHasBelowThresholdDocs) throw new Error('BELOW_ANONYMITY_THRESHOLD');
}
```

응답:

```json
{
  "error": "BELOW_ANONYMITY_THRESHOLD",
  "message": "응답 수가 적어 개인이 특정될 수 있으므로 결과를 제공하지 않습니다.",
  "required": 5
}
```

> 💡 **정확한 현재 건수를 알려주지 마세요.** "3건이라 못 봅니다"라고 하면
> 필터를 바꿔가며 건수를 탐색해 역추적할 수 있습니다. 임계값만 알립니다.

## 9. 접근 제어 — 누구도 개별 응답을 볼 수 없다

| 대상 | 익명 문항 |
|---|---|
| 양식 제작자(소유자) | 개별 ❌ / 집계 ✅ (임계값 충족 시) |
| 플랫폼 관리자 | 개별 ❌ — **관리자도 예외가 아니어야 신뢰가 섭니다** |
| 응답자 본인 | 개별 ❌ — §10 참조 |
| CSV 추출 / v1 API | 집계 또는 셔플된 값만 |

**자유응답(FREE_TEXT) 익명 문항**은 집계가 불가능하므로, 임계값 충족 시
**순서를 섞어 목록으로만** 제공합니다. 시각·부서 등 어떤 메타데이터도 붙이지 않습니다.

> 이는 권한 설정이 아니라 **서비스 계층에서 강제**해야 합니다.
> 익명 문서를 개별 반환하는 함수 자체를 만들지 않는 것이 가장 확실합니다.

## 10. 응답자에게 보이는 것

### 응답 화면

```
3. 조직 문화 만족도                      🔒 익명
   [ ○ 매우만족  ○ 만족  ● 보통  ○ 불만 ]
   이 문항은 익명으로 저장되며 작성자와 연결되지 않습니다.
```

폼 상단에도 요약: *"이 설문의 3~5번 문항은 익명 처리됩니다."*

### 마이페이지 (6단계)

익명 문항은 **본인에게도 내용을 보여주지 않습니다.**

```
[2026 조직문화 조사]  응답 완료 · 2026-01-15
  └ 🔒 익명 문항 3개 — 내용은 조회할 수 없습니다
```

> 본인에게 보여주는 것조차 "어딘가에 당신과 연결되어 저장되어 있다"는 뜻이 되어
> 익명성 주장이 무너집니다. 이 제약을 응답 시점에 미리 안내해야 합니다.

## 11. 제약사항 — 반드시 사전 고지할 것

익명성의 대가로 포기해야 하는 기능들입니다. **응답 화면에 명시하세요.**

| 불가능한 것 | 이유 |
|---|---|
| 제출 후 익명 응답 수정 | 어느 문서가 본인 것인지 지목할 수 없음 (버퍼 단계에서만 가능) |
| 익명 응답 개별 삭제 | 위와 동일 |
| 익명 문항의 개인별 추세 | 회차 간 연결 자체가 재식별 경로 |
| 익명 문항 기반 후속 조치 | *"불만이라고 답한 분께 연락"* — 구조적으로 불가 |

### 법적 함의 — 이건 오히려 유리합니다

개인정보보호법상 **적법하게 익명처리된 정보는 개인정보가 아닙니다.**
따라서 익명 문항 응답에는 정보주체의 열람·정정·삭제 요구가 적용되지 않습니다.

다만 **"적법한 익명처리"로 인정받으려면 재식별 불가능성을 입증할 수 있어야** 합니다.
§7의 대응 항목과 §8 임계값 설정을 **문서로 남겨두세요** — 그것이 입증 근거가 됩니다.

> ⚠️ 반대로, 익명이라 이름 붙였지만 실제로는 결합 가능한 상태라면 개인정보로 취급되며,
> "익명"이라는 고지 자체가 허위가 됩니다. §7을 형식적으로 넘기면 안 되는 이유입니다.

---

## 12. 마이그레이션

기존 제출 데이터는 전부 **일반(식별) 문항**으로 취급됩니다.

```
① FormField.anonymous 추가 — 선택적 필드이므로 기존 템플릿은 무변경(= false)
② ES 익명 인덱스 생성 (ensureIndices에 추가)
③ anonymous_response_buffer 테이블 생성
④ SystemConfig.defaultAnonymityThreshold, FormRegistry.anonymityThreshold 추가
⑤ 애플리케이션 배포
```

**기존 데이터 이관은 없습니다.** 이미 식별 상태로 저장된 것을 사후에 익명화해도
원본이 그대로 남아 의미가 없고, 오히려 "익명화했다"는 잘못된 안심을 줍니다.
**익명이 필요한 양식은 새로 만드는 것이 맞습니다.**

### flush를 무엇이 트리거하는가

| 방식 | 적합성 |
|---|---|
| 제출 시 인라인 검사 (k 도달하면 flush) | ✅ 권장 — 별도 프로세스 불필요, 온프레미스에 적합 |

| 양식 마감 시 | 필수 — 잔여분을 `belowThreshold`로 적재 |

## 14. 완료 기준 (검증 시나리오)

| # | 시나리오 | 기대 |
|---|---|---|
| 1 | 익명 문항 없는 기존 양식 제출 | ✅ 기존과 동일하게 단일 문서 |
| 2 | 익명 문항 포함 양식 제출 | ✅ 식별 문서에 익명 문항 **부재**, 버퍼에 1건 |
| 3 | 식별 문서와 익명 문서 간 공통 키 | ✅ **없음** (id·시각·순서 모두 불일치) |
| 4 | k-1건까지 제출 | ✅ 익명 인덱스 비어 있음 (버퍼 대기) |
| 5 | k번째 제출 | ✅ k건 일괄 적재, `bucketAt` 절삭 확인 |
| 6 | 적재 순서 vs 제출 순서 | ✅ **불일치**(셔플됨) |
| 7 | 임계값 미만 상태로 집계 조회 | ❌ `BELOW_ANONYMITY_THRESHOLD` |
| 8 | 전체는 충족하나 부서 필터가 미달 | ❌ 차단 — **가장 중요한 케이스** |
| 9 | 슈퍼관리자가 개별 익명 응답 조회 | ❌ API 자체가 없음 |
| 10 | CSV 추출 | ✅ 익명 문항 열이 없거나 집계값 |
| 11 | 익명 문항 이상치 감사 로그 | ✅ 응답자·정확시각·값 **미기록** |
| 12 | 확정된 양식의 `anonymous` 변경 | ❌ 거부 |
| 13 | 마이페이지에서 익명 문항 | ✅ "조회할 수 없습니다" 표시 |

## 15. 3단계(회차)와의 접점

미리 잡아둘 것:

- `AnonymousResponseBuffer.campaignId` 자리 — 회차별로 버퍼와 임계값이 분리되어야 합니다
  (Q1 3건 + Q2 3건 = 6건으로 임계값을 채우면 안 됩니다)
- 익명 문서에도 `campaignId` — 회차별 집계 비교용
- **회차 간 개인 추세는 익명 문항에서 불가능**함을 3단계 설계 시 전제로 둘 것
