# 양식지·데이터 플랫폼 재설계 제안

> 기획의도(부서가 양식을 만들고 → 배포하고 → 데이터를 모아 → 분석·보고에 쓰는 업무의 반복)를
> 실제로 굴러가게 하려면, 지금 구조에서 **두 가지 근본 전환**이 먼저 필요합니다.
> 보상(포인트)·최신화·추세분석·저장효율·품질관리는 전부 그 두 가지 위에 얹히는 것들입니다.

---

## 1. 현재 구조 진단

### 잘 되어 있는 것

| 영역 | 현황 |
|---|---|
| 양식 정의 | 23종 컴포넌트, 정형(Postgres 운영 메타) / 비정형(ES 필드구성) 분리가 적절 |
| 계약 안정성 | `lifecycle(DRAFT/PUBLISHED)` + `schemaVersion` — 외부 연동 계약 고정/변경감지 |
| 외부 연동 | v1 API (커서 대량조회, 멱등 대량입력, 스코프 키) — "분석 가능한 형태로 변환"의 토대 |
| 거버넌스 | 소유권, 공유승인, 감사로그, 대량추출 제한, 데이터베이스제작자 권리 |

이 토대는 버릴 게 없습니다. 아래 제안은 **교체가 아니라 확장**입니다.

### 막혀 있는 것 — 근본 원인 2가지

#### 🔴 원인 A. 응답자에게 신원이 없다

현재 `SubmissionDocument`:

```ts
{ formId, submissionId, submittedAt, data, externalId, source, schemaVersion }
//                                    ↑ "누가" 냈는지가 없음
```

응답은 `/q/{formId}`에 로그인 없이 들어와 익명으로 쌓입니다. 응답률에는 최선이지만,
**요청하신 기능 대부분이 "누가 냈는지"를 전제로 합니다.**

- 보상(포인트) → 누구에게 줄지 모름
- 최신화 → 이 사람의 지난 응답이 뭐였는지 모름
- 추세 확인 → 같은 사람의 변화인지, 다른 사람인지 구분 불가
- 공정한 보상 룰 → 중복 수령·어뷰징 방어 불가

#### 🔴 원인 B. "양식지 = 수집 1회"로 묶여 있다

`FormRegistry` 하나에 `submissionCount`, `startsAt/expiresAt`이 직접 붙어 있습니다.
즉 **한 양식은 한 번의 수집**입니다. 그래서 분기마다 다시 걷으려면 양식을 새로 만들어야 하고,
이것이 지적하신 *"또 다시 양식지를 생성해야 하는 반복 업무"* 의 정체입니다.

이 하나를 풀면 연쇄적으로 해결됩니다:

```
반복 수집  →  양식 재생성 불필요
추세 분석  →  회차가 곧 시계열 축이 됨
저장 효율  →  회차 간 변경분(delta)만 저장 가능
보상 공정  →  "회차당 1회 지급"이라는 명확한 기준이 생김
```

## 2. 두 개의 근본 전환

### 전환 1. 응답자 신원 — "로그인 없이"와 "누군지 안다"를 양립시키기

로그인을 강제하면 응답률이 떨어집니다. 기획의도(로그인 없이 들어오게 한다)를 지키면서
신원을 얻는 방법은 **개인화 링크(tokenized personal link)** 입니다.

```
배포 시:  임직원 각각에게 고유 토큰이 박힌 URL을 발급
          https://forms.company.com/q/f-101?t=abc123...

응답자:   링크 클릭 → 로그인 화면 없이 바로 폼 (체감상 익명과 동일)
시스템:   토큰으로 "김OO 사원"임을 이미 알고 있음
```

이메일/메신저로 개인별 링크를 뿌리면 되고, QR을 쓴다면 공용 QR(익명) + 개인 링크(식별) 두 종류를 함께 운영합니다.

**신원 등급을 3단으로 두는 것을 권합니다.** 모든 양식에 신원을 강제할 필요는 없습니다.

| 등급 | 방식 | 포인트 | 최신화/prefill | 용도 |
|---|---|---|---|---|
| **익명(Anonymous)** | 공개 URL/QR | ❌ | ❌ | 고객사 설문, 익명 고충 |
| **식별(Identified)** | 개인화 링크 토큰 | ✅ | ✅ | 임직원 대상 대부분 |
| **인증(Authenticated)** | 로그인(SSO) | ✅ | ✅ | 민감정보, 마이페이지 |

> ⚠️ **익명성은 양식 전체가 아니라 문항 단위로 필요합니다.** 한 양식 안에서 어떤 문항은
> 신원이 필요하고(후속 조치용) 어떤 문항은 익명이어야 하는(조직문화 평가 등) 경우가 실제로
> 더 흔합니다. 이 문제는 난이도가 달라 **§5에서 따로 다룹니다.**

### 전환 2. 양식(정의)과 수집(회차)의 분리

```
FormTemplate          양식 정의 — 재사용 가능. 필드 구성, schemaVersion
   └── Campaign       수집 회차 — "2026 Q1 정기조사". 기간, 대상자, 보상규칙
         └── Submission   응답 — respondent + campaign + data
```

| 수집 유형 | Campaign 설정 | 예시 |
|---|---|---|
| **일회성(One-off)** | 회차 1개 | 워크샵 참가 신청 |
| **주기적 갱신(Recurring)** | 분기/월 자동 생성 | 보유장비 현황, 자격증 최신화 |
| **상시(Continuous)** | 기간 무제한 1회차 | 고객 문의 접수 |

주기 수집은 스케줄러가 회차를 자동 생성하고 대상자에게 개인화 링크를 발송합니다.
**양식 제작자는 양식을 한 번만 만들면 됩니다.**

## 3. 역할 체계 재설계

현재는 `AdminUser(ADMIN/SUPER_ADMIN)` 하나뿐이고 응답자 모델이 없습니다.

> 💡 중요: **응답자와 관리자는 별개의 사람이 아닙니다.** 총무팀 담당자도 인사팀 설문에는
> 응답자입니다. 그러니 테이블을 둘로 나누지 말고, **`User` 하나에 역할을 여러 개 부여**하세요.
> 지금 구조(AdminUser만 존재)를 그대로 두고 응답자 테이블을 따로 만들면, 같은 사람이 두 곳에
> 중복 존재하며 포인트 귀속이 꼬입니다.

| 역할 | 핵심 권한 | 필요한 화면 |
|---|---|---|
| **Guest** | 공개 양식 응답 | `/q/{id}` |
| **Member**(임직원) | 응답 + 포인트 + 내 이력 | **마이페이지**(신규): 내 응답 이력, 포인트 잔액/내역, 갱신 요청 목록 |
| **Author**(양식 제작자) | 양식 CRUD, 캠페인 운영, 자기 양식 데이터 | 기존 admin + **캠페인 관리**(신규), **품질 대시보드**(신규) |
| **Platform Admin** | 포인트 룰/정산, 품질 정책, 계정, 거버넌스 | 기존 super-admin + **보상 정책**(신규), **정산 승인**(신규) |

역할 부여는 `UserRole` 다대다로 두고, **Author 권한은 양식 단위로 위임** 가능하게 하는 것이
부서 협업(담당자 교체, 휴가 대행)에 유리합니다. 현재 소유권 이전 기능이 있으니 그 연장선입니다.

## 4. 반복 수집 & 최신화 설계

### 4-1. 사전 채움(Prefill) — 이게 진짜 "반복 업무 해방"

주기 수집에서 응답자가 겪는 고통은 *"지난번과 똑같은 걸 또 적는 것"* 입니다.

```
갱신 요청 링크 클릭
  → 지난 회차 응답이 이미 채워진 상태로 폼이 열림
  → "변경사항 없음" 버튼 한 번  또는  바뀐 항목만 수정
  → 제출
```

응답 부담이 10분에서 30초로 줄어듭니다. **포인트보다 이것이 응답률에 더 크게 작용할 수 있습니다.**

필드 단위로 prefill 정책을 둘 수 있게 하세요:
- `carry-over`: 지난 값 그대로 (부서, 직급 등 잘 안 바뀌는 것)
- `clear`: 매번 새로 (이번 분기 실적 등)
- `carry-with-confirm`: 채워주되 확인 체크 필수 (자격증 유효기간 등 — 무심코 넘기면 안 되는 것)

### 4-2. 저장 효율 — Current + History 분리

*"반복 입력 데이터의 저장공간 효율화"* 에 대한 답입니다. 회차마다 전체 응답을 통째로 쌓으면
20개 필드 중 1개만 바뀌어도 20개를 다시 저장하게 됩니다.

```
current_records   (respondent × form 당 1건)   ← "지금의 최신 상태". 조회는 대부분 여기서
record_history    (변경분 delta만)              ← "언제 무엇이 어떻게 바뀌었나". 추세는 여기서
```

- 최신 현황 조회가 **O(1)** 로 빨라집니다 (지금은 전체 스캔 후 최신 골라내기)
- 변경 없는 필드는 저장하지 않아 저장량이 크게 줄어듭니다
- "이 값이 언제 바뀌었나" 감사 추적이 자연스럽게 따라옵니다

추가로 Elasticsearch **ILM(Index Lifecycle Management)** 로 오래된 회차 인덱스를
warm/cold 티어로 내리면 비용이 더 줄어듭니다.

> ⚠️ 단, delta 저장은 **복원 로직이 정확해야** 합니다. 특정 시점 스냅샷 재구성 기능과
> 그에 대한 테스트를 반드시 함께 만드세요. 여기서 버그가 나면 데이터 신뢰가 무너집니다.

## 5. 문항 단위 익명성

한 양식 안에 성격이 다른 문항이 섞이는 것이 현실입니다.

```
[부서]        [이름]        [담당업무]      ← 후속 조치·최신화에 필요 (식별)
[상사 평가]   [조직문화 만족도]  [고충사항]   ← 익명이어야 솔직한 답이 나옴 (익명)
```

양식 전체를 익명으로 돌리면 최신화·보상이 막히고, 전체를 식별로 돌리면 솔직한 답이 안 나옵니다.
**문항 단위로 익명 플래그**를 두고, 저장 자체를 물리적으로 분리해야 합니다.

### 5-1. 물리적 분리 저장

제출 시 하나의 응답을 **두 개의 문서로 쪼개서** 서로 다른 인덱스에 저장합니다.

```
identified_submissions     respondent 있음, 일반 문항만
anonymous_submissions      respondent 없음, 익명 문항만  ← 별도 인덱스
```

### 5-2. 🔴 조인 가능한 어떤 키도 공유하면 안 됩니다

여기가 가장 실수하기 쉬운 지점입니다. 분리해서 저장했더라도 두 문서를 다시 이어붙일 수 있으면
익명성은 없는 것과 같습니다. 아래는 **전부 재식별 경로**입니다.

| 위험 요소 | 왜 위험한가 | 방어 |
|---|---|---|
| 같은 `submissionId` 공유 | 그대로 조인됨 | 익명 문서는 **독립 랜덤 ID** |
| 정확한 `submittedAt` | 초 단위면 사실상 유일 → 시각 매칭 | 시간 단위로 **절삭**(예: 정시 단위) |
| 저장 순서 | 두 인덱스의 도착 순서로 매칭 | **배치 지연 + 셔플** 후 색인 |
| 소수 응답 | 5명 응답에 부서 필터 → 개인 특정 | **k-익명성 임계값**(아래) |
| 자유응답 내용 | 문체·사건 서술로 특정 가능 | 원문 노출 최소화, 필요 시 요약만 |

### 5-3. k-익명성 — 소수 응답 보호

익명 문항이라도 응답자가 적으면 조합으로 특정됩니다.
*"기획팀에서 조직문화 2점을 준 사람"* — 기획팀이 4명이면 사실상 실명입니다.

- **최소 응답 수(예: 5~10건) 미만이면 결과 자체를 비공개** 처리
- 부서·직급 등으로 **필터링·교차분석 시에도 동일 임계값** 적용
  (전체는 100건이어도 필터 결과가 3건이면 막아야 합니다)
- 임계값은 정책으로 설정 가능하게

### 5-4. 제작자도 볼 수 없어야 합니다

현재 소유자는 자기 양식 데이터를 전부 볼 수 있습니다. **익명 문항은 예외 처리가 필요합니다.**

| 대상 | 익명 문항 접근 |
|---|---|
| 양식 제작자(소유자) | 개별 응답 ❌ / 집계만 ✅ (k-임계값 충족 시) |
| 플랫폼 관리자 | 개별 응답 ❌ — 관리자도 예외가 아니어야 신뢰가 섭니다 |
| 데이터 추출(CSV/API) | 익명 문항은 respondent 없이, 집계 또는 셔플된 형태로만 |

> 익명성은 "약속"이 아니라 **시스템이 강제하는 구조**여야 합니다.
> 권한 설정으로 막는 방식은 언제든 풀 수 있어 신뢰의 근거가 되지 못합니다.

### 5-5. 응답자에게 보이는 것

신뢰는 **눈에 보여야** 생깁니다.

- 익명 문항 옆에 배지: 🔒 *"이 문항은 익명으로 저장되며, 작성자와 연결되지 않습니다"*
- 폼 상단에 요약: *"이 설문의 3~5번 문항은 익명 처리됩니다"*
- 제출 완료 화면에 재확인

## 6. 보상(포인트) 설계

### 6-1. 원장(Ledger)은 append-only로

**가장 중요한 조언입니다.** 포인트에 잔액 컬럼 하나를 두고 UPDATE 하는 방식은 절대 피하세요.

```
❌  user.points = user.points + 10        ← 동시성 사고, 감사 불가, 분쟁 시 증명 불가
✅  INSERT INTO point_ledger (userId, delta:+10, reason, refId, ...)
    잔액 = SUM(delta)  (또는 스냅샷 캐시)
```

포인트가 사내 복지몰 등 **현금성 가치**를 가지면 이것은 회계 장부입니다.
적립·차감·취소가 전부 append-only로 남아야 분쟁과 감사에 대응할 수 있습니다.
이 프로젝트는 이미 감사로그 문화가 있으니 같은 원칙을 적용하면 됩니다.

### 6-2. 사전 고지와 회차별 보상 플래그

**보상 규칙은 응답을 받기 전에 응답자에게 명시되어야 합니다.** 신뢰의 문제이자 분쟁 예방의 문제입니다.

#### 보상 정책은 회차(Campaign) 단위로 붙입니다

양식 단위가 아니라 **회차 단위**여야 합니다. 그래야 지적하신
*"보상이 되었다가 중간에 빠질 수도 있고, 다시 보상이 이루어질 수도 있는"* 운영이 표현됩니다.

```
f-101 "분기 만족도 조사"  (양식 — 한 번만 제작)
  ├── 2026 Q1 회차   보상 ON   10P      ← 초기 참여 유도
  ├── 2026 Q2 회차   보상 OFF   —       ← 예산 사정으로 중단
  ├── 2026 Q3 회차   보상 OFF   —
  └── 2026 Q4 회차   보상 ON   15P      ← 응답률 하락으로 재개
```

회차마다 `rewardEnabled` 플래그 + 지급액 + 지급조건을 둡니다.

#### 🔴 회차가 시작되면 보상 규칙을 잠급니다(freeze)

응답을 받는 도중에 `10P → 2P`로 바꾸면 신뢰가 무너지고 분쟁이 생깁니다.

- 회차 **공개 시점에 정책 고정**, 이후 변경 불가
- 바꾸려면 **다음 회차부터** 적용
- 이는 이미 있는 `lifecycle(DRAFT/PUBLISHED)` + `schemaVersion` 패턴과 동일한 사고방식입니다 —
  기존 구조와 일관되게 갑니다

#### 응답 시점 정책을 스냅샷으로 남깁니다

원장 엔트리에 **"그때 약속한 규칙"** 을 함께 기록하세요.

```
적립 근거 = { 회차, 정책버전, 약속액, 조건 }   ← 제출 시점에 복사해 저장
```

나중에 정책이 바뀌어도 *"응답할 때 10P라고 했으니 10P를 준다"* 를 증명할 수 있습니다.
이게 없으면 분쟁 시 대응이 불가능합니다.

#### 응답 화면 고지 (제작자가 작성)

양식 제작자가 회차를 만들 때 아래를 입력하고, 응답 화면 상단에 그대로 노출합니다.

> 💰 **이 설문에 응답하시면 10P가 지급됩니다**
> · 기한(3/31) 내 응답 시 +5P
> · 성실하게 작성한 응답에 한해 지급됩니다
> · 지급 시점: 회차 마감 후 검토를 거쳐 지급

마지막 두 줄이 중요합니다. **"조건부"임을 미리 알려야** 나중에 미지급이 생겨도
예측 가능한 결과가 되고, *"준다더니 안 줬다"* 는 불만이 되지 않습니다.

### 6-3. 무엇에 보상할 것인가

| 행동 | 대상 | 비고 |
|---|---|---|
| 응답 제출 | Member | 기본. **회차당 1회만** |
| 기한 내 응답 | Member | 조기 응답 가산 — 독촉 비용 절감 |
| 연속 참여(streak) | Member | 주기 수집 이탈 방지 |
| 성실 응답 | Member | 품질 점수 기준 통과 시 (§6 연계) |
| **양식이 많이 활용됨** | Author | ⭐ 좋은 양식을 만들 동기. 이게 빠지면 제작자는 순수 비용만 부담 |
| 템플릿이 재사용됨 | Author | 부서 간 양식 중복 제작 낭비를 줄임 |

### 6-4. 공정성 — 어뷰징 방어

포인트가 걸리는 순간 반드시 악용 시도가 생깁니다. 최소한 아래는 필요합니다.

| 위협 | 방어 |
|---|---|
| 같은 회차 반복 제출로 중복 수령 | `(respondent, campaign)` 유니크 — 재제출은 수정으로 처리, 적립은 1회 |
| 무의미한 응답 양산 | 품질 점수 기준 미달 시 미지급(§6) |
| 제작자가 자기 양식에 셀프 응답 | 소유자·공동작업자 적립 제외 |
| 유령 양식 만들어 포인트 펌핑 | 신규 양식은 **최소 응답자 수 도달 후** 제작자 보상 발생 |
| 포인트 인플레이션 | 일/주 단위 상한, 정기 정산 시 슈퍼관리자 승인 |
| 링크 유출로 외부인 응답 | 개인화 토큰 1회성·만료 처리 |

**룰은 하드코딩하지 말고 정책 테이블로 두세요.** 운영하면서 반드시 조정하게 됩니다.
(현재 `SystemConfig`가 있으니 그 연장선에서 `RewardPolicy`로 두면 됩니다.)

## 7. 정산 — 지급/미지급 분리와 가시성

*"지급된 포인트와 아직 받지 못한 부분이 분리되어 통계·조회되고, 양식지 제작자에게 공지"* 에 대한 설계입니다.

### 7-1. 원장 엔트리에 상태를 둡니다

적립은 응답 즉시 **확정되지 않습니다.** 품질 검증과 정산 승인을 거칩니다.

| 상태 | 의미 | 다음 단계 |
|---|---|---|
| `PENDING` | 적립 예정 — 품질검증/정산 대기 | → APPROVED 또는 REJECTED |
| `APPROVED` | 지급 확정 (아직 잔액 미반영) | → PAID |
| `PAID` | **지급 완료** — 잔액 반영 | (종료) |
| `REJECTED` | **미지급** — 사유 필수 | 이의제기 시 재심 |
| `CANCELED` | 지급 후 회수 (어뷰징 사후 적발 등) | 반드시 상계 엔트리로 |

> ⚠️ append-only 원칙과의 관계: **금액(delta)은 절대 수정하지 마세요.**
> 회수가 필요하면 기존 엔트리를 고치지 말고 **반대 부호의 새 엔트리**를 추가합니다.
> 상태 전이는 감사로그와 함께 기록합니다.

### 7-2. 미지급이 생기는 이유 — 이게 공지의 핵심 내용

| 사유 | 설명 | 조치 주체 |
|---|---|---|
| 품질 기준 미달 | §8 품질 점수 미달 | 제작자 확인 → 필요 시 재심 |
| **예산 소진** | 양식/부서 포인트 예산 초과 | 제작자·관리자 (예산 증액 or 다음 회차) |
| 정산 승인 대기 | 관리자 검토 전 | 관리자 |
| 어뷰징 의심 보류 | 이상 패턴 감지 | 관리자 조사 |
| 중복 수령 | 같은 회차 재제출 | 자동 (정상 동작) |

> 💡 **예산(Budget) 개념이 필요합니다.** 명시하지 않으셨지만, 미지급의 가장 흔한 원인이 되고
> 슈퍼관리자가 반드시 통제해야 하는 지점입니다. 양식별·부서별·기간별 예산 상한을 두고,
> 소진율을 실시간으로 보여주세요. 예산 없이 열면 포인트 인플레이션을 막을 방법이 없습니다.

### 7-3. 슈퍼관리자 정산 화면 (신규)

```
━━ 정산 현황 (2026 Q1) ━━━━━━━━━━━━━━━━━━━━━━━━
  지급 완료   1,240건   12,400P   ████████░░  78%
  승인 대기     210건    2,100P   ██░░░░░░░░  13%
  미지급        145건    1,450P   █░░░░░░░░░   9%
     └ 품질 미달 88 / 예산 소진 41 / 어뷰징 보류 16

━━ 양식별 ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
  양식        지급    미지급   예산소진율   담당자
  f-101       420P     80P      84%       마케팅팀
  f-103       310P    220P     100% ⚠️    총무팀
```

- 사유별 분류, 양식·부서·기간별 집계, 예산 대비 소진율
- 일괄 승인 / 보류 / 재심
- 정산 확정 시 스냅샷 보관 (사후 변경 불가)

### 7-4. 제작자 공지

미지급이 발생하면 해당 양식 제작자에게 알립니다. 기존 `AdminNotification`을 확장하면 됩니다.

> 🔔 **[f-103 워크샵 신청] 회차 마감 정산 결과**
> 지급 1,240P (98건) / **미지급 220P (12건)**
> · 품질 기준 미달 8건 — 응답 검토가 필요합니다
> · **예산 소진 4건** — 예산 증액을 신청하거나 다음 회차로 이월하세요
> [정산 상세 보기] [이의 신청]

제작자가 **미지급을 인지하고 조치할 수 있어야** 합니다. 모르면 응답자 불만이 제작자를 거치지 않고
플랫폼 관리자에게 직접 갑니다.

### 7-5. 🟡 응답자에게는 어떻게 보일 것인가

여기에 긴장 관계가 있습니다. §8에서 *"품질 점수를 응답자에게 감점으로 보여주지 말라"* 고
했지만, 미지급을 아무 설명 없이 두면 *"준다더니 안 줬다"* 가 되어 신뢰가 더 크게 무너집니다.

**절충안:**

1. **사전 고지에 조건을 명시**(§6-2) — 그러면 미지급도 예측 가능한 결과가 됩니다
2. 마이페이지에 상태 표시: `검토 중` / `지급 완료` / `미지급`
3. 미지급 사유는 **범주 수준으로만** 안내 (점수는 노출하지 않음)
   - ✅ *"응답 검토 기준을 충족하지 못했습니다"*
   - ❌ *"품질점수 32점 / 기준 60점"*
4. **이의제기 창구는 반드시 두세요.** 오탐이 있을 수밖에 없고, 창구가 없으면
   불만이 조직 내 비공식 경로로 번집니다

## 8. 데이터 품질

*"데이터 품질 제고"* 는 두 층으로 나뉩니다.

| 층 | 대상 | 질문 |
|---|---|---|
| **값의 품질** (§8-1~8-5) | 데이터 자체 | 이 값이 올바른가? |
| **응답 태도 품질** (§8-6) | 응답 행태 | 성실하게 작성했는가? |

지금 시스템에는 두 번째는커녕 첫 번째도 `required` + `regexPattern`이 전부입니다.

### 8-1. 🔴 의미 타입(Semantic Type) — 품질 진단의 전제

**지금 구조의 근본 한계입니다.** 현재 `FormField.type`은 *"어떻게 입력받는가"*(UI)만 표현합니다.

```ts
{ id: 'f101-5', type: 'number', label: '계약금액' }
{ id: 'f101-6', type: 'number', label: '수량' }
{ id: 'f101-7', type: 'number', label: '달성률' }
{ id: 'f101-8', type: 'number', label: '사번' }
//              ↑ 전부 'number' — 시스템은 이 넷을 구분하지 못합니다
```

그런데 이 넷은 품질 규칙이 전혀 다릅니다. 금액은 음수·자릿수·통화를 봐야 하고, 백분율은
0~100 범위와 합계 100을, 사번은 형식과 유일성을 봐야 합니다.
**의미를 모르면 무엇을 검사해야 할지 알 수 없습니다.**

> 💡 **UI 타입과 의미 타입을 별개의 축으로 분리하세요.**
> `type`(어떻게 입력받나)은 그대로 두고, `semanticType`(그 값이 무엇인가)을 추가합니다.
> 데이터 카탈로그·DQ 도구들이 쓰는 표준 접근입니다.

```ts
{ id: 'f101-5', type: 'number', semanticType: 'AMOUNT',
  semantic: { currency: 'KRW', allowNegative: false, scale: 0 } }
```

#### 의미 타입 목록

| 계열 | 타입 | 부가 속성 | 용도 |
|---|---|---|---|
| **키** | `PRIMARY_KEY` | — | 양식 내 유일 식별자 |
| | `FOREIGN_KEY` | 참조 대상 | 다른 양식/마스터 참조 |
| | `IDENTIFIER` | 형식, 유일성 | 사번, 사업자번호, 관리번호 |
| **수치** | `AMOUNT` | 통화, 소수자리, 음수허용 | 금액 |
| | `QUANTITY` | 단위, 정수여부 | 수량 |
| | `PERCENTAGE` | 합계제약 그룹 | 백분율 |
| | `RATIO` / `MEASURE` | 단위 | 비율, 측정값 |
| **시간** | `DATE_EVENT` | 과거/미래 제한 | 사건 발생일 |
| | `DATE_RANGE_START/END` | 짝 필드 | 기간 (자동 대소 검증) |
| | `DATE_BIRTH` | 나이 범위 | 생년월일 |
| | `DATE_EXPIRY` | 경고 시점 | 만료일 |
| **분류** | `CODE` | 코드체계 | 부서코드, 분류코드 |
| | `CATEGORY` | 허용값 | 분류 |
| | `BOOLEAN` | 참/거짓 표기 | 논리값 (Y/N, 예/아니오) |
| **개인정보** | `PII_NAME` `PII_PHONE` `PII_EMAIL` `PII_RRN` `PII_ADDRESS` | 마스킹 규칙 | ⭐ 아래 참조 |
| **자유** | `FREE_TEXT` | — | 의견, 서술 |

#### ⭐ 개인정보 계열은 특별히 중요합니다

`PII_*` 의미 타입을 붙여두면 **개인정보 관리가 자동화**됩니다. 지금 `privacyMasking`
불리언 하나로 처리하는 것을 여기로 승격시키면 훨씬 체계적입니다.

- 화면·추출 시 **자동 마스킹** (`홍길동` → `홍*동`, 뒷자리 가림)
- 개인정보 **수집 항목 목록 자동 생성** (영향평가·동의서 작성에 그대로 사용)
- 보유기간 경과 시 **파기 대상 자동 식별**
- 주민등록번호는 **체크섬 검증** + 저장 자체를 막거나 암호화 강제
- §10의 정보주체 권리(열람·정정·삭제) 대응 시 대상 필드 자동 추출

### 8-2. 의미 타입이 자동으로 켜는 검증

제작자가 규칙을 일일이 짜지 않아도, 타입만 고르면 아래가 자동 적용됩니다.

| 의미 타입 | 자동 검증 |
|---|---|
| `AMOUNT` | 음수 여부, 소수자리, **이상치 탐지**(사분위/표준편차), 자릿수 급변 감지 |
| `QUANTITY` | 정수 여부, 음수 불가, 상한 이상치 |
| `PERCENTAGE` | 0~100 범위, **그룹 합계 = 100** 검사 |
| `PRIMARY_KEY` | **유일성**, 결측 불가 |
| `FOREIGN_KEY` | **참조 무결성** (대상에 존재하는 값인가) |
| `IDENTIFIER` | 형식 일치, 유일성(옵션), 마스터 대조 |
| `DATE_RANGE_START/END` | **시작 ≤ 종료** 자동 검사 |
| `DATE_BIRTH` | 미래 불가, 비현실적 나이 차단 |
| `DATE_EXPIRY` | 이미 지난 날짜 경고 |
| `CODE` | **마스터 코드 대조** (없는 코드 차단) |
| `PII_RRN` | 체크섬, 자동 마스킹 |

> 이것이 *"품질 진단을 용이하게"* 의 실체입니다. 지금처럼 정규식 하나로 다 처리하려면
> 제작자가 정규식을 알아야 하고, 이상치·유일성·참조무결성은 아예 표현할 수 없습니다.

### 8-3. 필드 간 규칙 (논리 관계)

*"논리 관계"* 를 필드 간 제약으로도 이해했습니다. 단일 필드 검증으로는 표현 불가한 것들입니다.

| 규칙 | 예시 |
|---|---|
| **조건부 필수** | `기타`를 선택하면 `기타 내용` 필수 |
| **대소 관계** | 시작일 ≤ 종료일, 최소값 ≤ 최대값 |
| **합계 제약** | 비중 필드들의 합 = 100% |
| **상호 배타** | A와 B 중 하나만 입력 가능 |
| **의존 표시** | `해당없음` 체크 시 하위 문항 비활성 |

빌더 우측 상세패널에 **규칙 편집기**를 두고, 코드가 아니라 드롭다운 조합으로
(`[필드A] 가 [값] 이면 → [필드B] 를 [필수]`) 만들 수 있게 하세요.

### 8-4. DQ 6대 차원 — 표준 지표

일반적인 데이터 품질 관리의 표준 차원입니다. 위 의미 타입이 있으면 대부분 자동 산출됩니다.

| 차원 | 측정 | 산출 근거 |
|---|---|---|
| **완전성** Completeness | 필수·권장 항목 결측률 | `required` + 의미 타입 |
| **유효성** Validity | 형식·도메인·범위 위반율 | 의미 타입 자동 검증(§8-2) |
| **정확성** Accuracy | 마스터 대조 불일치율 | `CODE`, `FOREIGN_KEY` |
| **일관성** Consistency | 필드 간 규칙 위반율 | 필드 간 규칙(§8-3) |
| **유일성** Uniqueness | 중복률 | `PRIMARY_KEY`, `IDENTIFIER` |
| **적시성** Timeliness | 갱신 경과일 / 기한 준수율 | 회차(§4) + `DATE_EXPIRY` |

**적시성은 회차(Campaign) 개념이 있어야 측정됩니다** — *"3분기째 갱신 안 된 항목"* 같은 진단이
가능해집니다. 여기서도 §2 전환 2가 전제가 됩니다.

### 8-5. 품질 대시보드 (제작자·관리자)

```
━━ f-101 데이터 품질  (2026 Q1 회차) ━━━━━━━━━━━━━━
  종합         82점  ▼6 (전분기 대비)
  완전성 94 │ 유효성 88 │ 정확성 71 ▼ │ 일관성 90 │ 유일성 100 │ 적시성 68 ▼

━━ 문제 항목 ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
  ⚠ 계약금액(AMOUNT)   이상치 4건    최대 9,900,000,000원 — 자릿수 오입력 의심
  ⚠ 부서코드(CODE)     미등록 12건   'MKT-2' — 마스터에 없는 코드
  ⚠ 달성률(PERCENTAGE) 합계 오류 7건  구성비 합이 100이 아님
  ⚠ 갱신 경과          38건          6개월 이상 미갱신 → 갱신 요청 발송
                                      [해당 응답자에게 정정 요청]
```

- 이슈에서 **개별 레코드로 드릴다운** → 해당 응답자에게 **정정 요청 발송**
- 회차 간 품질 추이 (품질이 나빠지면 양식 설계를 의심)
- 여기서 발송한 정정 요청이 §9 마이페이지의 "조치 필요" 항목으로 연결됩니다

> 💡 품질 이슈를 **발견만 하고 고칠 경로가 없으면** 대시보드는 장식입니다.
> 정정 요청 → 응답자 수정 → 품질 점수 회복까지가 한 사이클이 되어야 합니다.

### 8-6. 응답 태도 품질

값 자체는 형식에 맞아도 성의 없는 응답일 수 있습니다.

| 신호 | 판정 |
|---|---|
| 응답 소요시간 | 문항 수 대비 비정상적으로 짧으면 무성의 의심 |
| 직진 응답(straight-lining) | 모든 척도 문항에 동일값 |
| 결측률 | 선택 문항 미응답 비율 |
| 자유응답 품질 | 길이, 무의미 문자열(`ㅇㅇ`, `.`) |
| 이전 회차와 100% 동일 | 갱신 요청인데 실제 확인 없이 통과시킨 정황 |

이 점수는 **응답자에게 감점으로 보여주지 마세요.** 위축되어 응답률이 떨어집니다.
내부 지표로만 쓰고, 기준 미달 시 조용히 포인트 미지급 + 제작자에게만 알립니다(§7-5).

### 8-7. 양식 자체의 품질 (제작자 피드백)

제작자가 자기 양식의 문제를 알아야 개선합니다. 지금 완전히 없는 영역입니다.

- 문항별 이탈률 → *"7번 문항에서 40%가 포기합니다"*
- 문항별 무응답률 → 질문이 모호하거나 불필요
- 평균 소요시간 → 너무 길면 응답률 하락 원인
- 검증 실패율 → 규칙이 과하게 엄격한지

## 9. 응답자 마이페이지 — 내 데이터 현황판

*"본인이 입력한 데이터가 무엇 무엇이었으며, 이들에 대한 대시보드 현황판"* 에 대한 설계입니다.

지금은 응답자가 제출하면 그걸로 끝이고, 자기가 뭘 냈는지 다시 볼 방법이 없습니다.
이 화면은 단순 조회를 넘어 **응답 동기·데이터 품질·법적 의무** 세 가지를 동시에 해결합니다.

### 9-1. 화면 구성

```
━━ 내 데이터 현황 ━━━━━━━━━━━━━━━━━━━━━━━━━━━

  응답한 양식  12건      보유 포인트  1,240P
  갱신 대기     2건 ⚠     검토 중        150P

━━ ⚠ 조치가 필요합니다 ━━━━━━━━━━━━━━━━━━━━━
  [보유장비 현황]     Q1 갱신 요청 — 3/31까지     +10P  [갱신하기]
  [자격증 정보]       만료 임박(4/15)                    [수정하기]
  [출장 신청서]       금액 확인 요청 — 자릿수 확인       [정정하기]
                                        ↑ §8-5 품질 이슈에서 발송된 것

━━ 내가 응답한 양식 ━━━━━━━━━━━━━━━━━━━━━━━
  양식              최근 응답     회차    상태      포인트
  보유장비 현황      2026-01-15   Q1 외 3   최신     +10P 지급
  만족도 조사        2026-01-10   Q1       🔒익명    +10P 지급
  워크샵 신청        2025-12-20   —        완료      검토 중
  고객사 방문기록    2025-11-30   —        완료      미지급 ⓘ

━━ 포인트 내역 ━━━━━━━━━━━━━━━━━━━━━━━━━━
  (적립/지급/미지급 이력 — §7 원장 그대로)
```

### 9-2. 각 영역이 하는 일

| 영역 | 목적 |
|---|---|
| **조치 필요** | 갱신 요청·정정 요청을 한곳에. 여러 부서의 요청이 흩어지지 않음 |
| **응답 이력** | *"내가 뭘 냈더라"* 해결. 회차별 내 응답 변화도 확인 |
| **포인트 내역** | §7 상태(지급/검토중/미지급) 그대로 노출 + 미지급 사유 |
| **익명 표시** | 🔒 표시된 것은 **응답 사실만 기록**되고 내용은 조회 불가임을 명시 |

> ⚠️ 익명 문항이 포함된 양식은 마이페이지에서도 **내용을 보여주면 안 됩니다.**
> 응답자 본인에게 보여주는 것조차 "저장되어 있다"는 뜻이 되어 익명성 주장이 약해집니다.
> *"응답하셨습니다(내용은 익명 처리되어 조회할 수 없습니다)"* 로만 표시하세요.

### 9-3. 결과 피드백 — 응답 동기의 핵심

§10에서 언급한 *"내 응답이 어디에 쓰였나"* 를 구현하는 자리입니다.

> 📊 **[2025 만족도 조사]** 참여해주신 조사 결과가 반영되었습니다
> · 응답자 342명 · 주요 개선사항 3건 반영 [결과 보기]

제작자가 회차 마감 후 **결과 요약을 한 줄이라도 남기게** 하세요.
비용이 거의 들지 않으면서 다음 회차 응답률에 가장 크게 작용합니다.

### 9-4. 정보주체 권리 (법적 요구사항)

신원이 붙는 순간 필요해집니다(§10). 마이페이지가 그 창구가 됩니다.

- **열람** — 내 데이터 전체 다운로드
- **정정** — 잘못된 값 수정 요청 → 품질 향상에 직접 기여
- **삭제·처리정지** — 요청 접수 및 처리 경과 확인
- 각 양식의 **수집 목적·보유기간** 표시

> 💡 정정 기능은 법적 의무이면서 동시에 **가장 값싼 품질 개선 수단**입니다.
> 데이터 주인이 직접 고치는 것보다 정확한 방법은 없습니다.

## 10. 데이터 가치 향상

v1 API로 외부 BI 연결은 이미 가능합니다. 다만 초기 의도가 *"쉬운 형태"* 였으므로,
**내장 분석**이 어느 정도는 있어야 합니다.

- **회차 비교**: 같은 문항의 회차별 분포 변화
- **필드 시계열**: 수치 필드의 추세선
- **코호트**: 부서별/직급별 추이 (신원이 생겨야 가능 — §2 전환 1의 부수 효과)
- **자동 리포트**: 회차 마감 시 요약 리포트 자동 생성 → *"보고서 작성"* 업무 직접 절감
- **템플릿 공유/포크**: 부서마다 비슷한 양식을 또 만드는 낭비 제거

## 11. 먼저 확인하셔야 할 리스크

기술 설계보다 이쪽이 프로젝트를 좌초시킬 위험이 큽니다.

### 🔴 개인정보 — 신원을 붙이는 순간 성격이 바뀝니다

지금은 익명 데이터라 상대적으로 가볍지만, **응답자 신원이 붙으면 개인정보처리 영역**입니다.
`DatabaseRegistration`(저작권법)은 이미 대응되어 있으나, 그것과 개인정보보호법은 별개입니다.

- 수집 목적·항목·보유기간 고지 및 동의 이력 보관
- 정보주체 권리: 열람 / 정정 / 삭제 / 처리정지 요구 대응 절차
- 보유기간 경과 데이터 자동 파기
- 부서 담당자가 자기 부서 양식의 응답자 신원을 어디까지 볼 수 있는지 **명확한 선**
  (현재 소유자/공유승인 모델이 있으니 확장 가능)

특히 **인사평가·고충·건강 관련 양식**은 민감정보로 별도 취급이 필요합니다.

### 🟡 포인트의 세무/노무 이슈

사내 포인트가 현금성 가치를 가지면 근로소득 과세 대상이 될 수 있습니다.
**설계 전에 인사/재무/법무 확인**을 받으세요. 나중에 뒤집히면 원장 전체를 손봐야 합니다.

### 🟡 포인트가 만능은 아닙니다

솔직히 말씀드리면, 포인트만으로 선순환이 나지는 않습니다. 실무에서 더 크게 작용하는 것들:

1. **응답 부담 감소** (prefill) — 포인트보다 효과가 클 수 있습니다
2. **결과 피드백** — *"당신의 응답이 이렇게 반영되었습니다"*. 응답이 어디에 쓰였는지
   모르면 다음 요청에 응하지 않습니다. 이건 **가장 저렴하면서 강력한 동기**입니다
3. **요청 총량 관리** — 여러 부서가 각자 설문을 남발하면 피로도로 전체 응답률이 무너집니다.
   플랫폼 관리자가 발송 총량을 조율하는 기능이 필요합니다

포인트는 이 셋을 갖춘 뒤의 보조 장치로 보시는 편이 안전합니다.

## 12. 단계별 로드맵

각 단계는 그 자체로 가치가 있고, 다음 단계의 전제가 됩니다.

### 1단계 — 신원 기반 (전제조건)
- `User` 모델 + 다중 역할 (기존 `AdminUser` 흡수)
- 개인화 링크 토큰 발급/검증
- `Submission`에 respondent 연결 (익명 허용 유지)
- **여기까지 없으면 이후 전부 불가능합니다**

### 2단계 — 문항 단위 익명성
- 필드 `anonymous` 플래그, 제출 시 분리 저장
- 재식별 방지(독립 ID, 타임스탬프 절삭, 배치 셔플)
- k-익명성 임계값, 제작자/관리자 접근 차단
- 응답 화면 익명 배지
- ➡️ **1단계와 짝입니다.** 신원을 붙이면서 익명 보호를 같이 열지 않으면,
  기존 익명 응답자들의 신뢰를 먼저 잃습니다

### 3단계 — 반복 수집
- `Campaign`(회차) 도입, 기존 submission을 기본 회차에 귀속
- 주기 자동 생성 + 대상자 발송
- Prefill (필드별 정책)
- ➡️ *"양식 재생성 반복업무"* 해소 — 체감 효과가 가장 큰 단계

### 4단계 — 저장 효율 & 추세
- `current_records` / `record_history` 분리
- 회차 비교·시계열 분석 화면
- ES ILM 적용

### 5단계 — 데이터 품질
- **의미 타입(semanticType) 도입** — 빌더 상세패널에서 선택, 기존 필드는 추론 후 확인
- 타입별 자동 검증, 필드 간 규칙 편집기
- DQ 6차원 산출 + 품질 대시보드 + **정정 요청 발송**
- 응답 태도 품질, 양식 품질 피드백
- ➡️ 의미 타입은 **빠를수록 좋습니다.** 데이터가 쌓인 뒤 소급 적용하면
  이미 들어온 값의 타입 추론·정합성 확인 비용이 커집니다
- ➡️ 다음 단계 보상의 공정성 근거가 됨.
  **품질보다 보상을 먼저 열면 어뷰징을 막을 수 없습니다**

### 6단계 — 응답자 마이페이지
- 내 응답 이력, 조치 필요 목록(갱신·정정 요청)
- 결과 피드백, 정보주체 권리(열람·정정·삭제)
- ➡️ 보상보다 **먼저** 여는 것을 권합니다. 포인트 없이도 가치가 있고,
  정정 기능은 품질을 직접 끌어올립니다

### 7단계 — 보상 (적립)
- append-only 원장, 회차별 보상 플래그, 정책 freeze + 스냅샷
- 응답 화면 사전 고지, 어뷰징 방어
- 마이페이지에 포인트 영역 추가

### 8단계 — 정산 (지급)
- 상태 전이(PENDING→APPROVED→PAID / REJECTED)
- 예산 관리, 슈퍼관리자 정산 화면(지급·미지급 분리 통계)
- 제작자 공지, 이의제기 창구
- ➡️ 7·8단계는 붙어 있지만 **적립과 지급을 분리해서 여는 것을 권합니다.**
  적립만 먼저 열어 데이터를 쌓고 룰을 검증한 뒤, 실제 지급을 켜면 초기 오작동의
  피해가 "포인트가 잘못 나감"이 아니라 "숫자만 틀림"에 그칩니다

### 9단계 — 확산
- 템플릿 공유/포크, 자동 리포트, 발송 총량 관리

## 13. 요약

| 질문 | 답 |
|---|---|
| 왜 반복 입력이 힘든가 | 양식과 수집회차가 붙어 있어서. **Campaign 분리**로 해결 |
| 왜 최신화·추세가 안 되나 | 응답자 신원이 없어서. **개인화 링크**로 로그인 없이 해결 |
| 특정 문항만 익명 보장 | **문항 단위 플래그 + 물리적 분리 저장 + k-익명성.** 조인키 공유 금지가 핵심 |
| 저장공간 효율화 | **Current + History 분리**, 변경분만 저장 |
| 보상 사전 명시 | **회차 단위 정책 + 공개 시 freeze + 응답시점 스냅샷.** 응답 화면에 조건까지 고지 |
| 보상 켜고 끄기 | 회차별 `rewardEnabled` 플래그 — ON/OFF/재개가 자연스럽게 표현됨 |
| 지급/미지급 분리 | **원장 상태 전이**(PENDING→APPROVED→PAID/REJECTED) + 예산 + 사유별 통계 |
| 제작자 공지 | 회차 마감 정산 시 미지급 건수·사유 알림 + 조치 경로 |
| 품질 진단을 쉽게 | **의미 타입(금액/수량/백분율/PK/코드/PII…) 정의** → 타입별 검증이 자동으로 켜짐 |
| 일반 DQ 기능 | **DQ 6차원**(완전성·유효성·정확성·일관성·유일성·적시성) + 품질 대시보드 + 정정 요청 |
| 논리 관계 | 의미 타입 `BOOLEAN` + **필드 간 규칙**(조건부 필수, 대소, 합계, 배타) |
| 응답 태도 품질 | 소요시간·직진응답·무의미 문자열 (내부 지표로만) |
| 사용자 현황판 | **마이페이지** — 내 응답 이력, 조치 필요, 포인트 상태, 결과 피드백, 정보주체 권리 |
| 역할 체계 | `User` 1개 + 다중 역할. Guest/Member/Author/PlatformAdmin |

**순서가 중요합니다.** 신원+익명성 → 회차 → 품질 → 적립 → 지급 순으로 가야 합니다.

- 보상을 품질보다 먼저 열면, 공정성을 담보할 수단이 없는 상태에서 어뷰징이 먼저 학습됩니다
- 신원을 익명성 보호보다 먼저 열면, 기존 익명 응답자의 신뢰를 먼저 잃습니다
- 적립과 지급을 동시에 열면, 초기 룰 오류가 곧바로 실제 포인트 사고가 됩니다
