# 3단계 — 회차(Campaign) 기반 반복 수집 스키마 명세

> [플랫폼 재설계 제안](./플랫폼-재설계-제안.md) §2 전환 2 / §4의 구현 명세.
> 기획의도에서 지적하신 *"또 다시 양식지를 생성해야 하는 반복 업무"* 를 실제로 없애는 단계이며,
> **체감 효과가 가장 큰 단계**입니다.

---

## 1. 범위

| 포함 | 제외 (이후 단계) |
|---|---|
| `Campaign`(회차) 도입, 기존 제출의 기본 회차 귀속 | Current+History 분리 — 4단계 |
| 주기 자동 생성 + 대상자 발송 | 품질 점수 — 5단계 |
| Prefill (필드별 정책) | 보상 지급 — 7·8단계 |
| 회차당 1인 1응답 보장 | 회차 간 추세 분석 화면 — 4단계 |

### 이 단계가 푸는 문제

지금은 `FormRegistry`에 `startsAt/expiresAt`과 `submissionCount`가 직접 붙어 있어
**한 양식 = 한 번의 수집**입니다. 분기마다 걷으려면 양식을 새로 만들어야 하고, 그 순간
과거 회차와의 연결이 끊겨 추세도 최신화도 불가능해집니다.

```
지금:  f-101(Q1)   f-107(Q2)   f-115(Q3)    ← 서로 남남인 양식 3개
이후:  f-101 ── Q1 회차 ── Q2 회차 ── Q3 회차  ← 양식 하나, 회차 3개
```

---

## 2. 모델 개요

```
FormRegistry (양식 정의 — 재사용)
   │
   ├── CampaignSchedule       주기 규칙 (분기/월/연) — 회차를 자동 생성
   │
   └── Campaign               회차. 기간·대상자·스키마버전을 고정
         ├── CampaignTarget          대상자 + 발송/열람 추적 (RespondentToken 연결)
         └── CampaignParticipation   ⭐ 참여 사실 (Postgres) — 1인 1응답 보장의 근거
                    │
                    └─→ Elasticsearch: SubmissionDocument + campaignId
```

> ⭐ **`CampaignParticipation`이 이 설계의 핵심입니다.** 제출 *내용*은 Elasticsearch에
> 있지만, ES에는 유니크 제약이 없어 "1인 1응답"을 강제할 수 없습니다.
> **참여 사실을 Postgres에 별도로 기록**해야 중복 응답 차단·보상 지급 기준·응답률 집계가
> 모두 가능해집니다. 익명 양식(2단계)에서 "내용은 분리하되 참여는 기록"하는 자리이기도 합니다.

## 3. `Campaign` — 수집 회차

```prisma
enum CampaignStatus {
  SCHEDULED // 생성됐으나 아직 시작 전
  OPEN      // 응답 수집 중
  CLOSED    // 마감 — 응답 불가, 집계·정산 대상
}

/// 수집 회차. 같은 양식으로 반복 수집할 때 각 회차를 나타낸다.
/// 일회성 수집도 회차 1개로 표현되므로, 모든 제출은 반드시 어떤 회차엔가 속한다.
model Campaign {
  id     String       @id @default(cuid())
  formId String
  form   FormRegistry @relation(fields: [formId], references: [id], onDelete: Cascade)

  /// 사람이 알아볼 이름 — "2026 Q1 정기조사"
  name     String
  /// 회차 번호. 자동 생성 시 직전 회차 +1.
  sequence Int

  startsAt DateTime
  endsAt   DateTime?
  status   CampaignStatus @default(SCHEDULED)

  /// 이 회차가 사용하는 폼 스키마 버전. 회차 시작 시점에 고정한다 —
  /// 이후 양식이 수정되어도 이 회차 데이터의 해석 기준은 바뀌지 않아야 한다.
  schemaVersion Int

  /// 이 회차의 익명 응답 공개 임계값(2단계). null이면 양식/시스템 기본값.
  /// 회차별로 분리해야 "Q1 3건 + Q2 3건 = 6건"으로 임계값을 채우는 사고를 막는다.
  anonymityThreshold Int?

  /// 자동 생성된 회차인지 — 수동 생성분과 구분해 스케줄 변경 시 영향 범위를 판단한다.
  autoCreated Boolean @default(false)

  createdAt DateTime @default(now())
  updatedAt DateTime @updatedAt

  targets        CampaignTarget[]
  participations CampaignParticipation[]

  @@unique([formId, sequence])
  @@index([formId, status])
  @@index([status, endsAt])
  @@map("campaigns")
}
```

### 🔴 `schemaVersion`을 회차에 고정하는 이유

양식은 계속 수정됩니다. Q1 회차 데이터를 Q3 시점의 필드 구성으로 해석하면
없는 필드를 찾거나 뜻이 바뀐 값을 잘못 읽습니다.

```
Q1 회차 (schemaVersion 1)  →  "만족도" 5점 척도
Q3 회차 (schemaVersion 3)  →  "만족도" 7점 척도로 변경됨
```

회차별 버전이 없으면 이 둘을 그냥 이어붙여 추세선을 그리게 됩니다.
**회차 비교 화면(4단계)은 버전이 다르면 경고를 띄워야 합니다.**

## 4. `CampaignSchedule` — 주기 자동 생성

```prisma
enum RecurrenceFrequency {
  MONTHLY
  QUARTERLY
  SEMIANNUAL
  ANNUAL
}

/// 회차 자동 생성 규칙. 이것이 있으면 스케줄러가 다음 회차를 미리 만들고
/// 대상자에게 개인화 링크를 발송한다 — 제작자는 양식을 한 번만 만들면 된다.
model CampaignSchedule {
  id     String       @id @default(cuid())
  formId String       @unique
  form   FormRegistry @relation(fields: [formId], references: [id], onDelete: Cascade)

  enabled   Boolean             @default(true)
  frequency RecurrenceFrequency

  /// 회차 시작일(해당 주기 내 며칠째). 예: 분기 시작 후 1일.
  startDayOfPeriod Int @default(1)
  /// 회차가 열려 있는 기간(일).
  durationDays     Int @default(14)
  /// 마감 며칠 전에 미응답자에게 리마인드할지. 빈 배열이면 발송 안 함.
  reminderDaysBefore Int[] @default([7, 1])

  /// 다음 회차를 만들 시각. 스케줄러가 이 값을 보고 동작한다.
  nextRunAt   DateTime?
  lastRunAt   DateTime?
  /// 회차 이름 템플릿. {year} {quarter} {month} 치환.
  nameTemplate String  @default("{year} {quarter} 정기조사")

  createdAt DateTime @default(now())
  updatedAt DateTime @updatedAt

  @@map("campaign_schedules")
}
```

> 💡 **회차는 시작 전에 미리 만들어 두세요.** 시작 시각에 만들면 스케줄러가 잠깐 죽어도
> 회차가 통째로 누락됩니다. `SCHEDULED` 상태로 앞서 생성해 두고 시작 시각에
> `OPEN`으로 전환하는 편이 안전합니다.

## 5. `CampaignTarget` — 대상자와 발송 추적

```prisma
enum TargetingMode {
  ALL_MEMBERS        // 전체 임직원
  DEPARTMENTS        // 특정 부서
  EXPLICIT           // 명시적 사용자 목록
  PREVIOUS_RESPONDENTS // 직전 회차 응답자 (최신화 요청에 적합)
}

/// 이 회차에 응답을 요청받은 사람. 개인화 링크(1단계 RespondentToken)와 짝을 이룬다.
/// 발송·열람·응답 시점을 남겨 응답률 저하의 원인을 진단할 수 있게 한다.
model CampaignTarget {
  id         String   @id @default(cuid())
  campaignId String
  campaign   Campaign @relation(fields: [campaignId], references: [id], onDelete: Cascade)
  userId     String
  user       User     @relation(fields: [userId], references: [id], onDelete: Cascade)

  /// 발급된 개인화 링크. 재발송 시 교체된다.
  tokenId String? @unique

  invitedAt   DateTime?
  deliveredAt DateTime?
  openedAt    DateTime?
  respondedAt DateTime?
  remindedAt  DateTime?
  reminderCount Int     @default(0)

  @@unique([campaignId, userId])
  @@index([campaignId, respondedAt])
  @@map("campaign_targets")
}
```

### 발송·열람 추적이 진단에 쓰이는 방식

```
대상 120명 · 발송 120 · 열람 78(65%) · 응답 41(34%)
   ├ 발송 대비 열람이 낮다  → 제목/발송 채널 문제
   └ 열람 대비 응답이 낮다  → 양식이 길거나 어렵다 (5단계 양식 품질과 연결)
```

이 구분이 없으면 응답률이 낮을 때 **무엇을 고쳐야 할지 알 수 없습니다.**

## 6. `CampaignParticipation` — 참여 사실 (핵심)

```prisma
/// 회차 참여 기록. 제출 "내용"은 Elasticsearch에 있고, 여기에는 "참여했다는 사실"만 둔다.
///
/// 이 테이블이 필요한 이유:
///   1. ES에는 유니크 제약이 없어 "회차당 1인 1응답"을 강제할 수 없다.
///   2. 보상 지급(7단계)의 기준이 되는 사실이 정형 저장소에 있어야 정산·감사가 가능하다.
///   3. 익명 문항만 있는 양식(2단계)에서도 참여 사실은 남아야 한다 —
///      내용은 익명 인덱스로 분리되지만 "누가 참여했는가"는 보상에 필요하다.
model CampaignParticipation {
  id         String   @id @default(cuid())
  campaignId String
  campaign   Campaign @relation(fields: [campaignId], references: [id], onDelete: Cascade)
  userId     String
  user       User     @relation(fields: [userId], references: [id], onDelete: Cascade)

  /// ES 식별 문서의 submissionId. 익명 전용 양식이면 내용이 비어 있을 수 있다.
  submissionId String
  submittedAt  DateTime @default(now())
  /// 수정 횟수. 최초 제출이 0.
  revision     Int      @default(0)
  lastEditedAt DateTime?

  /// 기한 내 응답 여부 — 조기 응답 보상(7단계)과 적시성 지표(품질)의 근거.
  onTime Boolean @default(true)

  @@unique([campaignId, userId])
  @@index([userId])
  @@map("campaign_participations")
}
```

> 🔴 **`@@unique([campaignId, userId])`가 중복 응답 방어의 전부입니다.**
> 1단계에서 `RespondentToken.singleUse`를 기본 `false`로 둔 이유가 여기 있습니다 —
> 토큰을 일회용으로 만들어 중복을 막는 대신, 이 제약으로 막고 토큰은 재진입을
> 허용하는 편이 사용자 경험과 데이터 정합성 모두에서 낫습니다.

재제출은 **거부가 아니라 수정**으로 처리합니다 (`revision` 증가).

## 7. Elasticsearch — `SubmissionDocument` 확장

```ts
export interface SubmissionDocument {
  // ... 기존 + 1단계(respondentId, identityLevel) ...

  /** 소속 회차. 3단계 이후 모든 제출은 반드시 값을 가진다. */
  campaignId?: string;
  /** 수정 횟수 — CampaignParticipation.revision과 일치시킨다. */
  revision?: number;
}
```

익명 문서(2단계)에도 동일하게 추가합니다.

```ts
export interface AnonymousSubmissionDocument {
  // ... 2단계 ...
  campaignId: string; // 회차별 임계값 판정에 필수
}
```

매핑: `campaignId: { type: 'keyword' }`, `revision: { type: 'integer' }`

## 8. Prefill — 반복 입력 해방

### 8-1. 필드별 정책

```ts
export type PrefillPolicy =
  | 'carry-over'         // 지난 값 그대로 (부서, 직급 등 잘 안 바뀌는 것)
  | 'carry-with-confirm' // 채우되 확인 체크 필수 (자격증 만료일 등)
  | 'clear';             // 매번 새로 (이번 분기 실적 등)

export interface FormField {
  // ... 기존 ...
  /** 반복 수집 시 이전 회차 값을 어떻게 처리할지. 기본 'clear'. */
  prefillPolicy?: PrefillPolicy;
}
```

**기본값은 `clear`여야 합니다.** 제작자가 의식적으로 켜지 않는 한 이전 값이
따라오면 안 됩니다 — 실적·의견처럼 매번 달라야 하는 항목이 조용히 복사되면
데이터가 오염됩니다.

### 8-2. 값 해석 순서

```
1. 직전 회차의 내 응답 있음 → prefillPolicy에 따라 채움
2. 없으면 → LDAP 동기화 값 (부서·직급·사번) — 읽기 전용
3. 없으면 → 빈 값
```

### 8-3. 🔴 Prefill이 품질을 해칠 수 있습니다

`carry-over`로 전부 채우고 "제출" 한 번이면 끝나게 만들면,
**확인 없이 통과한 값이 최신 데이터로 둔갑**합니다.
2단계에서 신뢰성 저하 신호로 꼽았던 *"이전 회차와 100% 동일"* 이 바로 이것입니다.

**대응:**
- 변경 없이 제출한 경우 `revision`은 올라가되 **품질 신호로 기록**
- 중요 항목은 `carry-with-confirm`으로 설정해 체크박스를 강제
- 화면에 *"지난 회차 값입니다 — 변경사항이 없는지 확인해 주세요"* 명시

### 8-4. 스키마 버전이 다를 때

직전 회차와 현재 회차의 `schemaVersion`이 다르면 필드가 사라졌거나 뜻이 바뀌었을 수 있습니다.

| 상황 | 처리 |
|---|---|
| 필드 id가 사라짐 | 무시 |
| 필드 id는 같으나 타입/선택지 변경 | **prefill하지 않음** — 값이 유효하지 않을 수 있음 |
| 선택지가 축소되어 지난 값이 없어짐 | prefill하지 않음 |

> 안전한 기본값은 **"확실할 때만 채운다"** 입니다. 애매하면 비워두세요.

### 8-5. 익명 문항은 prefill 불가

2단계 설계상 **응답자의 지난 익명 응답을 찾을 방법이 없습니다.**
이는 버그가 아니라 익명성의 필연적 대가이며, 양식 제작자에게 빌더에서 안내해야 합니다.

> `anonymous: true`인 필드에 `prefillPolicy`를 설정하면 저장 시 거부하거나 무시합니다.

## 9. 기존 `FormRegistry` 필드 정리

현재 `FormRegistry`가 직접 들고 있는 기간·카운터가 회차로 옮겨갑니다.

| 기존 필드 | 처리 |
|---|---|
| `startsAt` / `expiresAt` | **Campaign으로 이관.** 마이그레이션에서 기본 회차 생성에 사용 후 컬럼 제거(별도 릴리스) |
| `submissionCount` | 유지하되 **전 회차 누계**로 의미 변경. 회차별 건수는 `CampaignParticipation` 집계 |
| `status(OPEN/CLOSED)` | 유지 — 양식 전체의 on/off. 회차 상태와는 별개 |
| `lifecycle`, `schemaVersion` | 유지 — 회차가 시작될 때 `schemaVersion`을 회차에 복사 |

### 활성 판정 로직 변경

```ts
// 기존: 양식의 기간으로 판정
isFormActiveNow({ status, startsAt, expiresAt })

// 이후: 양식 status + 현재 열린 회차 존재 여부
isAcceptingResponses(form, campaign)
  = form.status === 'OPEN'
  && campaign?.status === 'OPEN'
  && now within [campaign.startsAt, campaign.endsAt]
```

`/q/{formId}`로 들어왔을 때 **어느 회차인지 결정**해야 합니다:
- 개인화 토큰에 `campaignId`가 있으면 그 회차
- 없으면 현재 `OPEN`인 회차 (여러 개면 가장 최근 시작분)
- 열린 회차가 없으면 거부

## 10. 2단계 익명성과의 상호작용

| 항목 | 처리 |
|---|---|
| 익명 버퍼 | **회차별로 분리** — `AnonymousResponseBuffer.campaignId` 추가 |
| k-임계값 | **회차 단위 판정** — Q1 3건 + Q2 3건을 6건으로 합산 금지 |
| 익명 문항 prefill | 불가 (§8-5) |
| 회차 간 개인 추세 | 익명 문항은 **원천적으로 불가** — 분석 화면에서 명시 |
| 참여 기록 | 익명 전용 양식도 `CampaignParticipation`은 생성 (보상 근거) |

## 11. 마이그레이션

기존 5개 양식과 제출 데이터가 회차 없이 존재합니다.

```
① 신규 테이블 생성 (campaigns, campaign_schedules, campaign_targets,
                    campaign_participations)
② 양식별 기본 회차 생성 — sequence=1, name="기본 수집",
   startsAt/endsAt는 기존 FormRegistry 값 사용(없으면 createdAt/null),
   schemaVersion은 현재 값, status는 form.status에서 유도
③ ES 기존 제출 문서에 campaignId 백필 (update_by_query)
④ 기존 제출에 대한 CampaignParticipation 생성
     ⚠️ 1단계 이전 제출은 respondentId가 없어 참여 기록을 만들 수 없다 →
        건너뛰고, 해당 회차를 "익명 수집 회차"로 표시
⑤ 애플리케이션 배포
⑥ (안정화 후) FormRegistry.startsAt/expiresAt 컬럼 제거
```

```json
// ③ 백필
POST /webreport-submissions/_update_by_query
{
  "query": { "bool": {
    "must": [{ "term": { "formId": "f-101" } }],
    "must_not": { "exists": { "field": "campaignId" } }
  }},
  "script": { "source": "ctx._source.campaignId = params.cid",
              "params": { "cid": "<기본 회차 id>" } }
}
```

> ⚠️ ④의 제약을 미리 인지하세요. **1단계 이전에 쌓인 익명 제출은 참여자를 알 수 없으므로
> 소급 보상이 불가능합니다.** 보상 시작 시점을 명확히 공지해야 분쟁이 없습니다.

### 스케줄러를 무엇으로 돌릴 것인가

온프레미스 전제이므로 외부 스케줄러 의존을 피합니다.

| 방식 | 평가 |
|---|---|
| 컨테이너 내 주기 태스크 (앱 기동 시 setInterval) | ✅ 단순. 단 다중 인스턴스면 중복 실행 → DB 잠금 필요 |
| 별도 cron 컨테이너 | ✅ 권장 — compose에 `scheduler` 서비스 추가, 앱과 분리 |
| DB 기반 잠금(advisory lock) | 다중 인스턴스 대비 시 병행 |

## 13. 완료 기준 (검증 시나리오)

| # | 시나리오 | 기대 |
|---|---|---|
| 1 | 기존 양식 제출 (마이그레이션 후) | ✅ 기본 회차에 귀속, 기존 동작 불변 |

| 4 | 열린 회차 없이 `/q/{id}` 접근 | ❌ 거부 |
| 5 | 주기 규칙에 따른 회차 자동 생성 | ✅ `SCHEDULED`로 사전 생성 |
| 6 | 회차 시작 시각 도달 | ✅ `OPEN` 전환 + 대상자 링크 발송 |
| 7 | `carry-over` 필드 | ✅ 지난 값 채워짐 |
| 8 | `clear` 필드 | ✅ 비어 있음 |
| 9 | `carry-with-confirm` 필드 | ✅ 확인 없이는 제출 불가 |
| 10 | 스키마 버전이 바뀐 필드 | ✅ **prefill 안 됨** |
| 11 | 익명 문항에 prefill 설정 | ❌ 거부 또는 무시 |
| 12 | 회차별 익명 k-임계값 | ✅ 회차 간 합산되지 않음 |
| 13 | 기한 후 응답 | ✅ `onTime=false` 기록 |
| 14 | 진행률 조회 | ✅ 발송/열람/응답 분리 집계 |
| 15 | 1단계·2단계 회귀 | ✅ 전체 통과 |

## 14. 4단계와의 접점

미리 잡아둘 것:

- `CampaignParticipation.revision` — 4단계 `record_history`의 변경 이력 단위가 됩니다
- 회차가 곧 **시계열 축** — 추세 분석은 `campaignId` 정렬로 구현됩니다
- `Campaign.schemaVersion` — 회차 비교 시 버전이 다르면 경고를 띄우는 근거
- `current_records`의 키는 `(respondentId, formId)` — 최신 회차 응답이 곧 현재 상태
