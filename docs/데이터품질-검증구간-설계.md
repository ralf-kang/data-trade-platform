# 데이터 품질 — 9개 차원과 검증 구간 설계

> 두 가지 질문에 대한 답입니다.
> 1. 기존 데이터의 체계·주제별 클러스터링을 **양식지 자동 입력**에 활용하려면?
> 2. 9개 품질 차원(정확성·완전성·일관성·신뢰성·현재성·이식성·대표성·유사성·적시성)을
>    **어느 인터페이스 구간**에서 점검할 것인가?

두 질문은 사실 하나로 이어집니다. **자동 입력을 하려면 기존 데이터를 신뢰할 수 있어야 하고,
그 신뢰는 품질 검증에서 나옵니다.** 순서를 뒤집으면 나쁜 데이터가 자동으로 번집니다.

---

## 1. 핵심 원칙 — 검증은 "한 곳"이 아니라 "5개 구간"에 나눠 배치한다

품질 검증을 한 군데(예: 제출 시점)에 몰아넣으면 두 가지가 다 실패합니다.
너무 늦게 잡으면 사용자가 이미 떠났고, 너무 빡빡하게 잡으면 응답을 포기합니다.

```
① 설계시점        ② 입력중        ③ 제출시        ④ 적재후(배치)      ⑤ 활용시
  (양식 빌더)      (응답 화면)      (서버)          (품질 대시보드)     (분석/추출)
      │               │               │                 │                │
  규칙을 "정의"    즉시 피드백     최종 게이트      추세·군집 진단    사용 가능 여부
  ─────────────────────────────────────────────────────────────────────────
  차단하지 않음    부드럽게        엄격하게         발견·요청        경고 표시
```

**구간마다 "차단 강도"가 달라야 합니다.**

| 구간 | 강도 | 이유 |
|---|---|---|
| ② 입력 중 | 🟡 안내만 | 타이핑 중간에 빨간 에러를 띄우면 이탈합니다 |
| ③ 제출 시 | 🔴 차단 | 여기가 유일한 강제 게이트 |
| ④ 적재 후 | 🟢 발견 | 이미 들어온 것은 막을 수 없으니 정정 요청으로 |
| ⑤ 활용 시 | 🟡 경고 | 품질 미달 데이터로 보고서를 쓰는 것을 막아야 함 |

## 2. 9개 차원별 — 무엇을, 어디서, 어떻게

### 2-1. 정확성 (Accuracy) — 값이 사실과 일치하는가

가장 어렵습니다. 시스템은 "진짜 사실"을 모르기 때문에 **참조할 기준(마스터)** 이 있어야 합니다.

| 검증 방법 | 구간 |
|---|---|
| 마스터 데이터 대조 (부서코드·사번·거래처코드) | ②실시간 + ③차단 |
| 체크섬 검증 (사업자번호, 주민번호) | ②실시간 |
| LDAP 대조 — 입력한 부서가 인사시스템과 일치하는가 | ③ + ④ |
| 외부 API 검증 (주소 → 우편번호 실재 여부) | ② |

> 💡 **LDAP 연동이 정확성에 직접 기여합니다.** 부서·사번·직급을 사용자가 타이핑하게 두지
> 말고 LDAP에서 가져온 값으로 **자동 채우고 읽기 전용**으로 만드세요. 입력 자체를 없애는
> 것이 가장 강력한 정확성 보장입니다.

### 2-2. 완전성 (Completeness) — 있어야 할 값이 다 있는가

| 검증 | 구간 |
|---|---|
| 필수 항목 미입력 | ②안내 → ③차단 |
| 조건부 필수 (A='기타'면 B 필수) | ② + ③ |
| 권장 항목 결측률 (차단은 안 하되 추적) | ④ |
| 응답률 자체 (대상자 100명 중 60명만 응답) | ④ — 이것도 완전성입니다 |

> 마지막 항목을 놓치기 쉽습니다. **개별 응답이 완전해도 전체 응답률이 낮으면
> 데이터셋은 불완전**합니다. 대표성(2-7)과 함께 봐야 합니다.

### 2-3. 일관성 (Consistency) — 서로 모순되지 않는가

| 검증 | 구간 |
|---|---|
| 필드 간 규칙 (시작일 ≤ 종료일, 비중 합계 = 100) | ②실시간 + ③차단 |
| 회차 간 모순 (지난 분기 '퇴사' → 이번 분기 '재직') | ③경고 + ④ |
| 동일인 중복 응답 간 불일치 | ④ |
| 단위 불일치 (천원 vs 원, kg vs g) | ①설계에서 예방 |

> ⚠️ 마지막이 실무에서 가장 자주 터집니다. **단위를 사용자가 쓰게 두지 말고
> 의미 타입(`AMOUNT`, `QUANTITY`)의 속성으로 고정**하세요. "3,000"이 3천원인지 3백만원인지
> 나중에는 아무도 모릅니다.

### 2-4. 신뢰성 (Reliability) — 이 값을 믿어도 되는가

값 자체는 형식에 맞아도 믿을 수 없는 경우가 있습니다.

| 신호 | 구간 |
|---|---|
| 응답 소요시간이 비정상적으로 짧음 | ③기록 + ④판정 |
| 직진 응답(모든 척도에 동일값) | ④ |
| 이전 회차와 100% 동일 (확인 없이 통과) | ③경고 |
| 자유응답이 무의미 (`ㅇㅇ`, `.`) | ③경고 + ④ |
| 입력 경로 (개인화 링크 vs 익명 vs API) | ③기록 |

**신뢰성 점수는 응답자에게 보여주지 마세요.** 위축되어 응답률이 떨어집니다.
내부 지표로만 쓰고, 보상 지급 판정(§7)과 분석 시 가중치에만 반영합니다.

### 2-5. 현재성 (Currency) — 값이 지금도 유효한가

| 검증 | 구간 |
|---|---|
| 마지막 갱신 경과일 | ④ — "6개월 이상 미갱신 38건" |
| 만료일 도래 (`DATE_EXPIRY`) | ④ + 자동 갱신 요청 |
| 회차 미참여 누적 | ④ |

> 이 차원은 **회차(Campaign) 개념이 있어야 측정됩니다.** 일회성 수집만 있으면
> "오래되었다"를 판단할 기준 자체가 없습니다.

### 2-6. 이식성 (Portability) — 다른 시스템에서 쓸 수 있는가

이 차원은 **①설계 시점에서 거의 결정됩니다.** 나중에 고치기가 가장 어렵습니다.

| 검증 | 구간 |
|---|---|
| 표준 코드체계 사용 여부 (자체 코드 vs 표준분류) | ①설계 경고 |
| 날짜/시간 형식 표준(ISO 8601) 준수 | ①고정 |
| 문자 인코딩·구분자 안전성 (CSV의 쉼표·줄바꿈) | ⑤추출 시 |
| 스키마 버전 명시 | 이미 구현됨 (`schemaVersion`) |
| 기계가 읽을 수 있는 필드 id (한글 라벨과 분리) | 이미 구현됨 |

> ✅ 현재 구조는 이 차원에서 이미 강점이 있습니다 — 필드 `id`와 라벨이 분리되어 있고,
> v1 API가 `schemaVersion`을 헤더로 알려줍니다. **자체 코드를 쓰는 것만 주의**하면 됩니다.
> 빌더에서 `CODE` 의미 타입을 고를 때 "표준 분류를 쓰시겠습니까?"를 물어보세요.

### 2-7. 대표성 (Representativeness) — 이 데이터로 전체를 말할 수 있는가

**분석·보고서 작성이 목적인 이 플랫폼에서 가장 중요한데, 가장 자주 무시되는 차원입니다.**

| 검증 | 구간 |
|---|---|
| 응답률 (대상자 대비) | ④ |
| 부서·직급별 응답 편중 | ④ |
| 무응답 편향 (특정 집단만 응답 안 함) | ④ |
| 표본 수가 결론을 내기에 충분한가 | ⑤경고 |

```
⚠ 이 데이터로 "전사 만족도"를 말하기 어렵습니다
   응답률 32% · 개발본부 편중(68%) · 생산직 응답 3건
   → 부서별 비교는 가능하나 전사 대표값으로는 부적절
```

이 경고를 **보고서 생성·데이터 추출 시점(⑤)에 띄우는 것**이 핵심입니다.
숫자만 뽑아가면 편향된 결론이 조직 의사결정에 들어갑니다.

> 대표성 검증은 **소수 응답 보호(k-익명성)와 같은 데이터를 씁니다.** 부서별 응답 수를
> 세는 로직 하나로 두 가지를 모두 처리할 수 있습니다.

### 2-8. 유사성 (Similarity) — 같은 것이 다르게 적혔는가

중복·표기 흔들림 문제입니다. 자유 입력을 허용하는 한 반드시 생깁니다.

```
"(주)한국산업"  "주식회사 한국산업"  "한국산업(주)"  "한국산업"
     ↑ 넷 다 같은 회사인데 집계하면 4개로 잡힘
```

| 검증 | 구간 |
|---|---|
| 정규화 후 근사 중복 탐지 (공백·괄호·법인격 제거) | ④배치 |
| 문자열 유사도 (편집거리·자카드) | ④ |
| 임베딩 기반 의미 유사도 (자유응답 군집) | ④ |
| **입력 중 유사값 제안** ("혹시 이것인가요?") | ② ⭐ |

> 💡 ②구간의 "유사값 제안"이 가장 효과적입니다. **사후 정제보다 입력 시점 통일이
> 압도적으로 쌉니다.** 이것이 3장의 자동 입력과 직접 연결됩니다.

### 2-9. 적시성 (Timeliness) — 필요한 때에 도착했는가

| 검증 | 구간 |
|---|---|
| 회차 마감 기한 준수율 | ④ |
| 지연 응답 비율 | ④ |
| 수집 → 분석 가능까지의 지연 | ④ |

현재성(2-5)과 혼동하기 쉽습니다. **현재성은 "값이 낡았는가", 적시성은 "제때 왔는가"** 입니다.

## 3. 기존 데이터의 체계·클러스터링을 활용한 자동 입력

이제 첫 번째 질문입니다. 위 품질 검증이 갖춰졌다는 전제에서 설계합니다.

### 3-1. 자동 입력의 4단계 — 신뢰도 순

**신뢰도가 높은 것부터 적용하고, 낮은 것은 반드시 사용자 확인을 받으세요.**

| 단계 | 출처 | 신뢰도 | 사용자 개입 |
|---|---|---|---|
| **① 신원 기반** | LDAP (부서·사번·직급) | ★★★★★ | 없음 — 읽기 전용으로 채움 |
| **② 이력 기반** | 내 지난 회차 응답 | ★★★★☆ | 확인만 ("변경 없음" 버튼) |
| **③ 군집 기반** | 유사 응답자들의 분포 | ★★☆☆☆ | **반드시 선택** (제안일 뿐) |
| **④ 유사값 정규화** | 기존 입력값 사전 | ★★★☆☆ | 제안 후 선택 |

> 🔴 **③을 ①②처럼 자동으로 채우면 안 됩니다.** "다른 사람들이 이렇게 답했으니 당신도
> 그럴 것"이라는 추정을 기본값으로 넣으면, 사용자가 무심코 통과시켜 **없는 사실이
> 데이터가 됩니다.** 이건 품질 개선이 아니라 오염입니다.

### 3-2. ② 이력 기반 — Prefill (가장 가치 높음)

이미 [재설계 제안](./플랫폼-재설계-제안.md) §4-1에 설계했습니다. 필드별 정책:

- `carry-over` — 지난 값 그대로 (부서, 직급)
- `clear` — 매번 새로 (이번 분기 실적)
- `carry-with-confirm` — 채우되 확인 필수 (자격증 만료일)

### 3-3. ④ 유사값 정규화 — 값 사전(Value Dictionary)

같은 필드에 들어온 과거 값들을 정규화해 사전으로 쌓아두고, 입력 중 제안합니다.

```
사용자 입력: "한국산"
              ↓ 값 사전 조회 (정규화 + 유사도)
제안: ┌────────────────────────────────┐
      │ (주)한국산업        ← 342건 사용 │
      │ 한국산업개발(주)     ← 28건 사용  │
      │ + "한국산"을 새 값으로 추가       │
      └────────────────────────────────┘
```

**설계 포인트:**
- 사용 빈도 순으로 정렬 → 표준 표기가 자연스럽게 상위로
- "새 값 추가"를 항상 열어둘 것 — 막으면 사용자가 엉뚱한 값을 고릅니다
- 새 값이 일정 빈도를 넘으면 **표준 후보로 승격**해 관리자에게 알림
- Elasticsearch의 `terms` 집계 + `fuzzy` 쿼리로 구현 가능 — 별도 저장소 불필요

> ✅ 이것이 비정형 저장소(ES)를 잘 쓰는 지점입니다. 값 사전을 따로 관리하지 않고
> **이미 쌓인 제출 데이터에서 실시간 집계**하면 됩니다.

### 3-4. ③ 군집 기반 — 조심스럽게

주제별 클러스터링을 자동 입력에 쓰려면 **제안(suggestion)으로만** 노출해야 합니다.

| 용도 | 적절성 |
|---|---|
| 자유응답을 주제별로 묶어 **분석 화면에 표시** | ✅ 매우 적절 |
| 유사 응답자의 값을 **선택지로 제안** | ⚠️ 조건부 (반드시 선택 UI) |
| 유사 응답자의 값을 **기본값으로 채움** | ❌ 금지 |
| 비슷한 양식지를 **템플릿으로 추천** (제작자에게) | ✅ 적절 — 양식 중복 제작 감소 |

마지막 항목이 의외로 가치가 큽니다. 부서마다 비슷한 양식을 또 만드는 낭비를,
**"이런 양식이 이미 있습니다"** 추천으로 줄일 수 있습니다.

### 3-5. 자동 입력에는 출처 표시가 필수입니다

```
부서       [ 품질보증팀 ]  🔒 인사시스템 자동
연락처     [ 010-•••• ]   ↩ 지난 회차 값
거래처     [ (주)한국산업 ] 💡 기존 입력값에서 제안
```

**왜 필요한가:** 자동으로 채운 값과 사용자가 직접 쓴 값의 신뢰도는 다릅니다.
`SubmissionDocument`에 필드별 입력 출처(`fieldSources`)를 남겨두면,
나중에 "이 값은 사람이 확인한 것인가, 그냥 따라온 것인가"를 구분해 품질 점수에
반영할 수 있습니다. 이걸 안 남기면 **자동 입력이 품질 지표를 부풀립니다.**

## 4. 구간별 구현 위치 (현재 코드 기준)

| 구간 | 위치 | 신규/기존 |
|---|---|---|
| ① 설계 | `FormBuilder` 우측 상세패널 — 의미 타입·규칙 편집기 | 확장 |
| ② 입력 중 | `/q/[id]` 응답 화면 — 실시간 검증·제안 API | 신규 |
| ③ 제출 시 | `submissionService`, `apiIngestService.validateRow` | **일부 존재** |
| ④ 적재 후 | 품질 배치 + 품질 대시보드 | 신규 |
| ⑤ 활용 시 | 데이터 추출·API 응답에 품질 메타 첨부 | 신규 |

> ✅ ③은 이미 `validateRow`(필수·정규식·선택지·숫자)가 있습니다. 여기에 의미 타입 기반
> 검증을 얹으면 되므로, **③이 가장 적은 비용으로 확장 가능한 지점**입니다.

### 검증 로직은 한 곳에 두고 세 곳에서 재사용하세요

```
src/lib/quality/rules.ts   ← 규칙 정의 (의미 타입 + 필드 간 규칙)
        │
        ├─ 클라이언트(②) : 입력 중 즉시 피드백
        ├─ 서버(③)      : 제출·API 게이트  ← 유일한 신뢰 경계
        └─ 배치(④)      : 기존 데이터 재검사
```

**클라이언트 검증은 UX용이지 보안이 아닙니다.** 서버(③)를 반드시 통과시켜야 하고,
규칙이 갈라지면 "화면에선 통과했는데 저장이 안 된다"는 최악의 경험이 나옵니다.

## 5. 우선순위 제안

전부 한 번에 하면 안 됩니다. 투자 대비 효과 순:

| 순위 | 항목 | 이유 |
|---|---|---|
| 1 | **LDAP 자동 채움 + 읽기 전용** (①정확성) | 입력을 없애는 것이 최선. LDAP 연동이 방금 갖춰짐 |
| 2 | **의미 타입 + ③서버 검증 확장** | 이미 있는 `validateRow`에 얹는 것이라 저비용 |
| 3 | **Prefill** (②이력 기반) | 응답 부담 감소 효과가 가장 큼 |
| 4 | **값 사전 제안** (유사성) | 사후 정제보다 압도적으로 쌈. ES 집계로 구현 |
| 5 | **④품질 대시보드 + 정정 요청** | 발견-조치 사이클 완성 |
| 6 | **⑤대표성 경고** | 잘못된 결론 방지 — 늦게 해도 되지만 반드시 필요 |
| 7 | 군집 기반 제안 | 가장 나중. 앞의 것들이 없으면 오염만 가속 |

## 6. 한 가지 경고

**품질 검증을 강화할수록 응답률은 떨어집니다.** 이건 피할 수 없는 상충입니다.

- 필수 항목을 늘리면 → 이탈률 상승
- 형식 검증을 엄격히 하면 → 포기율 상승
- 확인 단계를 추가하면 → 완료율 하락

그래서 **자동 입력(3장)과 품질 검증(2장)을 반드시 함께 설계해야 합니다.**
검증만 강화하면 사용자는 떠나고, 자동 입력만 강화하면 데이터가 오염됩니다.

> 가장 좋은 품질 관리는 **사용자가 입력할 것을 줄이는 것**입니다.
> LDAP에서 가져올 수 있는 건 묻지 말고, 지난번에 답한 건 다시 묻지 마세요.
