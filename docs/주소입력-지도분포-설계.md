# 주소 입력 컴포넌트 · 지도 분포 화면 설계

> 상태: **설계 초안** — 구현 착수 전 검토 필요
> 작성 배경: `map-address`("주소 및 지도") 컴포넌트는 현재 **팔레트 항목과 상세 패널 설명
> 문구만 존재**하고, 실제 응답 화면에서는 일반 텍스트 입력으로 렌더링된다
> (`FormClient.tsx`의 기본 `else` 분기로 떨어짐 — 이번 세션에 고친 `privacy-consent`와
> 같은 상태였다). 지도·주소 관련 패키지도 설치되어 있지 않다.
> 이 문서는 ① 주소 검색·입력 컴포넌트와 ② 수집된 주소의 지도 분포 화면을 함께 설계한다.

> ⚠️ **외부 서비스 사양 확인 필요**: 아래 §2-3에 언급하는 공공 주소 데이터·API의 제공
> 형태·갱신 주기·좌표 포함 여부는 **구현 착수 시점에 공식 문서로 재확인**해야 한다.
> 이 문서는 방식 선택의 논리를 정리한 것이지, 특정 API 스펙을 확정한 것이 아니다.

## 0. 한 줄 정의

> **응답자가 키워드로 주소를 찾아 정확히 입력하게 하고, 그렇게 모인 주소를 지도 위에
> "개인이 특정되지 않는 단위로만" 집계해 보여주는 기능.**

---

## 1. 먼저 — 지도는 이 플랫폼에서 가장 강한 재식별 경로다

**주소는 준식별자가 아니라 사실상 직접 식별자에 가깝다.** 지도에 핀 하나를 찍는 순간
그 핀은 "이 주소에 사는 사람이 이 설문에 응답했다"를 의미한다. 단독주택이면 곧 그 가구다.

워드클라우드나 온톨로지 캔버스에 걸어둔 안전장치를 여기에 **그대로, 더 강하게** 적용해야 한다.
그런데 이 기능에는 다른 기능에 없는 좋은 성질이 하나 있다:

> 💡 **클러스터링은 렌더링 최적화가 아니라 프라이버시 장치로 쓸 수 있다.**
> 요청받은 "줌 인/아웃 시 클러스터링" UX가, 설계만 제대로 하면 그 자체로 k-익명성 보장이 된다.

### 1-1. 핵심 규칙 — 클러스터는 k명 미만으로 쪼개지지 않는다

일반적인 지도 클러스터링은 줌을 당기면 클러스터가 개별 핀으로 분해된다. **이 동작을 막는다.**

```
줌 인 →  클러스터 분해 시도
          ↓
      분해 결과 자식 클러스터가 모두 k명 이상인가?
          ├─ 예  → 분해한다
          └─ 아니오 → 분해하지 않는다 (클러스터 유지, "더 확대할 수 없음" 표시)
```

이 규칙 하나로 **개별 핀은 어떤 줌 레벨에서도 렌더링되지 않는다.** 화면상 최소 단위가 항상
k명 이상의 묶음이므로, 지도에서 특정 개인의 위치를 읽어낼 수 없다.

k는 새로 정하지 않고 **이미 있는 `SystemConfig.defaultAnonymityThreshold`(기본 5)를 재사용**한다 —
워드클라우드·온톨로지·군집 제안이 모두 이 값을 쓰고 있어 기준이 하나로 유지된다.

### 1-2. k만으로 부족한 것 — 중심점도 위치를 흘린다

k명이 모인 클러스터라도, 그 k명이 전부 같은 아파트 단지면 **중심점이 곧 그 단지**다.
따라서 클러스터 마커의 좌표는 **실제 중심점이 아니라 격자(grid)에 스냅한 좌표**를 쓴다.
격자 크기는 줌 레벨에 연동한다(넓게 볼수록 거친 격자).

### 1-3. 나머지 안전장치 (기존 원칙 그대로 적용)

| # | 장치 | 근거 |
|---|---|---|
| 1 | **마스킹 대상 양식지 전면 제외** | 워드클라우드·값 사전·주제별 그룹과 동일 원칙. 주소 원문을 좌표로 바꿔 표시하는 것은 마스킹 우회다 |
| 2 | **개인식별자 태그 문항 제외** | 주소 문항이 `personalIdentifier`로 태그되면 지도 대상에서 제외 |
| 3 | **최대 줌 상한** | k 게이트와 별개로 줌 자체에 상한을 둔다(읍·면·동 수준). 값싼 이중 방어 |
| 4 | **클러스터 클릭 시 개별 레코드 노출 금지** | 팝업에는 건수·집계만. 응답 원문·응답자는 절대 표시하지 않는다 |
| 5 | **조회 감사 로그** | 지도 조회도 데이터 출구다. 워드클라우드 조회와 같이 기록 |

## 2. 주소 입력 컴포넌트 (`map-address` 재설계)

### 2-1. 저장 값 구조

현재는 문자열 하나다. 검색 결과를 구조화해 저장한다 — 특히 **법정동코드(`bcode`)가 중요**하다.
좌표 없이도 시·군·구 단위 집계가 가능해지고, 그 집계가 §4-1의 기본 표현이 된다.

```ts
interface AddressValue {
  postcode: string;      // 우편번호
  roadAddress: string;   // 도로명주소
  jibunAddress?: string; // 지번주소
  detail: string;        // 상세주소 — 응답자가 직접 입력 (동/호수 등)
  bcode?: string;        // 법정동코드 — 행정구역 집계의 키
  lat?: number;          // 지오코딩 결과 (저장 여부는 §2-4 정책 결정)
  lon?: number;
}
```

> 🔴 **상세주소(`detail`)는 지도·집계에 절대 쓰지 않는다.** 동·호수는 가구를 특정하는
> 값이며, 우편 발송 같은 원래 목적 외에는 쓸 이유가 없다. 저장은 하되 분석 경로에서 배제한다.

### 2-2. 응답 화면 동작

1. 응답자가 키워드 입력 ("테헤란로 152", "강남구청")
2. 유사 주소 목록 표시 → 선택
3. 선택 시 우편번호·도로명·지번·법정동코드가 자동 채워지고 **읽기 전용**이 된다
4. 상세주소만 직접 입력

3번의 읽기 전용 처리는 LDAP 자동 채움과 같은 논리다 — **사람이 타이핑하지 않으면 오타가
날 수 없고**, 표기 흔들림("서울시" vs "서울특별시")이 원천 차단되어 집계가 깨지지 않는다.

### 2-3. 주소 검색 방식 — 3가지 안 비교

요청하신 우선순위("패키지화 > 외부 API + 목적지 공개")에 맞춰 비교한다.

| 안 | 방식 | 온프레미스 | 외부 통신 | 판단 |
|---|---|---|---|---|
| **A** | **공공 주소 DB 파일을 받아 자체 구축** | ✅ 완전 가능 | **없음** | ✅ **권장** |
| B | 공공 주소 검색 OpenAPI 호출 | 망 개방 필요 | 있음 (검색어가 나감) | 차선 |
| C | CDN 배포형 주소 검색 위젯(JS) | ❌ 사실상 불가 | 있음 (CDN 스크립트) | 온프레미스 부적합 |

**C안이 국내 웹에서 가장 흔하지만 이 프로젝트에는 맞지 않는다.** 외부 CDN에서 스크립트를
내려받아 실행하는 구조라 폐쇄망에서 동작하지 않고, 스크립트 자체가 외부에서 바뀔 수 있어
온프레미스 환경의 변경 통제 원칙과도 어긋난다.

> ⚠️ **B안(외부 API)의 숨은 문제**: 외부로 나가는 것이 **응답자가 입력 중인 주소 문자열**이다.
> 즉 주소 검색을 외부 API로 돌리는 것은 그 자체로 개인정보를 외부 사업자에게 흘리는
> 경로가 된다. A안을 권장하는 이유가 단지 폐쇄망 대응만은 아니다.

### 2-4. 권장안 — 자체 구축 + 오프라인 갱신

행정안전부가 도로명주소 데이터를 **파일 형태로 배포**하며(전체분 + 변경분), 별도의
주소 기반 지원 서비스에서 **좌표 정보**도 제공한다. 이를 내려받아 로컬 저장소에 적재하면:

- 주소 검색 = **로컬 DB 질의** → 외부 통신 0
- 지오코딩(주소→좌표) = **로컬 조회** → 외부 통신 0
- 갱신 = 주기적으로 변경분 파일을 반입해 반영 (**오프라인 업데이트**)

> 📌 **확인 필요**: 제공 파일의 구성·갱신 주기·좌표 포함 범위, 그리고 **이용 조건(라이선스·
> 출처 표시 의무)**은 구현 착수 시 공식 문서로 확인해야 한다. 이 문서는 "파일 배포본을
> 받아 자체 구축한다"는 **방식**을 확정할 뿐이다.

**적재 위치**: 주소 검색은 오타·부분 일치 검색이 핵심이므로 **Elasticsearch**가 적합하다.
이미 Nori 형태소 분석기가 설치되어 있고, 값 사전 제안에서 쓴 `prefix`+`fuzzy` 조합을
그대로 재사용할 수 있다. 별도 인덱스(`webreport-address`)로 분리한다 — 응답 데이터가 아니라
참조용 마스터 데이터이므로 성격이 다르다.

### 2-5. 좌표계 주의

국내 공공 좌표 데이터는 **웹 지도와 다른 좌표계**(예: UTM-K 계열)로 제공되는 경우가 많다.
웹 지도는 WGS84 기반이므로 **적재 시점에 변환해 저장**한다. 조회 때마다 변환하면 느리고,
변환 로직이 여러 곳에 흩어지면 어긋난다. 변환은 `proj4` 같은 검증된 라이브러리를 쓴다.

### 2-6. 좌표를 응답 데이터에 저장할 것인가

두 가지 선택지가 있고, 이건 **정책 결정**이다(§8).

| 안 | 내용 | 장단 |
|---|---|---|
| **저장 안 함 (권장)** | 응답에는 주소·`bcode`만. 지도 조회 시 주소로 그때그때 로컬 지오코딩 | 정밀 좌표라는 새 개인정보를 만들지 않음. 조회 시 비용 발생 |
| 저장함 | 제출 시 좌표까지 저장 | 조회가 빠름. 다만 **원래 수집 항목에 없던 정밀 위치를 파생 생성**하는 셈 |

수집 동의서에 "주소"라고 고지하고 받았다면, 그로부터 정밀 좌표를 만들어 **저장**하는 것이
고지 범위 안인지 다툼의 여지가 있다. 지도 표시를 위한 **일시적 변환**은 목적 내로 보기 쉽다.
따라서 저장하지 않는 쪽을 기본으로 제안한다.

## 3. 외부 연결 투명성 — 슈퍼관리자 설정 화면

요청하신 "외부 API를 쓸 경우 목적지 URL/IP를 설정 화면에 표시" 요구를, **주소 기능에만
한정하지 않고 플랫폼 전체의 외부 연결 목록**으로 일반화한다. 폐쇄망 반입 시 방화벽 허용
목록을 뽑아야 하고, "이 시스템이 밖으로 무엇을 보내는가"는 어차피 감사 대상이기 때문이다.

### 3-1. `/super-admin/settings`에 "외부 연결" 섹션 신설

| 용도 | 모드 | 목적지 | 포트 | 상태 |
|---|---|---|---|---|
| 주소 검색 | 🟢 내장(로컬 DB) | — | — | 데이터 기준일 2026-07-01 |
| 지오코딩 | 🟢 내장(로컬 DB) | — | — | 데이터 기준일 2026-07-01 |
| 지도 타일 | 🟠 외부 | `tiles.example.go.kr` | 443 | 마지막 확인 2026-07-30 12:00 ✅ |
| LDAP | 🟠 외부 | `ldap.company.com` | 389 | 마지막 확인 … ✅ |
| SMTP | 🟠 외부 | `smtp.company.com` | 465 | 미설정 |

- **모드 배지**로 내장/외부를 한눈에 구분한다. 내장이면 목적지가 비어 있는 게 정상이다.
- 외부 항목은 **연결 테스트 버튼**을 둔다 — 이미 LDAP 설정에 있는 패턴(`/api/ldap-config/test`)을 그대로 쓴다.
- 내장 항목은 **데이터 기준일**을 표시한다. 오프라인 갱신 체계에서는 "언제 받은 데이터인가"가
  곧 신뢰도이며, 갱신을 잊으면 신규 주소가 검색되지 않는 방식으로 조용히 고장 나기 때문이다.

### 3-2. 설정은 코드가 아니라 DB에 둔다

`ExternalEndpointConfig` 모델(§6)로 관리한다. 목적지를 코드에 하드코딩하면 폐쇄망마다
빌드를 다시 해야 하고, 화면에 무엇이 표시되는지와 실제 호출 대상이 어긋날 수 있다.
**화면에 보이는 값이 곧 실제 호출 대상**이어야 이 기능이 의미가 있다.

## 4. 지도 분포 화면

위치: `/admin/data/[formId]/map` — 품질 대시보드·워드클라우드와 같은 양식지 단위 스코프.

### 4-1. 두 가지 표현 — 행정구역 집계가 기본, 핀 클러스터는 확대 보기

| 표현 | 단위 | 좌표 필요 | 안전성 | 위치 |
|---|---|---|---|---|
| **행정구역 집계 (기본)** | 시·도 → 시·군·구 → 읍·면·동 | ❌ (`bcode`만) | 높음 | 첫 화면 |
| **핀 클러스터 (확대)** | 격자 스냅된 클러스터 | ✅ | k 게이트로 확보 | 토글 |

**기본을 행정구역 집계로 두는 이유**: 실무에서 필요한 답은 대개 "어느 구에 몇 명"이지
"정확히 어느 지점"이 아니다. `bcode`만으로 계산되므로 **지오코딩도, 좌표도 필요 없고**,
k 게이트도 "해당 구역 응답 수 < k면 상위 구역으로 합산"으로 단순하게 걸린다.

핀 클러스터는 요청하신 줌 인/아웃 UX를 제공하되, §1-1의 분해 규칙을 지킨다.

### 4-2. 클러스터링 구현 — 서버에서 집계한다

> 🔴 **개별 좌표를 브라우저로 내려보내고 클라이언트에서 클러스터링하면 안 된다.**
> 화면에 클러스터만 그려도 **네트워크 응답에는 개별 좌표가 그대로 들어 있어**, 개발자 도구로
> 원본을 열람할 수 있다. 워드클라우드에서 지켰던 원칙("마스킹된 값만 내보낸다")과 같다.

따라서 **서버가 줌 레벨·화면 영역을 받아 클러스터를 계산해 내려준다.** 응답에는 클러스터의
격자 스냅 좌표와 건수만 담기고, 개별 좌표는 서버 밖으로 나가지 않는다.

```
GET /api/forms/{formId}/map?fieldId=...&zoom=11&bbox=...
→ { clusters: [ { lat, lon, count }, ... ], suppressed: 3 }
```

`suppressed`는 **k 미만이라 표시하지 못한 클러스터 수**다. 숨겼다는 사실 자체는 알려야
"데이터가 없는 것"과 "가려진 것"을 구분할 수 있다(품질 대시보드의 대표성 경고와 같은 취지).

### 4-3. 화면 구성

- 상단: 대상 문항 선택(주소 문항이 여러 개일 수 있음), 표현 토글(행정구역/핀)
- 지도: 클러스터 마커 + 건수 라벨. 클릭 시 **건수와 행정구역명만** 팝업
- 하단: 상위 행정구역 순위표 (k 미만 구역은 "기타"로 합산)
- 안내: k 게이트로 인해 일정 수준 이상 확대되지 않는다는 설명

## 5. 기술 스택

| 영역 | 선택 | 이유 |
|---|---|---|
| 지도 렌더링 | **Leaflet** (npm) | MIT, 자체 외부 통신 없음, 타일 소스 교체 자유 |
| 클러스터 계산 | **서버 측 격자 집계** (자체 구현) | §4-2 — 개별 좌표를 내보내지 않기 위해 클라이언트 라이브러리를 쓰지 않는다 |
| 좌표계 변환 | **proj4** (npm) | 적재 시점 1회 변환 |
| 주소 검색 인덱스 | **Elasticsearch** (기존) | Nori + `prefix`/`fuzzy` 자산 재사용 |
| 지도 타일 | **미결정 (§8)** | 유일하게 외부 의존이 남는 지점 |

> ⚠️ **타일이 마지막 관문이다.** 지도 배경 이미지는 어디선가 받아야 하고, 이것만은
> 자체 구축 비용이 크다(전국 타일 사전 렌더링·저장). 선택지는 ① 외부 타일 서버 허용
> (§3의 외부 연결 목록에 등재) ② 타일셋 반입 후 자체 서빙 ③ 배경 지도 없이 행정구역
> 경계만 표시(경계 데이터는 파일로 확보 가능, 용량 작음).
> **③은 §4-1의 행정구역 집계 표현과 결합하면 외부 의존 0으로 완결된다** — 폐쇄망
> 우선이라면 ③으로 시작하고 핀 클러스터는 타일 확보 후 여는 것이 현실적이다.

## 6. 스키마 (초안)

```prisma
enum EndpointMode { BUILTIN EXTERNAL DISABLED }

/// 이 플랫폼이 외부로 나가는 모든 목적지의 단일 목록.
/// 화면에 표시되는 값이 곧 실제 호출 대상이어야 하므로 코드가 아닌 DB에 둔다.
model ExternalEndpointConfig {
  id          String       @id            // "address-search" | "geocoding" | "map-tiles" | ...
  label       String                      // "주소 검색"
  mode        EndpointMode @default(BUILTIN)
  // mode=EXTERNAL일 때만 의미. 호스트 또는 IP.
  host        String?
  port        Int?
  scheme      String?                     // https | http
  pathPrefix  String?
  // mode=BUILTIN일 때 — 내장 데이터의 기준일. 오프라인 갱신 체계의 신뢰도 지표.
  dataAsOf    DateTime?
  lastCheckedAt DateTime?
  lastCheckOk   Boolean?
  note        String?
  updatedAt   DateTime     @updatedAt

  @@map("external_endpoint_config")
}
```

주소 마스터 데이터는 **Postgres가 아니라 Elasticsearch 인덱스**(`webreport-address`)로
관리하므로 Prisma 모델을 두지 않는다. 갱신 이력만 위 `dataAsOf`로 표시한다.

`FormField`에는 주소 문항의 세부 설정을 추가한다:

```ts
// map-address 전용
addressOptions?: {
  requireDetail: boolean;   // 상세주소 필수 여부
  mapEnabled: boolean;      // 이 문항을 지도 분포 대상으로 쓸지 (제작자가 명시적으로 켠다)
};
```

`mapEnabled`를 **기본 false**로 두는 것이 중요하다. 주소를 수집했다고 해서 자동으로 지도에
올라가면, 제작자가 의도하지 않은 데이터 노출 경로가 조용히 생긴다.

## 7. 구현 우선순위

| 순위 | 항목 | 이유 |
|---|---|---|
| 1 | **`map-address` 응답 화면 렌더링 수정** | 지금 일반 텍스트로 떨어지는 것부터 고친다. 구조화 저장(`AddressValue`) 포함 |
| 2 | **주소 마스터 데이터 적재 + 검색 API** | 컴포넌트가 동작하려면 검색이 먼저 있어야 한다 |
| 3 | **`/super-admin/settings` 외부 연결 섹션** | 주소 데이터를 어떤 모드로 쓰는지 표시할 자리. 요청하신 투명성 요건 |
| 4 | **행정구역 집계 지도** (`bcode` 기반) | 좌표·타일 없이 완결된다. 폐쇄망에서 바로 쓸 수 있는 첫 결과물 |
| 5 | **핀 클러스터 + k 분해 게이트** | 지오코딩·타일 확보가 전제 |
| 6 | 지도 조회 감사 로그 | 5번과 함께 |

1~4번까지는 **외부 통신 없이 완결**되고, 5번에서만 타일 문제를 마주한다.

## 8. 결정이 필요한 사항

1. **지도 타일 소스** (§5) — 외부 타일 서버를 허용할 수 있는 망 환경인가, 아니면
   행정구역 경계만으로 시작할 것인가? 이 답이 §7의 4·5번 순서를 결정한다.
2. **좌표 저장 여부** (§2-6) — 응답 데이터에 정밀 좌표를 저장할 것인가, 조회 시 변환할 것인가?
3. **주소 데이터 반입 경로** — 폐쇄망에 파일을 반입하는 절차(주기·승인)가 이미 있는가?
   없다면 갱신이 실무적으로 돌아가지 않는다.
4. **k 값** — 지도에도 `defaultAnonymityThreshold`(기본 5)를 그대로 쓸 것인가?
   주소는 다른 항목보다 식별력이 높아 **더 큰 값**을 쓸 여지가 있다.
5. **기존 주소 데이터 처리** — 이미 `map-address`로 수집된 값은 구조화되지 않은 문자열이다.
   소급 파싱할 것인가, 신규 응답부터만 지도 대상으로 삼을 것인가?
