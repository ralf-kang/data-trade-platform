# 양식지 간 관계(온톨로지) 기능 설계

> 상태: **설계 확인 대기** — 구현 전 승인 필요
> 작성 배경: 기존 `/super-admin/data-map`(시스템 테이블 ERD)은 요구사항을 잘못 해석한 것이다.
> 요구는 "**양식지와 양식지 사이에 같은 키값이 들어왔을 때, 사용자가 스스로 FK로 엮어보고
> 확장해 나갈 수 있는지 테스트·확인**"하는 온톨로지형 기능이다. 이 문서는 그 재설계다.

---

## 0. 한 줄 정의

> 서로 다른 양식지가 **같은 값을 담은 문항**을 갖고 있는지 사용자가 직접 **테스트**하고,
> 그 문항 쌍을 **관계로 선언**한 뒤, 응답 레코드에서 **한 홉씩 타고 넘어가며 탐색**하는 기능.

「시스템의 DB 스키마」가 아니라 「사용자가 수집한 데이터끼리의 의미적 연결」이 대상이다.

---

## 1. 이 기능이 위험한 이유 — 먼저 정리하고 시작한다

**이 기능은 구조적으로 재식별(re-identification) 도구다.** 마스킹 계층이 막으려던 바로 그
행위를 기능으로 제공하는 것이므로, 프라이버시 설계를 나중에 덧붙일 수 없다.

- 조인 키로 가장 쓸모 있는 필드(사번·전화번호·이메일)가 곧 **직접 식별자**다.
  각각으로는 안전하던 두 양식지가, 연결되는 순간 **결합된 하나의 프로파일**이 된다.
- k-익명성은 원래 "고립된 단일 테이블"을 전제로 설계된 개념이라 **외부 데이터셋과의 결합을
  견디도록 만들어지지 않았다.** 각각 안전해 보이던 준식별자도 교차 참조되면 유일해진다.
- 더 교묘한 경로: **연결 테스트 화면 자체가 정보 누출 채널**이다.
  "사번 12345로 필터 → 매칭 1건"을 확인하는 것만으로 k=1이 드러난다.
  즉 결과 레코드를 안 보여줘도, **통계만으로 재식별이 가능하다.**

### 필수 안전장치 (MVP 첫 커밋부터 포함)

| # | 안전장치 | 내용 |
|---|---|---|
| **S1** | **익명 문항 원천 배제** | `anonymous: true` 필드는 관계 정의 대상에서 **드롭다운에 나타나지도 않게** 하고 API에서도 거부. 익명 문항은 응답자와 분리 저장되므로 연결은 곧 익명성 파기다. **예외 없음.** |
| **S2** | **개인식별자 연결에는 개인정보 취급 자격 필요** | 마스킹 계층의 권한 모델(`AuthorAuthorization`)을 그대로 재사용. 무자격자는 비식별 키(부서코드·제품코드·캠페인ID)로만 연결 가능 |
| **S3** | **모든 통계에 k-익명성 하한** | 매치 건수·매치율·샘플값 등 **발견 단계의 모든 출력**에 최소 집계 크기 k 강제(기본 5). k 미만이면 정확한 수치 대신 "k 미만"으로 대체 |
| **S4** | **기본은 집계 전용** | 연결 결과를 원본 레코드가 아니라 **건수·분포**로 먼저 보여준다. 원본 열람은 별도 권한 + 별도 동작 |
| **S5** | **샘플 매칭값 마스킹** | 매칭된 실제 값 예시는 개인식별자에서 위험. 부분 마스킹(`010-****-5678`)만 제공하거나 자격자에게만 노출 |
| **S6** | **마스킹 상태 전파** | 연결 결과의 마스킹 수준은 **양쪽 중 더 엄격한 쪽**을 따른다. "마스킹된 양식 + 안 된 양식"을 이어 붙여 마스킹을 무력화할 수 없게. k=1 전면 마스킹 레코드는 연결 결과에서도 계속 제외 |
| **S7** | **감사 로그 — 테스트 시도까지 기록** | 누가/언제/어떤 양식지 쌍을/어떤 키로 테스트했는지, 결과 건수까지. **연결을 만들지 않고 "테스트만" 한 것도 로깅.** 재식별 시도 탐지의 유일한 방어선 |
| **S8** | **레이트 리밋 + 반복 질의 탐지** | 키 값을 바꿔가며 반복 조회하는 차분 공격 패턴 차단 |
| **S9** | **링크 기본 비공개** | 개인식별자 기반 링크는 슈퍼관리자(개인정보 담당) 승인 후에만 조직 공유로 승격 |

## 2. MVP (1단계) — 화면 설계

### 2-1. 관계 관리 화면 `/admin/form-links`

양식지 쌍 목록 + [새 관계 만들기]. 각 행: 좌측 양식·문항 → 우측 양식·문항, 매치율, 상태
(초안/승인대기/공유됨), 소유자.

### 2-2. ★ 연결 테스트 화면 — **이 기능의 핵심. 여기 품질이 전부다**

```
┌─ 좌측 ───────────────────┐   ┌─ 우측 ───────────────────┐
│ 양식지 [2024 만족도조사 ▾] │   │ 양식지 [온보딩 피드백  ▾] │
│ 문항   [사번           ▾] │   │ 문항   [사원번호       ▾] │
└──────────────────────────┘   └──────────────────────────┘
                    [ 연결 테스트 ]

┌─ 결과 ─────────────────────────────────────────────────┐
│  매치율   좌측 기준 94%  │  우측 기준 62%               │
│           (호버 시 계산식과 원시 수치 노출)              │
│                                                        │
│  좌측 고유값 128 │ 우측 고유값 194 │ 교집합 120          │
│  좌측에만 8건    │ 우측에만 74건                        │
│                                                        │
│  → 우측 문항이 100% 고유합니다. N:1 관계를 제안합니다.   │
└────────────────────────────────────────────────────────┘

정규화 규칙 (켤 때마다 매치율 실시간 재계산)
 ☑ 앞뒤/중복 공백 제거        62% → 94%
 ☐ 하이픈·구분자 제거          (010-1234-5678 ↔ 01012345678)
 ☐ 대소문자 통일
 ☐ 선행 0 무시                (00123 ↔ 123)
 ☐ 전각/반각 숫자 변환
 ☐ 한글 자모 정규화(NFC)      ← macOS(NFD)/Windows(NFC) 혼재 시 필수
```

**설계 근거 (벤치마킹)**
- 매치율 배지 + 호버 계산식 노출 = **Trifacta**. 블랙박스로 점수만 던지면 신뢰를 못 얻는다.
- 좌/우 **양방향** 포함률을 둘 다 보여주는 이유: 어느 쪽이 FK이고 어느 쪽이 PK인지
  **방향 판정에 결정적**이기 때문. 한쪽만 보면 크기 차이가 큰 경우 오판한다.
- 좌측만/우측만 건수 = **Alteryx의 J·L·R 3앵커 Venn**을 숫자로 축약한 것.
- 유일성 비율로 카디널리티 자동 제안 = **Power BI**. 단 자동 확정하지 않고 **제안만** 한다
  (Power BI도 확신이 낮으면 아예 관계를 만들지 않는 보수적 정책).
- 정규화 효과를 실시간으로 보여주는 것이 사용자에게 가장 설득력 있다.
- **한글 자모 정규화(NFC)** 는 눈에는 같아 보이는데 절대 매칭 안 되는 대표 함정이라 필수.

**여기에 S3·S5 적용**: 교집합이 k 미만이면 수치 대신 "k 미만" 표기, 샘플값은 마스킹.

### 2-3. 관계 정의 시 입력 항목

| 항목 | 필수 | 비고 |
|---|---|---|
| 좌/우 양식지 + 문항 | ✅ | |
| **관계 이름** | ✅ | 업무 언어로. 예: "이 직원이 제출한 만족도조사" |
| **역방향 이름** | ✅ | 예: "이 응답을 제출한 직원". **Foundry는 양쪽 이름을 한 정의 안에서 필수 입력**받는다 |
| 카디널리티 | ✅(자동 제안) | 1:1 / 1:N / N:1 / N:N |
| 정규화 규칙 | ✅ | 위 토글 상태 |
| 설명·근거 메모 | 권장 | 거버넌스·감사용 |

> **동일한 두 양식지 사이에 여러 관계가 존재할 수 있다** (예: "작성자 사번" 관계와
> "대상자 사번" 관계). 따라서 관계마다 고유 ID가 필요하다 (Foundry의 API name 개념).

### 2-4. 탐색 UI — **그래프 캔버스가 아니라 트리 뷰로 시작**

응답 레코드 상세 화면 하단에 **"연결된 데이터"** 섹션:

```
▼ 연결된 데이터
   ▼ 이 직원이 제출한 만족도조사 (3건)
        • SUB-001  2026-07-27  만족도 4점    → [열기]
        • SUB-014  2026-05-02  만족도 3점    → [열기]
   ▶ 이 직원의 워크샵 신청 (1건)
```

레코드를 열면 **거기서 또 그 레코드의 "연결된 데이터"를 펼칠 수 있다** = 자연스러운
hop-by-hop 순회. **Foundry Object Explorer의 Links 위젯(nested links)** 패턴이다.

캔버스 그래프 없이도 온톨로지 경험의 대부분을 제공하면서 구현 비용은 훨씬 낮다.
캔버스는 2단계로 미룬다.

### 2-5. MVP에서 의도적으로 제외

자동 관계 발견 / 그래프 캔버스 / 복합 키 / 퍼지 매칭 / 필터 전파 방향

> **퍼지 매칭을 MVP에서 빼는 이유**: 식별자 조인에서 퍼지 매칭은
> **오결합 = 타인의 데이터가 붙는 사고**로 직결된다. 이득 대비 위험이 크다.

## 3. 저장 구조

| 대상 | 저장소 | 근거 |
|---|---|---|
| 관계 정의 (`FormLink`) | **PostgreSQL** | 트랜잭션·권한·감사가 필요한 거버넌스 자산. FormRegistry와 같은 계층 |
| 매칭 인스턴스(실제 연결된 레코드 쌍) | **저장하지 않고 질의 시 계산** | ★ 사전 계산해 저장하면 그것이 곧 **마스킹을 우회하는 비마스킹 사본**이 되어 S6를 정면으로 위반한다. 성능 문제가 실제로 발생하면 그때 **정규화된 키의 해시 인덱스**만 두고 원본 값은 절대 복제하지 않는다 |
| 감사 로그 | 기존 `AuditLog` | S7 |

### `FormLink` 스키마 초안

```prisma
model FormLink {
  id            String  @id @default(cuid())
  leftFormId    String
  leftFieldId   String
  rightFormId   String
  rightFieldId  String

  name          String   // "이 직원이 제출한 만족도조사"
  reverseName   String   // "이 응답을 제출한 직원"
  cardinality   String   // ONE_TO_ONE | ONE_TO_MANY | MANY_TO_ONE | MANY_TO_MANY

  /// 정규화 규칙 (trim/stripSeparator/lowercase/stripLeadingZero/nfc ...)
  normalization Json

  /// 개인식별자 기반 여부 — true면 S2(자격) + S9(승인) 적용 대상
  isPersonalKey Boolean @default(false)

  visibility    String  @default("PRIVATE") // PRIVATE | PENDING | SHARED
  approvedBy    String?
  approvedAt    DateTime?

  createdBy     String
  createdAt     DateTime @default(now())
  description   String?
}
```

## 4. 2단계 이후 (참고 — MVP 승인 후 별도 논의)

- **자동 관계 발견**: 필드 프로파일 사전 계산(타입·포맷 시그니처·고유값 수·MinHash 스케치)
  → LSH로 후보 생성 → 상위 후보만 정밀 계산. 전수 비교를 피하는 것이 핵심.
  결과는 **"제안"으로만** 띄우고 자동 확정하지 않는다. [무시] 이력을 학습해 재제안 억제.
- **한국어 필드명 동의어 사전**: 사번=사원번호=직원번호=EMP_NO. 한국어 환경에서
  필드명 유사도는 가장 약한 신호라 사전 없이는 실용성이 낮다. 대신 **값 포맷 시그니처**
  (전화번호/이메일/사업자번호 패턴)가 훨씬 강력하다.
- **양식지-양식지 스키마 그래프 뷰** (Power BI Model view 형태)
- **인스턴스 그래프 + Search Around** (Foundry Vertex): 홉을 패널에서 조립 후 일괄 실행.
  **홉 상한 3단계**, 각 홉마다 k-익명성 체크 — 홉을 거칠수록 결과가 좁아져 재식별 위험이
  급증하므로 k 미만이 되는 홉에서 **탐색 중단 + 사유 표시**.
- **논리 엔티티 도입** (Foundry Object Type): "사원"·"고객" 같은 엔티티를 정의하고 양식지
  문항을 매핑 → N개 양식지의 N² 관계가 N개 매핑으로 축소된다.
- **사용 이력 기반 추천** (Alation QLI 패턴): 사용자들이 실제로 만든 링크를 학습.
  콜드스타트 이후 가장 정밀도 높은 신호.

## 5. 확인이 필요한 결정 사항

1. **k 임계값 기본값**: 5로 할지 10으로 할지 (민감 데이터는 10 권장)
2. **연결 테스트 권한 범위**: 본인 소유 양식지끼리만 테스트 가능하게 할지,
   공유 승인받은 양식지도 포함할지
3. **개인식별자 판정 방식**: 필드에 "개인식별자" 태그를 제작자가 직접 달게 할지,
   값 포맷(전화번호/이메일 패턴)으로 시스템이 자동 판정할지
4. **MVP 범위 확정**: 위 2장(테스트 + 정의 + 트리 뷰 탐색)으로 1차를 끊는 것이 맞는지
