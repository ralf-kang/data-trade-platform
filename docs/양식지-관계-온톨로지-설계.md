# 양식지 간 관계(온톨로지) 기능 설계

> 상태: **설계 확정** (§5 결정 사항 반영 완료) — 구현 착수 지시 대기
> 작성 배경: 기존 `/super-admin/data-map`(시스템 테이블 ERD)은 요구사항을 잘못 해석한 것이다.
> 요구는 "**양식지와 양식지 사이에 같은 키값이 들어왔을 때, 사용자가 스스로 FK로 엮어보고
> 확장해 나갈 수 있는지 테스트·확인**"하는 온톨로지형 기능이다. 이 문서는 그 재설계다.

---

## 0. 한 줄 정의

> 서로 다른 양식지가 **같은 값을 담은 문항**을 갖고 있는지 사용자가 직접 **테스트**하고,
> 그 문항 쌍을 **관계로 선언**한 뒤, 응답 레코드에서 **한 홉씩 타고 넘어가며 탐색**하는 기능.

「시스템의 DB 스키마」가 아니라 「사용자가 수집한 데이터끼리의 의미적 연결」이 대상이다.

> **`/super-admin/data-map`(시스템 테이블 ERD)은 그대로 둔다.** 그 화면은 이 플랫폼 자체의
> Postgres 스키마(User/FormRegistry/Campaign 등 실제 FK)를 보여주는 별개의 유틸리티이고,
> 이 문서가 다루는 "사용자가 수집한 양식지 데이터끼리의 연결"과는 목적이 다르다.
> 두 화면은 이름이 비슷해 보여도 **서로 다른 대상을 다루는 별개 기능으로 공존**한다.

---

## 1. 이 기능이 위험한 이유 — 먼저 정리하고 시작한다

**이 기능은 구조적으로 재식별(re-identification) 도구다.** 마스킹 계층이 막으려던 바로 그
행위를 기능으로 제공하는 것이므로, 프라이버시 설계를 나중에 덧붙일 수 없다.

- 조인 키로 가장 쓸모 있는 필드(사번·전화번호·이메일)가 곧 **직접 식별자**다.
  각각으로는 안전하던 두 양식지가, 연결되는 순간 **결합된 하나의 프로파일**이 된다.
- k-익명성은 원래 "고립된 단일 테이블"을 전제로 설계된 개념이라 **외부 데이터셋과의 결합을
  견디도록 만들어지지 않았다.** 각각 안전해 보이던 준식별자도 교차 참조되면 유일해진다.
- 더 교묘한 경로: **연결 테스트 화면 자체가 정보 누출 채널**이다.
  "사번 12345로 필터 → 매칭 1건"을 확인하는 것만으로 k=1이 드러난다.
  즉 결과 레코드를 안 보여줘도, **통계만으로 재식별이 가능하다.**

### 필수 안전장치 (MVP 첫 커밋부터 포함)

| # | 안전장치 | 내용 |
|---|---|---|
| **S1** | **익명 문항 원천 배제** | `anonymous: true` 필드는 관계 정의 대상에서 **드롭다운에 나타나지도 않게** 하고 API에서도 거부. 익명 문항은 응답자와 분리 저장되므로 연결은 곧 익명성 파기다. **예외 없음.** |
| **S2** | ~~개인식별자 연결에는 개인정보 취급 자격 필요~~ → **기능 전체가 슈퍼관리자 전용이므로 단순화됨** | §5-2 결정에 따라 이 기능은 슈퍼관리자만 쓸 수 있고, 슈퍼관리자는 이미 개인정보 취급자로 간주된다. 따라서 별도의 `AuthorAuthorization` 신청·승인 절차는 **불필요** — 접근 통제는 `requireSuperAdmin()` 하나로 충분하다. 일반 관리자에게 이 기능을 열어주는 순간 이 항목은 반드시 재도입해야 한다 |
| **S3** | **모든 통계에 k-익명성 하한** | 매치 건수·매치율·샘플값 등 **발견 단계의 모든 출력**에 최소 집계 크기 **k=5**(§5-1 확정) 강제. k 미만이면 정확한 수치 대신 "k 미만"으로 대체 |
| **S4** | **기본은 집계 전용** | 연결 결과를 원본 레코드가 아니라 **건수·분포**로 먼저 보여준다. 원본 열람은 별도 권한 + 별도 동작 |
| **S5** | **개인식별자 태그 컬럼은 블러 처리** | 어떤 컬럼이 "개인식별자"인지는 **제작자가 폼 빌더에서 사전에 태그**한다(§5-3, `FormField.personalIdentifier`). 미태그 필드는 개인식별자로 간주하지 않는다. 태그된 컬럼이 미리보기·샘플값에 등장하면 부분 마스킹(`010-****-5678`)만 제공 |
| **S6** | **마스킹 상태 전파** | 연결 결과의 마스킹 수준은 **양쪽 중 더 엄격한 쪽**을 따른다. "마스킹된 양식 + 안 된 양식"을 이어 붙여 마스킹을 무력화할 수 없게. k=1 전면 마스킹 레코드는 연결 결과에서도 계속 제외 |
| **S7** | **감사 로그 — 테스트 시도까지 기록** | 누가/언제/어떤 양식지 쌍을/어떤 키로 테스트했는지, 결과 건수까지. **연결을 만들지 않고 "테스트만" 한 것도 로깅.** 재식별 시도 탐지의 유일한 방어선 |
| **S8** | **레이트 리밋 + 반복 질의 탐지** | 키 값을 바꿔가며 반복 조회하는 차분 공격 패턴 차단 |
| **S9** | ~~링크 기본 비공개, 승인 후 공유~~ → **현재는 대상이 없어 보류** | §5-2 결정상 슈퍼관리자만 이 기능을 쓰므로 "누구에게 공유·승인받는가"라는 질문이 아직 성립하지 않는다. **일반 관리자에게 조회 권한을 여는 시점에 반드시 재설계**할 것 |

## 2. MVP (1단계) — 화면 설계

### 2-1. 관계 관리 화면 `/super-admin/form-links`

> §5-2 결정에 따라 **이 기능 전체가 슈퍼관리자 전용**이다. 일반 관리자(양식 제작자)는
> 접근할 수 없다. 라우트도 `/admin/...`이 아니라 슈퍼관리자 영역(`/super-admin/...`)에 둔다.

양식지 쌍 목록 + [새 관계 만들기]. 각 행: 좌측 양식·문항 → 우측 양식·문항, 매치율, 소유자
(=만든 슈퍼관리자). 슈퍼관리자는 **본인 소유 여부와 무관하게 모든 양식지**를 대상으로
관계를 만들 수 있다(§5-2).

> 승인·공유 상태(초안/승인대기/공유됨)는 **MVP에서 제외**한다. 이 기능을 쓸 수 있는 사람이
> 슈퍼관리자뿐이라 "누구에게 공유·승인받는가"라는 질문 자체가 아직 성립하지 않는다
> (S9 참조 — 일반 관리자에게 공개하는 흐름이 생기면 그때 재도입).

### 2-2. ★ 관계 캔버스 — **이 기능의 핵심. 여기 품질이 전부다**

> 애초 초안의 "연결 테스트 화면"(드롭다운 2개)과 "탐색 UI(트리 뷰)"를 하나의 **캔버스**로
> 합친다. Power BI Model view처럼 **양식지-양식지 스키마 그래프를 직접 조립하는 화면**이며,
> 이로써 원래 2단계로 미뤄뒀던 "양식지-양식지 스키마 그래프 뷰"가 MVP에 바로 포함된다.

```
┌─ 툴박스 ──────┐  ┌─ 캔버스 ─────────────────────────────────────────────┐
│ 🔍 양식지 검색 │  │  ┌─ 2024 만족도조사 ──┐      ┌─ 온보딩 피드백 ──┐      │
│               │  │  │ 사번        [펼침]●─┼──94%──┼─●[펼침] 사원번호│      │
│ □ 만족도조사   │  │  │ 연락처      [펼침]●─┼─      │  부서            │      │
│ □ 온보딩 피드백│→ │  │ 개선 사항         │      │  성함            │      │
│ □ 워크샵 신청  │  │  └───────────────────┘      └──────────────────┘      │
│ ...(드래그)    │  │                                                       │
└───────────────┘  └───────────────────────────────────────────────────────┘
```

**조작 흐름**
1. 좌측 툴박스에서 양식지를 검색해 캔버스로 **드래그앤드롭** → 그 양식지가 **카드(노드)** 로
   놓이고, 카드 안에는 문항(컴포넌트) 목록이 나열된다(익명 문항은 S1에 따라 목록에서 제외).
2. 카드 안의 문항을 **여러 개 클릭해 각각 "펼침" 상태로** 만든다 — 펼친 문항은 카드에서
   컬럼 형태로 도드라져 나오며, **연결의 시작/끝점**이 된다. 한 카드에서 여러 문항을 동시에
   펼쳐둘 수 있고(예: "사번"과 "연락처" 둘 다), 캔버스에 올려진 카드가 여러 장이면 그만큼
   여러 컬럼을 동시에 펼쳐놓고 비교할 수 있다.
3. 펼쳐진 컬럼끼리 **드래그로 연결**하면 그 즉시 후보 관계선(엣지)이 생기고 **곧바로
   "연결 테스트"가 실행**되어 엣지 위에 **매치율 배지**가 표시된다. 별도의 "테스트" 버튼을
   누를 필요가 없다. 한 화면에서 **여러 쌍을 동시에 연결**해두고 비교할 수 있다
   (예: "사번↔사원번호" 엣지와 "연락처↔휴대폰번호" 엣지를 나란히 두고 매치율 비교).
4. **엣지를 클릭**하면 우측에 **인스펙터 패널**이 열린다 (Power BI의 "관계선 클릭 → 속성
   패널 편집" 패턴). 패널 내용은 기존 "연결 테스트" 결과와 동일:

   ```
   ┌─ 인스펙터: 사번 ↔ 사원번호 ────────────────────────────┐
   │  매치율   좌측 기준 94%  │  우측 기준 62%               │
   │           (호버 시 계산식과 원시 수치 노출)              │
   │                                                        │
   │  좌측 고유값 128 │ 우측 고유값 194 │ 교집합 120          │
   │  좌측에만 8건    │ 우측에만 74건                        │
   │                                                        │
   │  → 우측 문항이 100% 고유합니다. N:1 관계를 제안합니다.   │
   │                                                        │
   │  정규화 규칙 (켤 때마다 매치율 실시간 재계산)             │
   │   ☑ 앞뒤/중복 공백 제거        62% → 94%                │
   │   ☐ 하이픈·구분자 제거                                  │
   │   ☐ 대소문자 통일 · ☐ 선행 0 무시 · ☐ 전각/반각          │
   │   ☐ 한글 자모 정규화(NFC)   ← macOS/Windows 혼재 시 필수 │
   │                                                        │
   │  [관계로 저장]  이름/역방향 이름 입력 (§2-3)             │
   └────────────────────────────────────────────────────────┘
   ```

5. **엣지(또는 노드) 호버** 시 팝오버로 **최근 레코드 5건 이하**를 미리보기 — 이는
   "구조가 맞는지 확인"용이지 **레코드 열람용이 아니다.** 전체 레코드 리스팅/드릴다운은
   **퓨처워크**(§4)로 명시 유지한다.

   **팝오버 구조 (★ 1장의 "구조적 재식별 도구가 되지 않도록" 사전 방지 장치)**
   - 5건 이하 표시. **결과가 k(=5) 미만이면 아예 표시하지 않는다** (S3·S4 적용).
   - **개인식별자 태그가 붙은 컬럼(§5-3)이 미리보기에 포함되면 값을 블러 처리**한다
     (예: `010-****-5678`). 태그되지 않은 컬럼은 그대로 표시.
   - **익명 응답 버퍼(`AnonymousResponseBuffer`)에 저장된 레코드는 미리보기 대상에서
     원천 제외**한다 — 익명 문항 자체를 링크 대상에서 빼는 S1과 별개로, "이 응답 자체가
     익명으로 분리 저장된 레코드"인 경우까지 이중으로 막는다.
   - 이 블러·제외는 **열람자의 권한과 무관하게 항상 적용**되는 구조적 안전장치다 —
     매치 건수·샘플값 노출 자체가 재식별 채널이라는 1장의 문제의식을 팝오버에도 그대로
     적용한 것이다. **이것이 개인정보 취급 자격 문제인 것은 아니다** — 이 기능 자체가
     슈퍼관리자 전용(§5-2)이고 슈퍼관리자는 이미 개인정보 취급자로 간주되므로, 블러는
     "권한이 없어서"가 아니라 "구조적으로 항상 그렇게 동작하도록" 설계된 것이다.

**설계 근거 (벤치마킹)**
- 카드+엣지 캔버스 = **Power BI Model view / Tableau 논리 레이어**. 노드를 드래그해 배치하고
  엣지를 클릭해 속성을 편집하는 조작 자체가 "스키마를 조립한다"는 감각을 준다.
- 매치율 배지 + 호버 계산식 노출 = **Trifacta**. 블랙박스로 점수만 던지면 신뢰를 못 얻는다.
- 좌/우 **양방향** 포함률을 둘 다 보여주는 이유: 어느 쪽이 FK이고 어느 쪽이 PK인지
  **방향 판정에 결정적**이기 때문. 한쪽만 보면 크기 차이가 큰 경우 오판한다.
- 좌측만/우측만 건수 = **Alteryx의 J·L·R 3앵커 Venn**을 숫자로 축약한 것.
- 유일성 비율로 카디널리티 자동 제안 = **Power BI**. 단 자동 확정하지 않고 **제안만** 한다
  (Power BI도 확신이 낮으면 아예 관계를 만들지 않는 보수적 정책).
- 정규화 효과를 실시간으로 보여주는 것이 사용자에게 가장 설득력 있다.
- **한글 자모 정규화(NFC)** 는 눈에는 같아 보이는데 절대 매칭 안 되는 대표 함정이라 필수.
- 호버 팝오버 5건 제한 = **Foundry Object Explorer**가 "구조 확인"과 "레코드 열람"을 분리하는
  것과 같은 사상 — 캔버스는 구조를 조립하는 화면이지 데이터를 브라우징하는 화면이 아니다.

**여기에 S3·S5 적용**: 교집합이 k 미만이면 수치 대신 "k 미만" 표기, 샘플값은 마스킹.

### 2-3. 관계 정의 시 입력 항목

| 항목 | 필수 | 비고 |
|---|---|---|
| 좌/우 양식지 + 문항 | ✅ | |
| **관계 이름** | ✅ | 업무 언어로. 예: "이 직원이 제출한 만족도조사" |
| **역방향 이름** | ✅ | 예: "이 응답을 제출한 직원". **Foundry는 양쪽 이름을 한 정의 안에서 필수 입력**받는다 |
| 카디널리티 | ✅(자동 제안) | 1:1 / 1:N / N:1 / N:N |
| 정규화 규칙 | ✅ | 위 토글 상태 |
| 설명·근거 메모 | 권장 | 거버넌스·감사용 |

> **동일한 두 양식지 사이에 여러 관계가 존재할 수 있다** (예: "작성자 사번" 관계와
> "대상자 사번" 관계). 따라서 관계마다 고유 ID가 필요하다 (Foundry의 API name 개념).

### 2-4. 레코드 단위 탐색(트리 뷰) — **2단계로 유지**

응답 레코드 상세 화면 하단에 "연결된 데이터" 섹션을 펼쳐 **hop-by-hop**으로 순회하는
트리 뷰(Foundry Object Explorer의 Links 위젯/nested links 패턴)는 **여전히 2단계 이후**다.

```
▼ 연결된 데이터
   ▼ 이 직원이 제출한 만족도조사 (3건)
        • SUB-001  2026-07-27  만족도 4점    → [열기]
        • SUB-014  2026-05-02  만족도 3점    → [열기]
   ▶ 이 직원의 워크샵 신청 (1건)
```

2-2의 캔버스가 "**어떤 관계가 존재하는가**"(스키마 조립 + 구조 확인용 5건 미리보기)를
다룬다면, 이 트리 뷰는 "**그 관계를 타고 실제 레코드를 넘나드는 것**"을 다룬다 — 지금
MVP는 전자만 포함하고, 후자(레코드 다건 리스팅, 다단계 hop, Search Around)는 미룬다.

### 2-5. 최초 이용 안내 · 동의

- **최초 진입 시 1회만**: 캔버스 화면에 처음 들어오면 재식별 위험 요약 + 확인 모달을
  노출한다. 확인 후에는 **화면마다 반복 노출하지 않는다.**
- **재열람**: 사용자가 원하면 개인 설정 화면에서 토글로 안내 모달을 다시 볼 수 있다.
- **관리자 조회**: 슈퍼관리자는 "옵션 상세화면"에서 **각 사용자의 동의 시각·상태를 지속적으로
  조회**할 수 있어야 한다. 기존 `privacyWarningAck`(§조합 위험 경고) + `AuditLog` 패턴을
  그대로 재사용한다 — 별도 개념을 새로 만들지 않는다.
  - `User.ontologyConsentAt DateTime?` 필드(또는 별도 동의 로그 테이블)를 추가하고,
    동의/재열람 모두 `AuditLog`에 기록한다(`ONTOLOGY_CONSENT_ACK` 등).
  - 이 동의는 **"슈퍼관리자만 쓸 수 있다"(S2·§5-2)는 접근 통제와는 별개**다 — 접근 통제는
    "누가 이 기능을 쓸 수 있는가"를 판정하고, 이 동의는 그 사람이 **"재식별 위험을
    인지했는가"**를 확인한다. 캔버스 화면에 진입하는 슈퍼관리자 본인에게도 그대로 적용된다.

### 2-6. MVP에서 의도적으로 제외

자동 관계 발견 / 복합 키 / 퍼지 매칭 / 필터 전파 방향 / 레코드 단위 다건 탐색(트리 뷰,
hop-by-hop, Search Around)

> **퍼지 매칭을 MVP에서 빼는 이유**: 식별자 조인에서 퍼지 매칭은
> **오결합 = 타인의 데이터가 붙는 사고**로 직결된다. 이득 대비 위험이 크다.

model FormLink {

  leftFormId    String
  leftFieldId   String
  rightFormId   String

  cardinality   String   // ONE_TO_ONE | ONE_TO_MANY | MANY_TO_ONE | MANY_TO_MANY

## 4. 2단계 이후 (참고 — MVP 승인 후 별도 논의)

- **자동 관계 발견**: 필드 프로파일 사전 계산(타입·포맷 시그니처·고유값 수·MinHash 스케치)
  → LSH로 후보 생성 → 상위 후보만 정밀 계산. 전수 비교를 피하는 것이 핵심.
  결과는 **"제안"으로만** 띄우고 자동 확정하지 않는다. [무시] 이력을 학습해 재제안 억제.
- **한국어 필드명 동의어 사전**: 사번=사원번호=직원번호=EMP_NO. 한국어 환경에서
  필드명 유사도는 가장 약한 신호라 사전 없이는 실용성이 낮다. 대신 **값 포맷 시그니처**
  (전화번호/이메일/사업자번호 패턴)가 훨씬 강력하다.
- **레코드 단위 다건 탐색 + Search Around** (Foundry Vertex, §2-4): 트리 뷰에서 홉을 패널에
  조립 후 일괄 실행.
  **홉 상한 3단계**, 각 홉마다 k-익명성 체크 — 홉을 거칠수록 결과가 좁아져 재식별 위험이
  급증하므로 k 미만이 되는 홉에서 **탐색 중단 + 사유 표시**.
- **논리 엔티티 도입** (Foundry Object Type): "사원"·"고객" 같은 엔티티를 정의하고 양식지
  문항을 매핑 → N개 양식지의 N² 관계가 N개 매핑으로 축소된다.
- **사용 이력 기반 추천** (Alation QLI 패턴): 사용자들이 실제로 만든 링크를 학습.
  콜드스타트 이후 가장 정밀도 높은 신호.

## 5. 결정 사항 (확정)

### 5-1. k 임계값

**5로 확정.** S3의 모든 하한값은 k=5를 쓴다.

### 5-2. 연결 테스트 권한 범위

**슈퍼관리자만 이 기능을 사용한다.** 일반 관리자(양식 제작자)는 접근할 수 없다.
슈퍼관리자는 **모든 양식지를 확인할 수 있는 권한**을 가지므로, 본인 소유 여부와 무관하게
아무 양식지 쌍이나 골라 연결을 테스트할 수 있다.

- 접근 통제는 `requireSuperAdmin()` 하나로 충분 (S2 참조 — 별도 자격 신청 불필요)
- 라우트: `/super-admin/form-links`, `/super-admin/form-links/canvas`(§2-1)
- 승인·공유 워크플로(S9)는 대상(일반 관리자)이 아직 없으므로 **보류**. 일반 관리자에게
  열어주는 시점에 반드시 재설계

### 5-3. 개인식별자 판정 방식

**제작자가 폼 빌더에서 사전에 태그한다. 태그되지 않은 필드는 개인식별자로 간주하지 않는다.**
값 포맷(전화번호/이메일 패턴 등)으로 시스템이 자동 판정하지 않는다 — 오탐(예: 사번을
전화번호로 오인)을 피하고, "이 필드가 무엇을 담는지"를 가장 잘 아는 제작자의 판단을
신뢰한다.

- 스키마: `FormField`에 `personalIdentifier?: boolean` 추가 (FormBuilder에서 문항별 토글)
- 이 태그가 곧 S5(블러 처리 대상)와 `FormLink.isPersonalKey`(§3) 판정 기준이 된다
- 개인정보 컴포넌트(예: `privacy-consent`)와는 별개 개념 — 자유서술/단답형/정규식 등
  어떤 문항이든 제작자가 "이건 개인식별자다"라고 표시할 수 있다

### 5-4. MVP 범위

**확정.** §2장(관계 캔버스 + 관계 정의 + 최초 이용 동의)으로 1차를 끊고, 레코드 단위
트리 뷰 탐색(§2-4)은 2단계로 미룬다.
