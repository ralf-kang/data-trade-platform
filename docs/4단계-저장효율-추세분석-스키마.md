# 4단계 — 저장 효율(Current+History)과 추세 분석 스키마 명세

> [플랫폼 재설계 제안](./플랫폼-재설계-제안.md) §4-2 / §10의 구현 명세.
> [3단계 회차](./3단계-회차-반복수집-스키마.md)가 선행되어야 합니다 — 회차가 곧 시계열 축이기 때문입니다.

---

## 1. 범위

| 포함 | 제외 |
|---|---|
| `current_records` / `record_history` 분리 | 품질 점수 — 5단계 |
| 변경분(delta) 저장 + **시점 복원** | 보상 — 7·8단계 |
| 첨부파일 중복 제거 | |
| ES ILM(인덱스 수명주기) | |
| 회차 비교·시계열·코호트 분석 | |

## 2. 문제 정의 — 무엇이 실제로 비효율인가

먼저 정직하게 짚습니다. **필드 20개짜리 텍스트 양식이라면 회차마다 통째로 저장해도
저장량 자체는 큰 문제가 아닙니다.** 임직원 500명 × 분기 4회 = 연 2,000건 수준이면
전체 복사본을 쌓아도 수십 MB입니다.

실제로 문제가 되는 것은 셋입니다.

| 실제 비효율 | 규모 |
|---|---|
| **첨부파일·이미지의 반복 저장** | 🔴 가장 큼 — 자격증 사본 2MB × 500명 × 8회차 = 8GB |
| **"현재 상태" 조회 비용** | 전체 스캔 후 최신분 선별 → 회차가 쌓일수록 선형 악화 |
| **"이 값이 언제 바뀌었나" 추적 불가** | 지금은 전체 문서를 비교해야 알 수 있음 |

> 💡 그래서 이 단계의 핵심 가치는 **바이트 절감보다 ①첨부 중복 제거 ②조회 성능
> ③변경 추적**입니다. 저장량 절감은 첨부가 있는 양식에서만 극적으로 나타납니다.
> 텍스트 위주 양식이라면 delta 저장을 무리하게 적용하지 않는 편이 나을 수 있습니다(§6 참고).

## 3. 구조

```
webreport-submissions        (기존) 회차별 원본 제출 — 감사·법적 근거로 보존
        │
        ├─→ webreport-current-records    respondent × form 당 1건 = "지금의 상태"
        │                                 조회의 대부분이 여기서 끝난다
        │
        └─→ webreport-record-history-*   변경된 필드만 = "언제 무엇이 어떻게"
                                          추세·감사 추적
```

> ⚠️ **원본 제출 문서는 지우지 마세요.** current/history는 원본에서 파생된
> **가공물(derived)** 입니다. 파생만 남기고 원본을 지우면 복원 로직에 버그가 있을 때
> 되돌릴 방법이 없고, 데이터베이스제작자 권리·감사 대응의 근거도 사라집니다.
> 저장 비용은 §8 ILM으로 낮추는 것이 맞습니다.

## 4. `current_records` — 현재 상태

```ts
export interface CurrentRecordDocument {
  /** 결정적 id: `${formId}__${respondentId}` — 갱신이 곧 덮어쓰기가 된다. */
  recordId: string;
  formId: string;
  respondentId: string;

  /** 전 회차에 걸쳐 병합된 최신 값. 조회는 대부분 이 필드만 본다. */
  data: Record<string, unknown>;

  /** 각 필드가 마지막으로 갱신된 회차 — "부서는 Q1 이후 안 바뀜"을 알 수 있다. */
  fieldUpdatedAt: Record<string, string>;

  lastCampaignId: string;
  lastSubmittedAt: string;
  revision: number;
  schemaVersion: number;

  /** 코호트 분석용 스냅샷 — 응답 시점의 소속. 이후 부서가 바뀌어도 당시 기준이 유지된다. */
  department: string | null;
  position: string | null;
}
```

```ts
const CURRENT_RECORD_MAPPING = {
  properties: {
    recordId:       { type: 'keyword' },
    formId:         { type: 'keyword' },
    respondentId:   { type: 'keyword' },
    lastCampaignId: { type: 'keyword' },
    lastSubmittedAt:{ type: 'date' },
    revision:       { type: 'integer' },
    schemaVersion:  { type: 'integer' },
    department:     { type: 'keyword' },
    position:       { type: 'keyword' },
    fieldUpdatedAt: { type: 'object', enabled: false }, // 색인 불필요, 저장만
    data:           { type: 'object', dynamic: true },
  },
} as const;
```

### `department` 스냅샷을 두는 이유

부서는 조직 개편으로 바뀝니다. `User.department`를 조인해 코호트를 만들면
**과거 데이터가 현재 소속 기준으로 재분류**되어, 지난 분기 보고서를 다시 뽑으면
숫자가 달라집니다. 응답 시점의 소속을 함께 박아두면 이 문제가 사라집니다.

## 5. `record_history` — 변경분만

```ts
export interface RecordHistoryDocument {
  historyId: string;       // 랜덤
  formId: string;
  respondentId: string;
  campaignId: string;
  submittedAt: string;
  revision: number;
  schemaVersion: number;

  /**
   * 변경된 필드만. from을 함께 남기는 이유는 이 문서 하나만 보고도
   * 무엇이 어떻게 바뀌었는지 읽을 수 있어야 감사에 쓸 수 있기 때문이다.
   * (from은 직전 이력에서 유도 가능하지만, 재생 없이 읽히는 편이 실무에 낫다.)
   */
  changes: Record<string, { from: unknown; to: unknown }>;

  /** 변경 없이 그대로 제출한 회차인지 — 5단계 신뢰성 신호로 쓰인다. */
  unchanged: boolean;

  /** 이 시점의 전체 상태를 담은 체크포인트 여부 — §6 참고. */
  checkpoint: boolean;
  /** checkpoint=true일 때만 채워지는 전체 스냅샷. */
  snapshot?: Record<string, unknown>;
}
```

인덱스는 **연 단위로 롤오버**합니다: `webreport-record-history-2026`.
ILM(§8)과 맞물려 오래된 연도를 warm 티어로 내리기 위함입니다.

### `unchanged` 플래그

3단계 Prefill에서 지적한 *"확인 없이 통과"* 를 잡는 자리입니다.
변경이 하나도 없으면 `changes: {}`, `unchanged: true`로 기록하고,
5단계 품질 점수에서 신뢰성 저하 신호로 사용합니다.

## 6. 🔴 시점 복원 — 가장 위험한 부분

delta 저장의 대가는 **"Q2 시점의 전체 현황"을 즉시 알 수 없다**는 것입니다.
분기 보고서를 다시 뽑는 일이 실제로 생기므로 복원 기능은 필수입니다.

```
복원(respondentId, targetCampaign):
  1. targetCampaign 이전(포함)의 가장 최근 checkpoint 문서를 찾는다
  2. 없으면 빈 상태에서 시작
  3. checkpoint 이후 ~ targetCampaign까지의 history를 시간순으로 changes.to 적용
  4. 결과 반환
```

### 체크포인트로 재생 비용을 묶습니다

체크포인트가 없으면 회차가 40개 쌓였을 때 40건을 재생해야 합니다.

| 정책 | 값 |
|---|---|
| 체크포인트 주기 | **N회차마다 1회** (기본 5) — `SystemConfig.historyCheckpointInterval` |
| 첫 제출 | 항상 체크포인트 (기준점) |
| 스키마 버전 변경 직후 | 항상 체크포인트 (해석 기준이 바뀌므로) |

### ⚠️ 반드시 함께 만들어야 할 것

> **복원 결과와 원본 제출 문서를 대조하는 검증 테스트.**
> `webreport-submissions`에 원본이 남아 있으므로, 임의 시점을 복원해
> 그 회차 원본과 일치하는지 자동으로 확인할 수 있습니다.
> **이 테스트 없이 delta 저장을 운영에 올리면 안 됩니다** — 여기서 버그가 나면
> 데이터가 조용히 틀리고, 발견 시점에는 이미 신뢰가 무너져 있습니다.

### 적용하지 않아도 되는 경우

**일회성 양식(회차 1개)에는 delta를 적용하지 마세요.** 이득이 없고 복잡도만 늘어납니다.
`FormRegistry`에 플래그를 둡니다.

```prisma
model FormRegistry {
  /// 반복 수집 양식에서만 Current+History 파생을 생성한다.
  /// 일회성 양식은 원본 제출만으로 충분하다.
  deriveRecords Boolean @default(false)
}
```

## 7. 첨부파일 중복 제거 — 저장 절감의 실체

자격증 사본·증빙 이미지는 회차가 바뀌어도 대개 그대로입니다.
매번 새로 저장하면 **저장량의 대부분을 첨부가 차지**하게 됩니다.

```prisma
/// 내용 주소(content-addressed) 첨부 저장소.
/// 같은 파일을 여러 회차·여러 응답자가 제출해도 실제 바이트는 한 벌만 보관한다.
model FileObject {
  /// SHA-256(파일 내용). 이것이 곧 파일의 정체성이다.
  contentHash String @id
  size        Int
  mimeType    String
  /// 실제 저장 경로(로컬 볼륨 또는 S3 호환). 온프레미스 전제로 기본은 볼륨 경로.
  storagePath String
  /// 참조 카운트. 0이 되어도 즉시 삭제하지 않고 유예 후 정리한다.
  refCount    Int      @default(0)
  createdAt   DateTime @default(now())

  references FileReference[]

  @@map("file_objects")
}

/// 어느 제출의 어느 필드가 어떤 파일을 가리키는지.
/// 원본 파일명은 응답자마다 다를 수 있으므로 여기에 둔다.
model FileReference {
  id           String     @id @default(cuid())
  contentHash  String
  file         FileObject @relation(fields: [contentHash], references: [contentHash])
  formId       String
  campaignId   String
  respondentId String
  fieldId      String
  originalName String
  createdAt    DateTime   @default(now())

  @@index([formId, respondentId])
  @@index([contentHash])
  @@map("file_references")
}
```

제출 데이터의 파일 필드에는 **해시만** 저장합니다.

```json
{ "f999-10": { "contentHash": "a3f1…", "name": "자격증.pdf", "size": 204800 } }
```

### 효과와 주의점

```
자격증 사본 2MB × 500명 × 8회차 = 8GB   →   변경 없으면 2MB × 500명 = 1GB
```

> ⚠️ **`refCount`가 0이 되어도 즉시 지우지 마세요.** 동시에 다른 제출이 같은 해시를
> 참조하려는 순간과 겹치면 파일이 사라집니다. 유예 기간(예: 30일)을 두고
> 배치로 정리하며, 삭제 전 참조를 재확인해야 합니다.

> ⚠️ **해시 충돌이 아니라 "같은 내용 = 같은 파일" 자체가 정보 노출입니다.**
> 두 응답자가 동일 해시를 가리키면 "둘이 같은 파일을 냈다"는 사실이 드러납니다.
> 익명 문항의 첨부에는 **중복 제거를 적용하지 마세요**(2단계 §7과 같은 맥락).

## 8. ILM — 인덱스 수명주기

```
webreport-record-history-2026   hot   (현재 연도)
webreport-record-history-2025   warm  (조회 빈도 낮음)
webreport-record-history-2024-  cold  또는 삭제 정책
```

| 단계 | 시점 | 조치 |
|---|---|---|
| hot | 현재 연도 | 기본 |
| warm | 1년 경과 | 샤드 병합(forcemerge), 복제본 축소 |
| cold | 3년 경과 | 읽기 전용 전환 |
| delete | 보존기간 경과 | ⚠️ 아래 참조 |

> 🔴 **삭제 정책은 개인정보 보유기간과 반드시 연동해야 합니다.**
> ILM을 "저장 절감"으로만 설정하면 법정 보존 의무가 있는 데이터를 지우거나,
> 반대로 파기해야 할 개인정보를 무기한 보관하게 됩니다.
> 보유기간은 양식 단위로 정의하고(§10), ILM은 그 정책을 집행하는 수단이어야 합니다.

> ℹ️ ILM과 hot/warm/cold 티어는 Elasticsearch **Basic 라이선스에서 사용 가능**합니다.
> 다만 frozen 티어(searchable snapshot)는 상위 라이선스가 필요하므로,
> 온프레미스 Basic 환경에서는 cold까지만 설계하세요.

## 9. 추세 분석

### 제공 화면

| 분석 | 데이터 출처 |
|---|---|
| **회차 비교** — 같은 문항의 분포 변화 | history + 회차별 집계 |
| **필드 시계열** — 수치 필드 추세선 | history의 `changes` |
| **개인 이력** — 내 값의 변화 | history(respondentId 필터) |
| **코호트** — 부서·직급별 추이 | current/history의 department 스냅샷 |
| **미갱신 현황** — 오래된 값 | current의 `fieldUpdatedAt` |

### 🔴 스키마 버전이 다른 회차를 그냥 이어붙이면 안 됩니다

3단계에서 회차에 `schemaVersion`을 고정한 이유가 여기서 회수됩니다.

```
⚠ Q1~Q2는 5점 척도, Q3부터 7점 척도입니다.
   구간을 나눠 보시거나 정규화 후 비교하세요.   [구간 분리] [정규화 비교]
```

버전이 다른 구간을 자동으로 정규화해 한 선으로 그리면 **없는 추세를 만들어냅니다.**
경고를 띄우고 사용자가 선택하게 해야 합니다.

### 대표성 경고와 연결

[데이터 품질 문서](./데이터품질-검증구간-설계.md) §2-7의 ⑤활용 시점 경고가
이 화면에 붙습니다.

```
⚠ 이 추세로 "전사 만족도 개선"을 말하기 어렵습니다
   Q3 응답률 32% · 개발본부 편중(68%) · 생산직 3건
```

## 10. 익명성·회차와의 상호작용

| 항목 | 처리 |
|---|---|
| 익명 문항 | **current/history를 만들지 않음** — 개인 추세가 곧 재식별 |
| 익명 문항 회차 비교 | 회차별 **집계값만** 비교 (k-임계값 충족 시) |
| 익명 첨부 | 중복 제거 미적용 (§7) |
| 회차별 코호트 | 응답 시점 department 스냅샷 사용 |

```prisma
model FormRegistry {
  /// 이 양식 데이터의 보유기간(개월). ILM 삭제 정책과 정보주체 파기 요구의 기준.
  retentionMonths Int?
}
```

## 11. 마이그레이션

```
① current/history 인덱스 + ILM 정책 생성
② FileObject / FileReference 테이블 생성
③ deriveRecords=true인 양식에 대해 기존 제출을 회차 순으로 재생하여
   current_records + record_history 생성 (첫 건은 checkpoint)
④ 기존 첨부를 해시 계산 후 FileObject로 이관, 제출 문서의 파일 필드를 해시 참조로 치환
⑤ 애플리케이션 배포
```

> ⚠️ ③④는 **원본을 건드리지 않는 파생 생성**이므로 실패해도 되돌리기 쉽습니다.
> 다만 ④에서 제출 문서를 치환하는 부분은 원본 수정이므로, **치환 전 인덱스 스냅샷**을
> 반드시 확보하세요.

기존 데이터에는 `respondentId`가 없는 제출(1단계 이전)이 섞여 있습니다.
**이들은 current/history를 만들 수 없으므로 건너뛰고**, 해당 양식의 분석 화면에
*"N건은 응답자 식별 이전 데이터로 추세에서 제외됨"* 을 표시합니다.

| `src/lib/services/fileService.ts` | **신규** — 해시 기반 저장·참조·GC |
| `src/lib/services/submissionService.ts` | 제출 후 파생 생성 훅 |
| `src/lib/services/analyticsService.ts` | **신규** — 회차 비교·시계열·코호트 |
| `src/app/(admin-portal)/admin/forms/[formId]/trends/` | **신규 화면** |
| `prisma/schema.prisma` | FileObject, FileReference, 플래그 3종 |

### 파생 생성은 동기인가 비동기인가

| 방식 | 평가 |
|---|---|
| 제출 트랜잭션 내 동기 생성 | ✅ 권장 — 일관성이 단순하고, 건당 비용이 작다 |
| 큐 기반 비동기 | 대량 API 입력(bulk)에서만 고려. 파생 지연 상태 표시 필요 |

bulk 입력(v1 API)은 1,000건이 한 번에 들어오므로, **bulk 경로만 배치 생성**으로
분리하는 편이 안전합니다.

## 13. 완료 기준 (검증 시나리오)

| # | 시나리오 | 기대 |
|---|---|---|
| 1 | 첫 제출 | ✅ current 1건 + history(checkpoint) 1건 |
| 2 | 두 번째 회차, 1개 필드만 변경 | ✅ history.changes에 **1개 필드만** |
| 3 | 변경 없이 제출 | ✅ `unchanged: true`, changes 비어 있음 |
| 4 | current 조회 | ✅ 회차 수와 무관하게 단건 조회 |
| 5 | **임의 시점 복원 vs 원본 대조** | ✅ **완전 일치** — 가장 중요 |
| 6 | 체크포인트 주기 도달 | ✅ snapshot 포함 문서 생성 |
| 7 | 스키마 버전 변경 직후 제출 | ✅ 체크포인트 생성 |
| 8 | 같은 파일 재제출 | ✅ FileObject 1건, refCount 증가 |
| 9 | 첨부 삭제 후 refCount 0 | ✅ 즉시 삭제되지 않음(유예) |
| 10 | 익명 문항 | ✅ current/history **미생성** |
| 11 | 버전이 다른 회차 비교 | ✅ 경고 표시 |
| 12 | 부서 변경 후 과거 회차 조회 | ✅ **당시 부서**로 집계 |
| 13 | `deriveRecords=false` 양식 | ✅ 파생 미생성 |
| 14 | 1~3단계 회귀 | ✅ 전체 통과 |

## 14. 5단계와의 접점

- `record_history.unchanged` → 신뢰성 점수 입력값
- `current_records.fieldUpdatedAt` → **현재성·적시성 지표**의 직접 근거
  (*"6개월 이상 미갱신 38건"*)
- 회차별 품질 점수 추이 → history와 같은 시계열 축 사용
- `FileObject.size` 합계 → 양식별 저장 비용 가시화
