# 테넌트(부서) · 데이터 제공/거래 설계

> 상태: **설계 초안** — 구현 착수 전 검토 필요
> 작성 배경: `/super-admin`의 "데이터 거래 및 B2B 통계 (CRM)" 섹션은 현재 **하드코딩된 카드
> 2개와 동작하지 않는 버튼 3개**뿐이다. 백엔드·스키마·API가 전혀 없고, 거기 쓰인 "테넌트"는
> 실체 없는 라벨이다(`영업본부`/`인사팀` 문자열이 JSX에 박혀 있을 뿐이다).
> 이 문서는 그 자리를 실제로 채우기 위한 설계다.

> ⚠️ **법률 판단 주의**: 이 문서는 개인정보 보호법 조문을 근거로 설계를 전개하지만, 최종
> 적법성 판단은 법무·개인정보보호책임자의 검토를 받아야 한다. 특히 §1의 "내부 제공 vs
> 외부 제공" 구분은 기관의 법인격 구조에 따라 달라질 수 있다.

---

## 0. 한 줄 정의

> **부서(테넌트)가 수집한 데이터의 소유 주체를 명확히 하고, 그 데이터를 다른 부서나 외부
> 기관에 제공할 때 "동의받은 범위 안인지"를 시스템이 강제로 검증하는 기능.**

"거래"라는 말이 붙어 있지만, 이 기능의 본질은 **판매**가 아니라 **제공 통제**다.
과금·정산은 이 설계의 범위 밖이며(§8 참조), 그것 없이도 이 기능은 독립적으로 가치가 있다.

---

## 1. 시작 전에 — 이 기능은 법적으로 가장 위험한 지점이다

이 플랫폼에서 지금까지 만든 모든 개인정보 보호 장치(마스킹, k-익명성, 익명 문항 분리 저장,
동의서 컴포넌트)는 **데이터가 시스템 안에 머무는 것**을 전제로 한다. 데이터 제공은 그
전제를 깨는 **유일한 출구**다. 한 번 나간 데이터는 회수할 수 없다.

### 1-1. 내부 제공과 외부 제공은 법적 근거가 다르다

이 구분을 코드 레벨에서 섞으면 안 된다. 화면과 API가 하나여도 판정 로직은 분리해야 한다.

| 구분 | 상대 | 근거 조문 | 필요 조건 |
|---|---|---|---|
| **내부 부서 간** | 같은 기관의 다른 부서 | 제15조(수집 목적 내) 또는 **제18조**(목적 외 이용) | 수집 목적 범위 내면 추가 동의 불요. 목적을 벗어나면 제18조 요건 충족 필요 |
| **외부 기관** | 별개 법인격의 기관 | **제17조**(제3자 제공) | 수집 시점에 **그 제공받는 자를 특정해** 동의를 받았어야 함 |
| **익명 통계** | 내부·외부 무관 | **제58조의2**(익명정보) | 개인을 알아볼 수 없게 처리했다면 개인정보가 아니므로 동의 불요 |

> 🔴 **제17조 동의는 소급이 불가능하다.** 이미 수집을 마친 데이터에 대해 "이제 외부에
> 주기로 했으니 동의를 받자"는 성립하지 않는다. 동의는 **수집 시점에, 제공받는 자를
> 특정해서** 받았어야 한다. 이 사실이 아래 §3 설계 전체를 결정한다.

### 1-2. 그래서 현실적인 주력 경로는 "익명 통계 제공"이다

이 플랫폼에 이미 쌓인 양식지 대부분은 `consentMeta.thirdParty`가 비어 있다 —
즉 **원본 개인정보의 외부 제공 자격이 애초에 없다.** 이건 결함이 아니라 정상이다.

따라서 설계의 무게중심을 이렇게 잡는다:

- **주력**: 익명·집계 통계 제공 (제58조의2) — 동의 불요, k-임계값으로 재식별 차단
- **예외**: 원본/가명 데이터 제공 (제17조) — 수집 시점 동의가 있는 양식지에 **한해서만**,
  계약 단위로 승인·감사

거꾸로 설계하면(원본 제공을 기본으로 두고 동의를 나중에 확인) 반드시 사고가 난다.

## 2. 테넌트 = 사내 부서

### 2-1. 왜 `User.department` 문자열로는 부족한가

현재 부서 정보는 `User.department`(String?)에 LDAP 동기화로 들어온다. 이걸 그대로
소유 주체로 쓰면 세 가지가 깨진다.

1. **부서명이 바뀌면 과거 데이터의 소유권이 끊긴다.** "품질보증팀" → "품질기술본부"로
   개편되면 기존 양식지의 소유 부서를 잃는다.
2. **제작자가 퇴사·이동하면 데이터가 고아가 된다.** 현재 `FormRegistry.ownerId`는 개인이다.
   개인이 떠나면 그 데이터를 누가 승인·제공하는지 정해져 있지 않다.
3. **저작권법상 데이터베이스제작자와 어긋난다.** 제2조 20호의 "상당한 투자를 한 자"는
   개인이 아니라 **조직**이다. `DatabaseRegistration.producerName`이 이미 기관을 가리키는데,
   실제 소유 관계는 개인(ownerId)에만 있어 서로 맞지 않는다.

### 2-2. 모델

```
Tenant  (부서 = 테넌트)
  ├─ TenantDepartment  (LDAP 부서명 → 테넌트 매핑, N:1)
  └─ FormRegistry.tenantId  (이 양식지 데이터의 소유 부서)
```

- `Tenant`는 **안정 식별자**(`code`)를 갖는다. LDAP 부서명이 바뀌어도 `TenantDepartment`
  매핑만 갱신하면 되고, 이미 수집된 데이터의 소유권은 흔들리지 않는다.
- `FormRegistry.ownerId`(개인)는 **그대로 둔다**. 제작·편집 권한의 주체다.
  `tenantId`(부서)는 **데이터 소유·제공 승인의 주체**다. 둘은 다른 역할이므로 공존한다.
- 각 테넌트는 **개인정보보호 책임자**를 지정한다. 제공 승인은 이 사람만 할 수 있다 —
  양식지를 만든 사람이 자기 데이터를 자기가 외부에 넘기도록 두면 통제가 아니다.

### 2-3. 마이그레이션 — 기존 데이터를 어떻게 할 것인가

기존 `FormRegistry`에는 `tenantId`가 없다. 소유자의 `department`로 자동 추정해 채우되,
**추정에 실패한 것은 비워 두고 화면에 드러낸다.** 임의로 아무 테넌트에나 넣는 것이
데이터 소유권을 조용히 왜곡하는 최악의 선택이다. `tenantId`가 없는 양식지는
**제공 대상에서 자동 제외**된다(소유 주체가 불분명한 데이터를 내보낼 수는 없다).

## 3. 데이터 제공의 3가지 경로

세 경로는 **필요 조건이 다르므로 별도 타입으로 명시**한다. 하나의 "공유" 개념으로 뭉뚱그리면
가장 약한 조건이 전체에 적용되는 사고가 난다.

### 3-1. 경로 A — 내부 부서 간 제공 (제15조/제18조)

- 상대: 같은 기관의 다른 테넌트
- 인증: **LDAP 로그인 그대로** — 이미 있는 사용자다
- 기존 `ShareRequest`(사용자 간 공유 신청)가 이 경로의 원형이다. 다만 현재는 **개인 간**이라
  부서가 바뀌면 권한이 따라다니는 문제가 있다. **테넌트 간**으로 승격시킨다.
- 마스킹 계층은 그대로 적용된다 — 다른 부서 사람이라고 해서 마스킹이 풀리지 않는다.

### 3-2. 경로 B — 외부 기관 제공 (제17조)

- 상대: 별개 법인격의 외부 기관. **LDAP 계정이 없다.**
- **동의 게이트가 이 경로의 핵심이다** (§4)
- 인증: 계약에 종속된 API 키 (§5)
- 원본 식별 데이터가 나가는 유일한 경로이므로 승인·감사·기간 제한을 모두 건다.

### 3-3. 경로 C — 익명 통계 제공 (제58조의2)

- 상대: 내부·외부 무관
- 개인을 알아볼 수 없게 처리된 집계만 나간다 → 개인정보가 아니므로 **동의 불요**
- 이미 구현된 자산을 그대로 쓴다:
  - 워드클라우드의 **k=5 게이트**
  - 품질 대시보드의 **분포 통계**(평균/최소/최대/표준편차, 선택지 비율)
  - 익명 문항 인덱스(`webreport-anon-submissions`) — 애초에 응답자와 분리 저장됨
- **개별 레코드는 절대 나가지 않는다.** 집계 결과만 나간다. 이 제약이 곧 익명성의 근거다.

> 💡 실무적으로 "데이터 거래"의 대부분은 이 경로여야 한다. 개인정보를 원본으로 파는 것이
> 아니라, **분석 결과를 파는 것**이 법적으로도 사업적으로도 지속 가능하다.

## 4. 동의 기반 게이팅 — 이 설계의 핵심

### 4-1. 이미 있는 것을 근거로 쓴다

이번 세션에서 만든 `privacy-consent` 컴포넌트의 `consentMeta.thirdParty`가 정확히
제17조 고지 항목이다:

```ts
thirdParty: {
  recipient: string;        // 제공받는 자   ← 이 값이 게이트의 열쇠
  purpose: string;          // 제공 목적
  items: string;            // 제공 항목
  retentionPeriod: string;  // 보유·이용 기간
}
```

즉 **"이 양식지의 응답자들은 누구에게 데이터가 갈 것을 알고 동의했는가"가 이미 데이터로
남아 있다.** 제공 계약은 이 값과 대조되어야 한다.

### 4-2. 검증 규칙

외부 제공 계약(경로 B)을 **활성화하는 시점**에 대상 양식지 전부를 검사한다.
하나라도 통과하지 못하면 계약을 활성화할 수 없다.

| # | 검사 | 통과 조건 |
|---|---|---|
| 1 | 동의서 존재 | 양식지에 `privacy-consent` 문항이 있다 |
| 2 | 제3자 제공 동의 존재 | 그 문항의 `consentMeta.thirdParty`가 채워져 있다 |
| 3 | **제공받는 자 일치** | `thirdParty.recipient`가 계약 상대 기관과 일치한다 |
| 4 | **제공 목적 부합** | 계약의 제공 목적이 `thirdParty.purpose` 범위 안이다 |
| 5 | **제공 항목 부합** | 계약이 요구하는 필드가 `thirdParty.items` 범위 안이다 |
| 6 | **보유 기간 내** | 계약 종료일이 `thirdParty.retentionPeriod`를 넘지 않는다 |
| 7 | 소유 주체 명확 | 양식지에 `tenantId`가 있다 |

3~5번은 **문자열 비교로 자동 판정할 수 없다** — "○○연구원"과 "재단법인 ○○연구원"은
같은 기관일 수 있고, 목적·항목은 자연어다. 따라서:

> **자동 판정은 "불일치 의심"을 띄우는 데까지만 쓰고, 최종 통과는 개인정보보호 책임자의
> 명시적 확인(체크 + 사유 기록)으로 처리한다.** 자동 통과시키면 시스템이 법적 판단을
> 대신한 셈이 되어, 사고 시 책임 소재가 사라진다.

### 4-3. 응답자별 동의 여부도 확인해야 한다

동의서 문항은 **필수가 아닐 수 있다**(선택 동의). 응답자가 동의 체크를 하지 않은 건도
있을 수 있으므로, 제공 대상 레코드는 **그 문항에 동의한 응답만** 포함한다.
동의하지 않은 사람의 데이터가 섞여 나가는 것이 가장 흔한 사고 유형이다.

## 5. 외부 기관 인증 — LDAP를 쓸 수 없다

외부 기관은 LDAP 계정이 없다. `User` 테이블에 넣어서도 안 된다 — `User`는 임직원 신원
모델이고, 여기에 외부인을 섞으면 부서 통계·k-익명성 코호트·권한 판정이 전부 오염된다.

### 5-1. 별도 주체로 모델링한다

```
ExternalRecipient  (외부 기관 — User가 아니다)
  └─ DataProvisionContract  (제공 계약)
       └─ ApiKey  (계약에 종속된 접근 키)
```

### 5-2. 기존 `ApiKey`를 재사용하되, 계약에 종속시킨다

`ApiKey` 모델은 이미 필요한 것을 거의 다 갖고 있다 — 해시 저장, scope, 분당 요청 제한,
만료, 폐기, 사용 이력. **새로 만들 이유가 없다.** 다만 지금은 양식지 단위로 자유롭게
발급되므로, 외부 제공용 키는 다음을 추가로 강제한다:

- `contractId` 연결 — 계약 없이는 외부 제공용 키를 발급할 수 없다
- **계약 상태에 종속** — 계약이 만료·해지되면 키도 즉시 무효 (키 자체의 `expiresAt`과
  별개로, 요청 시점에 계약 상태를 매번 확인한다)
- **scope는 READ 고정** — 외부 기관이 데이터를 쓰게 할 이유가 없다
- 제공 대상 양식지·필드를 계약이 정의하며, 키는 그 범위를 넘어설 수 없다

### 5-3. 인증 방식을 왜 이렇게 하는가

| 후보 | 판단 |
|---|---|
| 외부 기관용 로컬 계정(ID/PW) 발급 | ❌ 비밀번호 관리 책임이 생기고, 사람이 로그인해 화면을 보는 순간 마스킹·k 게이트를 화면마다 다시 설계해야 한다 |
| **API 키 (계약 종속)** | ✅ 기계 대 기계. 나가는 데이터가 API 응답 하나로 좁혀져 통제·감사가 쉽다 |
| OAuth/OIDC 연동 | 장기적으로는 타당하나 외부 기관마다 IdP 협의가 필요해 초기 도입 비용이 크다. 후순위 |

## 6. 스키마 (초안)

```prisma
enum TenantStatus { ACTIVE ARCHIVED }

model Tenant {
  id               String   @id @default(cuid())
  code             String   @unique   // "QTD" — 계약서·API에 쓰는 안정 식별자
  name             String   @unique   // "품질기술본부"
  status           TenantStatus @default(ACTIVE)
  // 제공 승인 권한자 — 양식지 제작자와 분리해야 통제가 성립한다
  privacyOfficerId String?
  privacyOfficer   User?    @relation(fields: [privacyOfficerId], references: [id])
  createdAt        DateTime @default(now())

  departments      TenantDepartment[]
  forms            FormRegistry[]
}

// LDAP 부서명 → 테넌트. 부서명이 바뀌어도 매핑만 갱신하면 소유권이 유지된다.
model TenantDepartment {
  id             String @id @default(cuid())
  tenantId       String
  tenant         Tenant @relation(fields: [tenantId], references: [id], onDelete: Cascade)
  departmentName String @unique   // User.department 값과 대조

  @@index([tenantId])
}

// 외부 기관 — User가 아니다. 임직원 신원 모델을 오염시키지 않기 위해 분리한다.
model ExternalRecipient {
  id           String   @id @default(cuid())
  name         String                  // "○○연구원"
  businessNo   String?  @unique        // 사업자/기관 등록번호 — 계약 상대 특정
  contactEmail String
  contactName  String?
  createdAt    DateTime @default(now())

  contracts    DataProvisionContract[]
}

enum ProvisionType {
  INTERNAL_CROSS_TENANT   // 경로 A — 내부 부서 간
  EXTERNAL_THIRD_PARTY    // 경로 B — 외부 기관 (원본/가명)
  ANONYMIZED_STATS        // 경로 C — 익명 통계
}

enum LegalBasis {
  PURPOSE_WITHIN_ART15    // 수집 목적 범위 내
  PURPOSE_BEYOND_ART18    // 목적 외 이용·제공
  THIRD_PARTY_ART17       // 제3자 제공 동의
  ANONYMIZED_ART58_2      // 익명정보 — 개인정보 아님
}

enum ContractStatus { DRAFT PENDING_APPROVAL ACTIVE SUSPENDED EXPIRED TERMINATED }

model DataProvisionContract {
  id             String        @id @default(cuid())
  title          String
  provisionType  ProvisionType
  legalBasis     LegalBasis

  fromTenantId   String                        // 제공하는 부서
  fromTenant     Tenant        @relation("ProvisionFrom", fields: [fromTenantId], references: [id])
  toTenantId     String?                       // 경로 A일 때
  toTenant       Tenant?       @relation("ProvisionTo", fields: [toTenantId], references: [id])
  recipientId    String?                       // 경로 B일 때
  recipient      ExternalRecipient? @relation(fields: [recipientId], references: [id])

  purpose        String                        // 제공 목적 — 동의서와 대조 대상
  itemsScope     String                        // 제공 항목 — 동의서와 대조 대상
  startsAt       DateTime
  expiresAt      DateTime                      // 필수 — 무기한 제공은 허용하지 않는다
  status         ContractStatus @default(DRAFT)

  // 활성화 시점의 동의 적합성 확인 기록 (§4-2) — 자동 판정에만 맡기지 않는다
  consentVerifiedBy   String?
  consentVerifiedAt   DateTime?
  consentVerifyNote   String?

  createdBy      String
  createdAt      DateTime      @default(now())

  forms          ContractForm[]
  apiKeys        ApiKey[]
  logs           DataProvisionLog[]

  @@index([fromTenantId])
  @@index([status, expiresAt])
}

model ContractForm {
  id         String @id @default(cuid())
  contractId String
  contract   DataProvisionContract @relation(fields: [contractId], references: [id], onDelete: Cascade)
  formId     String
  form       FormRegistry @relation(fields: [formId], references: [id])
  // 제공 필드를 명시적으로 좁힌다. 비우면 "전체"가 아니라 "미설정"으로 간주해 차단한다.
  fieldIds   String[]

  @@unique([contractId, formId])
}

// 실제로 무엇이 언제 얼마나 나갔는가 — 계약 이행 증빙이자 남용 탐지 근거
model DataProvisionLog {
  id         String   @id @default(cuid())
  contractId String
  contract   DataProvisionContract @relation(fields: [contractId], references: [id])
  at         DateTime @default(now())
  formId     String
  rowCount   Int
  fieldIds   String[]
  apiKeyId   String?
  actorEmail String?              // 화면에서 내려받은 경우

  @@index([contractId, at])
}
```

`FormRegistry`에 `tenantId String?` 추가, `ApiKey`에 `contractId String?` 추가.
둘 다 **nullable**로 시작한다 — 기존 데이터를 깨지 않고 점진 이행하기 위함이다.

## 7. 화면 설계

### 7-1. `/super-admin` — 현재 Mock 섹션의 대체

하드코딩된 카드 2개를 **실제 집계**로 바꾼다. 테넌트별로:

- 보유 양식지 수 / 누적 응답 수 (실제 `FormRegistry` + ES 카운트)
- 활성 제공 계약 수, 만료 임박 계약 (30일 이내)
- 이번 달 제공 건수 (`DataProvisionLog` 집계)
- 동의 부적합으로 **차단된** 제공 시도 — 이게 가장 중요한 지표다

현재의 "패키징 생성(JSON)", "B2B 거래용 엑셀 추출" 버튼은 **계약을 거치지 않은 직접 추출**을
암시하므로 제거한다. 추출은 반드시 계약 화면을 경유해야 한다.

### 7-2. `/super-admin/tenants` (신규)

부서 목록 / LDAP 부서명 매핑 / 개인정보보호 책임자 지정 / 미할당(`tenantId` 없는) 양식지 경고.

### 7-3. `/super-admin/provisions` (신규)

계약 목록 · 생성 · 승인. 계약 생성 화면에서 **§4-2 검사 결과를 항목별로 표시**하고,
불일치 항목은 책임자가 확인 사유를 적어야 활성화 버튼이 열린다.

### 7-4. `/api/v1/provisions/...` (신규, 외부 기관용)

계약 종속 API 키로만 접근. 응답은 계약이 정의한 양식지·필드로 좁혀지고,
매 요청이 `DataProvisionLog`에 남는다.

## 8. 범위 밖 — 의도적으로 빼는 것

| 항목 | 이유 |
|---|---|
| **과금·정산·청구** | 데이터 제공 통제와 독립적인 별개 도메인이다. 통제 없이 과금부터 만들면 "팔 수 없는 데이터를 파는" 구조가 된다. 제공 통제가 자리 잡은 뒤 별도 설계 |
| **가명처리(제28조의2) 파이프라인** | 가명정보는 동의 없이 통계·연구 목적 처리가 가능해 가치가 크지만, 가명처리 자체가 별도의 큰 설계(식별자 제거·결합키 관리·재식별 금지 통제)다. 경로 C(익명 통계)로 먼저 가치를 확인한 뒤 착수 |
| **외부 기관 OAuth/OIDC** | §5-3 참조. API 키로 시작 |
| **다중 법인 테넌시** | 현재 요구는 "사내 부서 단위"다. 별도 법인까지 확장하면 `User`·LDAP·감사 로그 전반이 바뀐다 |

## 9. 구현 우선순위

| 순위 | 항목 | 이유 |
|---|---|---|
| 1 | **Tenant + TenantDepartment + FormRegistry.tenantId** | 소유 주체가 없으면 나머지 전부가 성립하지 않는다. 마이그레이션 포함 |
| 2 | **경로 C (익명 통계 제공)** | 동의 게이트가 필요 없어 가장 빨리 실제 가치가 나온다. 기존 k=5 자산 재사용 |
| 3 | **`/super-admin` Mock 섹션 실제 집계로 교체** | 지금 가짜 숫자가 노출 중인 상태를 먼저 없앤다 |
| 4 | **DataProvisionContract + 동의 검증(§4-2)** | 경로 B의 전제. 검증 로직이 계약보다 먼저 완성되어야 한다 |
| 5 | **ExternalRecipient + 계약 종속 API 키 + 제공 로그** | 외부 제공 실행 경로 |
| 6 | **경로 A (내부 부서 간)를 ShareRequest에서 승격** | 기존 기능이 이미 부분적으로 동작 중이라 급하지 않다 |

## 10. 결정이 필요한 사항

구현 착수 전에 확인받아야 할 것들:

1. **기관 법인격 구조** — 부서들이 모두 단일 법인 소속인가? 그렇다면 §1-1의 "내부=제18조,
   외부=제17조" 구분이 성립한다. 별도 법인이 섞여 있으면 내부 제공도 제17조가 된다.
2. **개인정보보호 책임자 지정 단위** — 테넌트마다 1명인가, 기관 전체에 1명인가?
   전체 1명이면 `Tenant.privacyOfficerId` 대신 전역 역할로 단순화된다.
3. **미할당 양식지 처리** — `tenantId` 추정에 실패한 기존 양식지를 누가 어떻게 배정할 것인가?
4. **경로 C의 상대 범위** — 익명 통계는 외부에 **누구에게나** 제공 가능한가, 아니면
   그것도 계약을 거쳐야 하는가? (법적으로는 불요하나, 사업적으로 계약을 원할 수 있다)
5. **과금 여부** — §8에서 뺐지만, 애초에 유상 거래가 목표인지 무상 제공 통제가 목표인지에
   따라 이후 우선순위가 달라진다.
